    第 5 章 接口测试用例设计¶

    本章目标

    • 会用等价类和边界值给参数设计取值，不再凭感觉填数字；
    • 会列判定表，把组合型的业务规则测全；
    • 会画状态图，把合法和非法的状态迁移都测到；
    • 会设计负面和异常场景：坏凭证、碰别人的数据；
    • 会把多个接口组合成场景，抓住时序、余额这类藏在流程里的边界；
    • 会给用例排优先级，知道哪些先跑、哪些可以砍掉；
    • 把设计落进 pytest：参数化表格、中文用例编号、smoke 标记。

    前两章解决的是「怎么跑」：requests 发请求，pytest 组织用例，夹具准备数据，接口客户端把重复代码收拢。这一章解决「测什么」。工具再顺手，取值是随手填的、场景是想到哪写到哪的，用例跑得再快也只是在顺手的地方找问题。接口自动化跑一轮才几秒钟，真正贵的是漏测——线上出了问题，你没写到的那个取值没人替你补上。

    本章的全部方法都用练习网站的真实接口演示，每个方法配一组用例，写进工程、跑给你看。读完这一章，工程里的接口用例会从 28 条增加到 79 条，每一条都来自一个明确的设计方法，而不是灵感。

    方法 回答的问题 在哪一节
    等价类与边界值 这个参数该填哪些值？ 5.2
    判定表 几个条件组合起来会怎样？ 5.3
    状态迁移 一个东西的每种状态都能进、能出吗？ 5.4
    负面与异常 故意使坏，系统还守规矩吗？ 5.5
    组合与串联 几个接口按业务顺序走，中间状态对吗？ 5.6
    优先级与粒度 这么多用例，先跑哪些、哪些可以不要？ 5.7

    5.1 设计解决测什么¶

    先看一个反例。测下单接口，随手写三条：买 1 件、买 10 件、买负数件。前两条几乎一样（都成功了），第三条碰巧撞上一个异常。看上去测了，实际上有效输入只盖住一个点，无效输入只靠运气碰到一个。

    有设计的样子是这样的：动手之前先问三个问题——

    1. 文档怎么说？ 数量的约定是 1～999，这就是要验证的承诺：1 行不行，999 行不行，0 和 1000 被不被拦住；
    2. 业务上什么最要紧？ 下单会占库存、支付会扣钱，这些数字的增减比「返回成功」要紧得多；
    3. 怎么使坏？ 数量填字符串、token 伪造一个、去碰别人的订单、下单之后库存被别人买光再支付。

    第 2 章 2.8 节给过一张「一个接口要测哪些方面」的清单，那是从面上看；本章的方法是从点上凿：每个方法负责把清单里的某几行变成具体取值和具体断言。两章合起来，拿到一个新接口就不会发呆，而是有一套固定的动作可做。

    说明

    提示： 本章的方法不依赖练习网站，换任何系统都一样用。变的只有取值和业务码，动作是同一套。

    设计不用写成八股文。一张取值表、一张判定表、一张状态图，加三五句业务规则，就是设计的全部产出物。它们有两个用处：写用例之前，评审表格比评审代码便宜得多，同事一眼能看出「少测了 0」；写完用例之后，表格是用例的说明书，半年后接手的人对着表格能看懂每条用例为什么存在。本章接下来就把这三样东西一样一样做出来。

    5.2 等价类与边界值¶

    5.2.1 两个方法¶

    等价类划分：把输入分成几类，认为同一类里的值服务器会同样对待，每类挑一个代表去测。购买数量可以分成：1～999 之间的整数（有效类）、小于 1（无效类）、大于 999（无效类）、不是整数（无效类）、不是数字（无效类）。全部测完要无穷多条，每类测一个代表，五类五条就够了。

    边界值：问题最爱长在边上。写范围判断时 >= 和 > 一字之差，1 和 999 就会出问题。所以每个边界都取「点上」和「点旁边」的值：下边界测 0 和 1，上边界测 999 和 1000。

    两个方法配合着用：等价类负责「分几类、选代表」，边界值负责「代表优先选边界上的」。

    等价类也完全适用于数字之外的参数。常见的几种参数类型，套这两步就能列出取值：

    参数类型 有效类 无效类 边界值
    整数区间（1～999） 区间内的整数 小于下限、大于上限、非整数、非数字 0、1、999、1000
    字符串长度（2～20 个字） 长度合适的字符串 太短、太长、非字符串、空串 1、2、20、21 个字
    枚举（如订单状态三种取值） 每个合法枚举值各一类 未知枚举值、空值 每个合法值各测一条
    文本关键词（模糊搜索） 能命中的词、确定命不中的词 超长字符串、特殊字符 空串、最长合法长度

    后面几节反复用到这张表，可以先混个眼熟。

    5.2.2 给购买数量列表¶

    下单接口的 quantity，文档约定 1～999。把 5.2.1 的思路落成一张表，每个取值写清属于哪类、预期是什么、为什么选它：

    取值 属于哪类 预期 为什么选它
    1 有效类，下边界 下单成功 最小合法值
    2 有效类 下单成功 下边界内侧再补一个正常值
    998 有效类 下单成功 上边界内侧再补一个正常值
    999 有效类，上边界 下单成功 最大合法值
    0 无效类：小于 1 HTTP 422 恰好在下边界外
    -1 无效类：小于 1 HTTP 422 负数代表
    1000 无效类：大于 999 HTTP 422 恰好在上边界外
    1.5 无效类：非整数 HTTP 422 类型不对
    "abc" 无效类：非数字 HTTP 422 类型不对
    不传（None） 无效类：缺值 HTTP 422 缺值代表

    0 和 1、999 和 1000 卡住两个边界的里外两侧；2 和 998 是有效区间中部的普通代表——正常值也得有，不然整组用例全是边界，看不出边界值和普通值的行为差别。这张表就是用例清单，接下来只是把它翻译成代码。

    5.2.3 翻译成参数化用例¶

    新建 tests/api/test_design_boundary.py。有效取值和无效取值的断言不同，分成两个参数化函数，各管各的：

    # 购买数量的文档约定是 1～999：有效边界 1、2、998、999 都该成功，
# 无效等价类 0、负数、1000、小数、非数字、空值都该被 422 拦下
QUANTITY_VALID = [1, 2, 998, 999]
QUANTITY_INVALID = [
    ("数量为0", 0),
    ("数量为负数", -1),
    ("数量为1000", 1000),
    ("数量是小数", 1.5),
    ("数量不是数字", "abc"),
    ("数量为空", None),
]


@allure.feature("用例设计")
@allure.title("购买数量取有效边界值 {quantity} 件时下单成功，库存随之减少")
@pytest.mark.parametrize("quantity", QUANTITY_VALID, ids=[f"买{q}件" for q in QUANTITY_VALID])
def test_quantity_valid_boundary(api, product, quantity):
    stock_before = ok(api.get_product(product["id"]))["stock"]
    order = ok(api.create_order([{"productId": product["id"], "quantity": quantity}]))
    try:
        assert order["status"] == "UNPAID"
        assert order["amount"] == pytest.approx(product["price"] * quantity)
        assert ok(api.get_product(product["id"]))["stock"] == stock_before - quantity
    finally:
        ok(api.cancel_order(order["orderNo"]))   # 归还库存，下次运行还是同样的初始状态


@allure.feature("用例设计")
@allure.title("购买数量取无效值时返回 422：{title}")
@pytest.mark.parametrize("title, quantity", QUANTITY_INVALID, ids=[c[0] for c in QUANTITY_INVALID])
def test_quantity_invalid(api, product, title, quantity):
    resp = api.create_order([{"productId": product["id"], "quantity": quantity}])
    assert resp.status_code == 422
    body = resp.json()
    assert body["code"] == 422
    assert body["data"][0]["field"].endswith("quantity")

    三个写法上的要点：

    • ids 写中文场景名。 报告里显示「买998件」「数量为负数」，一眼看懂每条用例在测什么，用 -k 挑选时也好认（第 3 章 3.5 节加过让中文原样显示的配置）；
    • 有效用例断业务数据。 只断「返回成功」不够：买 999 件成功了、库存却没扣，照样是缺陷。所以库存的前后变化、金额的计算都断上；
    • 有效用例当场取消订单。 999 件的下单会占库存，finally 里取消掉，跑多少轮数据都不变（第 4 章 4.8 节的第 1 条原则）。

    5.2.4 等价类的划分依据会被实测修正¶

    表里的十个取值全过了。但等价类的划分依据是「我以为服务器怎么想」，实测偶尔会告诉你它另有想法。比如「数量传字符串」这一类，按文档推断该被 422 拦住，实际呢：

    @allure.feature("用例设计")
@allure.title("数量传字符串数字也能下单：接口的校验比界面宽")
def test_quantity_type_lenient(api, product):
    """等价类不能只按文档划：实际系统可能接受文档没提的写法，这类偏差也要有用例盯着。"""
    stock_before = ok(api.get_product(product["id"]))["stock"]
    order = ok(api.create_order([{"productId": product["id"], "quantity": "3"}]))   # 字符串数字
    try:
        assert order["amount"] == pytest.approx(product["price"] * 3)
    finally:
        ok(api.cancel_order(order["orderNo"]))
    assert ok(api.get_product(product["id"]))["stock"] == stock_before

    quantity 传字符串 "3"，下单成功了，金额、库存都对。练习网站的参数校验对「长得像数字的字符串」是宽容的：数字字符串、整数值的小数（1.0）都能过，带小数点的 1.5、字母才被拦。这件事值得专门写一条用例钉住：接口的校验比页面上的输入框宽，页面上你根本输不进字符串，绕过页面直接调接口的人却可以。把它记成预期行为，哪天有人收紧了校验，用例会提醒大家这是有意变更。

    坑

    边界值照着文档抄一遍就完事，等于没测。 文档是开发想做什么，测试要验证实际做成了什么。本章后面「两个空格绕过昵称长度校验」的发现，文档里一个字都没提，全部来自实测。

    5.2.5 每页条数和翻页¶

    搜索接口的 size 约定 1～50，page 从 1 开始。同一个套路，取值表和代码：

    取值 预期
    1 成功，返回 1 条
    50 成功，返回 25 条（全部商品）
    0 HTTP 422
    51 HTTP 422

    翻页还有一个不在文档里的边界：最后一页之外。25 件商品、每页 10 条，第 3 页只剩 5 条，第 4 页应该是空列表，但 total 还是 25：

    # 25 件商品、每页 10 件：第 3 页是最后一页，只剩 5 件；第 4 页已经翻过头。
# 参数名用 page_no 不用 page：page 是 pytest-playwright 的夹具名，重名会被它接管
PAGE_CASES = [
    ("最后一页", 3, 5),
    ("最后一页之后", 4, 0),
]


@allure.feature("用例设计")
@allure.title("翻页的边界：{title}")
@pytest.mark.parametrize("title, page_no, expect_count", PAGE_CASES, ids=[c[0] for c in PAGE_CASES])
def test_page_boundary(guest, title, page_no, expect_count):
    data = ok(guest.search_products(page=page_no, size=10))
    assert data["total"] == 25                     # 翻到哪一页，总数都不变
    assert len(data["items"]) == expect_count

    size 取 1 和 50 的两条成功用例也在文件里（test_size_boundary），取值和预期就是上面那张表。第一次设计时，容易把第 3 页当成「超出去、该是空的」——这正是要实测的原因：页是算出来的，25 除以 10 余 5，余数占着一页。

    坑

    参数名别和夹具重名。 给参数化起名 page，pytest-playwright 的 page 夹具（浏览器页面）会把它接管，用例拿到的是浏览器对象而不是你给的数字，用例编号还莫名其妙多了个「chromium-」前缀。改成 page_no 一切正常。

    5.2.6 昵称长度和两个空格的发现¶

    改昵称接口的 nickname 约定 2～20 个字。边界取值：1 个字、2 个、20 个、21 个、非字符串，有效无效各一组参数化：

    NICKNAME_INVALID = [
    ("昵称只有1个字", "超"),
    ("昵称超过20个字", "超" * 21),
    ("昵称不是字符串", 123),
]

NICKNAME_VALID = [
    ("昵称2个字", "阿宝"),
    ("昵称20个字", "超" * 20),
]

    按这张表测完，边界全部符合预期。还剩最后一个疑问：校验算的是哪个值？ 传两个空格试试：

    PUT /api/users/me，请求体 {"nickname": "  "}

HTTP/1.1 200 OK

{"code":0,"msg":"ok","data":{"username":"bob","nickname":""}}

    两个空格长度正好是 2，通过了长度校验；服务器存昵称之前会去掉首尾空格，最后存进去一个空字符串。再查用户信息，昵称真的变成了空。这条用例（test_nickname_whitespace_quirk）把两步都断上，然后恢复昵称。它算不算缺陷、要不要修，由团队定；测试的职责是发现并钉住它——先校验、后处理，顺序一换行为就变，这类问题只有边界值加实测能挖到。

    5.2.7 一次下单的行数¶

    items 列表还有一个上限：最多 20 行。20 行成功、21 行返回 422，一有效一无效，两条参数化用例各测一头：

    # 一次下单最多 20 行：20 行是有效边界，21 行是无效边界
ITEMS_COUNT_CASES = [
    ("20行", 20, 200),
    ("21行", 21, 422),
]


@allure.feature("用例设计")
@allure.title("一次下单的行数取边界值：{title}")
@pytest.mark.parametrize("title, lines, status", ITEMS_COUNT_CASES, ids=[c[0] for c in ITEMS_COUNT_CASES])
def test_items_count_boundary(api, product, title, lines, status):
    resp = api.create_order([{"productId": product["id"], "quantity": 1} for _ in range(lines)])
    assert resp.status_code == status
    if status == 200:
        ok(api.cancel_order(resp.json()["data"]["orderNo"]))   # 下单成功的当场取消，归还库存

    5.3 判定表：登录的六种组合¶

    5.3.1 先把组合全试出来¶

    等价类一次只看一个参数。如果结果由几个条件共同决定，单看每个条件就不够了：登录的结果由「用户名对不对」和「密码对不对」共同决定。先写个十几行的脚本，把两个条件各取「空、对、错」三种值的九种组合挨个试一遍（存成 scratch/login_grid.py）：

    # 把登录的两个条件各取「空、对、错」三种值，九种组合挨个试一遍，看服务器返回什么业务码
import requests

BASE = "http://127.0.0.1:8000"
USERNAMES = {"空": "", "对": "bob", "错": "nobody"}
PASSWORDS = {"空": "", "对": "bob123", "错": "wrong-password"}

for u_name, username in USERNAMES.items():
    row = []
    for p_name, password in PASSWORDS.items():
        body = requests.post(f"{BASE}/api/login", json={"username": username, "password": password}, timeout=10).json()
        row.append(f"密码{p_name}→{body['code']}")
    print(f"用户名{u_name}：", "  ".join(row))

    5.4 状态迁移：订单的一生¶

    5.4.1 画出状态图¶

    订单有三种状态：待支付（UNPAID）、已支付（PAID）、已取消（CANCELLED）。把它的一生画出来：

                ┌─────────┐  支付   ┌─────────┐
  下单 ────►│ UNPAID  │───────► │  PAID   │ 终态
            │ 待支付  │         │ 已支付  │
            └────┬────┘         └─────────┘
                 │ 取消
                 ▼
            ┌───────────┐
            │ CANCELLED │ 终态
            │  已取消   │
            └───────────┘

    从图上读出两类用例：

    • 合法迁移：UNPAID → PAID（支付）、UNPAID → CANCELLED（取消）。每条都要走到，并核对状态之外的数据（余额、库存）跟着变；
    • 非法迁移：四个角上的组合——已支付再支付、已支付再取消、已取消再支付、已取消再取消，全部该被业务码 3003 拒绝。图上没有的入口也测一个：拿着不存在的订单号做查询、支付、取消，该是 3001。

    状态图一眼就能看出 PAID 和 CANCELLED 没有出去的路，是终态——非法迁移清单就是从这张图上抄下来的。没有图的时候，这些拒绝逻辑藏在接口文档的字缝里，最容易漏。

    拿到一个陌生的系统，状态从哪里找？三个来源：接口文档里的状态字段（订单的 status、任务的 state，字段注释里往往就列着全部取值）；业务码表里的拒绝类提示（「已支付，不能取消」一句话就同时泄露了一个状态和一条非法迁移）；名词表（订单、支付单、退款单，每个业务名词背后通常藏着一个状态机）。把状态罗列出来，把迁移一条条画上去，图自然就有了。

    5.5 负面与异常场景¶

    5.5.1 token 的三种坏法¶

    需要登录的接口，token 是唯一凭证。设计负面用例时问一句：token 能坏出几种花样？ 至少三种：请求头里压根不带、带一个伪造的、带一个格式完全正确但服务器从没发出过的。三种的预期一样：HTTP 401，业务码 40101。

    UNKNOWN_TOKEN = secrets.token_hex(16)   # 每轮运行都不同，但永远不会是服务器发过的

# 三种坏 token，预期都一样：HTTP 401，业务码 40101
BAD_TOKENS = [
    ("不带token", None),
    ("伪造的token", "totally-fake-token"),
    ("格式对但不存在的token", UNKNOWN_TOKEN),
]


@allure.feature("用例设计")
@allure.title("token 三种坏法都被拦下：{title}")
@pytest.mark.parametrize("title, token", BAD_TOKENS, ids=[c[0] for c in BAD_TOKENS])
def test_bad_token(config, title, token):
    client = ShopApi(config["base_url"])
    if token is not None:
        client.session.headers["token"] = token
    resp = client.me()
    assert resp.status_code == 401
    assert resp.json()["code"] == 40101

    三种的实测响应一字不差：

    HTTP/1.1 401 Unauthorized

{"code":40101,"msg":"未登录或 token 无效","data":null}

    为什么伪造的也要单独测？因为「格式正确的假 token」是最常见的一种试探：拿到别人的 token 改一位、自己编一个 32 位十六进制。服务器必须对三种坏法给出同样的回答，任何一种返回了别的东西（比如 500），都是不该出现的行为。另外注意 UNKNOWN_TOKEN 用 secrets.token_hex(16) 现生成，格式和真 token 一模一样——这正是「格式对但不存在」的构造方法。

    注意这条用例用的是自己新建的客户端（ShopApi(...)），没碰共享的 api 夹具。它专门在凭证上使坏，弄脏了共享登录态，后面的用例就全成 401 了。

    token 其实还有一种状态不是用户弄坏的：过期。练习网站默认 token 永不过期，用环境变量把有效期调短再启动，就能构造出「登录过」和「登录过期」（业务码 40102）两种情况的差异，第 6 章 6.4 节的 token 过期与自动续期会用到它。把「没登录、登录过期、伪造、格式对但不存在」四种情况分开编码，前端才能分别处理：跳登录页、静默续期、直接拒绝。设计凭证类用例时，这四种都要过一遍。

    服务器把两行合并成了一行 quantity=2，库存一次扣掉 2，金额 5.0 元。这就是接口文档没写、必须实测才知道的规则。 把它钉成用例（test_same_product_lines_merge）：明细只有一行、数量是 2、库存恰好少 2。哪天有人改了合并逻辑，这条用例最先知道。

    组合类场景的套路是固定的：手工探出真实行为 → 查文档和代码确认是不是有意的 → 写成用例钉住。 跳过中间那步直接写用例，会把缺陷固化成预期。

    5.6.2 时序：下单之后库存被别人买光¶

    两个用户操作同一件商品，顺序不同结果不同。设计之前先问一个业务问题：库存是什么时候扣的？ 练习网站在下单那一刻就扣（下单接口的说明写着「同时占用库存」）。由此推论：我下了单、别人把剩下的买光，我的支付照样该成功，因为库存已经在下单时归我，支付只检查余额。

    构造这个时序：「限量版手办」一共 3 件。user002 下单买 1 件（剩 2），bob 把剩下 2 件全买走（剩 0），user002 再支付自己的订单：

    @allure.feature("用例设计")
@allure.title("下单时库存已锁定：剩下的被别人买光，也不影响我支付")
def test_stock_locked_at_order_time(config):
    """这条用例每跑一次消耗 1 个手办（别人那单会退回）。库存不足 3 件时跳过，
    重启练习网站把数据恢复成初始状态后再跑。"""
    shop = ShopApi(config["base_url"])
    figure = ok(shop.search_products(keyword="限量版手办"))["items"][0]
    stock_before = figure["stock"]
    if stock_before < 3:
        pytest.skip("手办库存不足 3 件，重启练习网站恢复数据后再跑")

    mine = ShopApi(config["base_url"])            # user002 先下单，锁住 1 件
    ok(mine.login("user002", "test123"))
    my_order = ok(mine.create_order([{"productId": figure["id"], "quantity": 1}]))

    other = ShopApi(config["base_url"])           # bob 把剩下的全部买走
    ok(other.login("bob", "bob123"))
    other_order = ok(other.create_order([{"productId": figure["id"], "quantity": stock_before - 1}]))
    try:
        assert ok(shop.get_product(figure["id"]))["stock"] == 0    # 前提：剩下的确实被买光了
        body = mine.pay_order(my_order["orderNo"]).json()
        assert body["code"] == 0, f"库存在下单时已经锁定，支付不该失败：{body}"
    finally:
        ok(other.cancel_order(other_order["orderNo"]))             # bob 那单退掉，只消耗我买的 1 件
        if ok(mine.get_order(my_order["orderNo"]))["status"] == "UNPAID":
            ok(mine.cancel_order(my_order["orderNo"]))             # 我没付成，也退掉

    实测通过。注意这条用例悄悄做了四件数据管理的事：用账号池里的 user002，不动主账号；先断言库存真的到了 0，排除「bob 没买光」的假验证；finally 里把 bob 的订单退掉，就算支付断言失败了数据也回到只消耗 1 件的状态；库存不足 3 件时跳过并写明原因，第二天接着跑不会红一片。消耗型的数据要么当场归还，要么明说消耗多少、怎么恢复，这是时序类用例能不能反复跑的关键。

    同一件事换一种库存策略，结论就反过来：如果系统改成支付时才扣库存，同样的时序里 user002 的支付会失败。这条用例测的其实是「库存锁定时机」这个业务规则本身——规则变了，用例就该变。

    在真实项目里，这种时序往往没法一步到位地构造：另一个用户的操作可能被定时任务抢跑，可能被缓存延迟。常用的办法是把每一步的触发写进脚本，用例里做的是精确编排（就像本条用例那样）；更复杂时，借助环境开关把中间步骤暂停住，再执行下一步。实在构造不出来就退一步：用日志或数据库确认两个操作的真实先后顺序，别按想象中的顺序写断言。

    5.6.3 余额的边界：刚好付得起¶

    金额的边界藏在流程里：支付成功的条件是「余额大于等于订单金额」。第 4 章已经测过边界的外侧（买超过余额的显示器，支付返回 3002），这一条测内侧：把余额买到「付得起的最大台数」，支付必须成功。显示器 1299 元一台，步长清晰：

    @allure.feature("用例设计")
@allure.title("余额边界：买到刚好付得起的最大台数，支付成功")
def test_pay_max_affordable(config):
    """余额边界的里侧。外侧（多买一台就付不起）是第 4 章的 test_pay_balance_not_enough。

    用账号池里的 user001，别把主账号的余额花光。每跑一次把 user001 的余额花到
    不足一台显示器，重启练习网站恢复数据后可以再跑。"""
    user = ShopApi(config["base_url"])
    ok(user.login("user001", "test123"))
    balance = ok(user.me())["balance"]
    monitor = ok(user.search_products(keyword="显示器"))["items"][0]   # 1299 元一台
    quantity = int(balance // monitor["price"])    # 付得起的最大台数（// 是整除）
    if quantity < 1:
        pytest.skip("user001 余额不足一台显示器，重启练习网站恢复数据后再跑")

    order = ok(user.create_order([{"productId": monitor["id"], "quantity": quantity}]))
    body = user.pay_order(order["orderNo"]).json()
    if body["code"] != 0:
        ok(user.cancel_order(order["orderNo"]))    # 没付出去就还掉库存，再报失败
    assert body["code"] == 0, f"余额 {balance} 元买 {quantity} 台应该付得起：{body}"

    数量取值来自当前余额，不是写死的台数，别的环境、别的初始余额照样能跑。两条用例一内一外，把这个边界合围了。

    // 是整除。 balance // price 得到「买得起的最大台数」，写成 / 会得到小数，下单直接 422。Python 的整除符号在这一行是边界计算的基石。

    5.6.4 组合爆炸怎么砍¶

    5.2 到 5.6 的参数都有自己的取值集合，你可能会想：数量 10 个取值 × 行数 2 个取值 × 支付状态 3 个取值……乘起来几十条，要不要全测？不要。 绝大多数参数互不影响，全乘一遍是浪费。砍法只有一条原则：每次只让一个因素取边界值，其余因素取正常值。 比如测数量 999 时，行数用 1 行、商品用普通商品；测 20 行上限时，每行数量用 1。只有当你有理由相信两个因素互相影响时（比如「行数多」和「每行数量大」可能一起触发金额上限），才把它们组合成一条专项用例。本章 51 条新用例里，组合类只有 4 条，就是这个原则的结果。

    5.7 用例优先级与粒度¶

    5.7.1 四档优先级¶

    用例多起来之后，得回答「先跑哪些、哪些能砍」。给每条用例标档：

    档 含义 本章的例子 条数
    P0 冒烟 系统还活着、主链路通不通 支付把待支付变成已支付；两行合并扣一次库存 2
    P1 主流程 正常业务的关键分支 取消归还库存；两种商品一单；库存时序；余额边界；判定表全对；数据隔离三连 8
    P2 边界 参数取值的边界与类型 数量、翻页、每页条数、昵称长度、下单行数 24
    P3 异常提示 纯拒绝、纯提示类 token 三种坏法、非法迁移四条、不存在的订单、判定表的失败行、空格昵称 17

    分档的用处是实打实的：回归时间紧，先跑 P0，两分钟知道系统还能不能用；P3 可以放到夜间跑。P2 边界用例是砍不得的——历史上最多的线上问题出在边界上——时间实在不够时才轮到 P3 让路。

    优先级也不是定一次就完事：新上的功能先用 P0 盯着，稳定后补 P1、P2；反复通过的 P3 可以降频。用 Allure 报告时还能按 @allure.severity 再叠一层重要程度（第 4 章 4.11.5 节的表格）。

    冒烟集要定期修剪。新增主流程用例时补进 smoke；发现某条 P1 用例经常第一个发现问题，把它提拔进冒烟集；反过来，冒烟集里连续几十轮只报环境问题的用例，要及时请出去。冒烟集的标准是又快又有用：条数控制在两位数以内、两三分钟跑完，它才会在每次提交后被真的跑起来。

    5.7.2 一条用例验证一个点¶

    粒度比优先级更容易做错。反例长这样：

    def test_pay_all_in_one(api, unpaid_order):
    ok(api.pay_order(unpaid_order["orderNo"]))
    assert api.pay_order(unpaid_order["orderNo"]).json()["code"] == 3003   # 重复支付被拒
    assert ok(api.get_product(13))["stock"] >= 0                           # 顺带看一眼库存
    assert ok(api.me())["balance"] > 0                                     # 顺带看一眼余额

    一条用例塞了三个验证目标：重复支付被拒、库存合理、余额合理。问题是：第二条断言失败时，你不知道是支付没拦住还是库存真有问题；第一行一旦失败，后面两个「顺带」根本没执行；用例名字说不清它测什么，半年后没人敢删也没人敢改。

    本章的写法是各回各家：重复支付被拒归状态迁移（5.4），库存增减归它所属的下单、取消用例，余额扣减归支付用例自己。一条用例一个验证目标，名字就是把目标说出口。 串联用例（5.6）看起来断了很多，但断的是同一条流程链上的检查点，链断在哪一步，用例就报哪一步，这和「顺带看一眼」有本质区别。

    5.9 常见的坑¶

    现象 原因与解决
    边界值照文档抄了一遍，全过，心里没底 文档是「想做什么」，实测才知道「做成了什么」。每个取值都要真发请求；本章的字符串数量、空格昵称都是实测挖出来的
    参数化变量起名 page，用例编号多了个 chromium- 前缀，断言报错说拿到的是浏览器对象 和 pytest-playwright 的 page 夹具重名了。参数名换一个（比如 page_no）
    想把几个参数的取值组合全测，用例数爆炸 每次只让一个因素取边界值，其余取正常值（5.6.4）；确认两个因素真的互相影响时才做组合
    非法迁移的用例单独跑通过，一起跑就失败 上一条用例把订单支付了，这条拿到的已经是已支付订单，断言全部错位。每条用例自己下一单：登录态可以共享，业务数据不要共享
    边界用例通过了，系统还是有问题 只断言了「返回成功」。有效边界要连业务数据一起断：库存真的少了、金额真的对（5.2.3 的要点）
    跑完 token 用例，后面的用例全是 401 用例把共享的登录态弄失效了。会破坏凭证的操作用专用客户端和专用账号（第 4 章 4.6.1 节的 test_logout_invalidates_token 同理）
    第二天再跑，手办和余额的用例全红 上一轮把库存、余额消耗掉了。要么当场归还，要么 pytest.skip 并注明重启练习网站恢复（5.6.2、5.6.3 的写法），别让用例只能跑一轮
    负面用例断言写成 code != 0 3001 和 3003 混着断都能过，等于没断。断到具体的业务码，状态类再断到提示文案
    用例名叫 test_order_1，过一个月没人知道它测什么 名字说出输入和预期；参数化用例的 ids 写中文场景名，报告和 -k 筛选都受益

    5.10 练习¶

    1. 给商品搜索的 keyword 设计等价类：空字符串、正常关键词、前后带空格的关键词、SKU 编号、超长字符串、特殊字符。先列表格再写成参数化用例，实测对照（提示：空关键词返回全部 25 件；关键词匹配是对名称和编号做模糊搜索，前后带空格也能搜到，因为服务器会先去掉首尾空格——想想这和 5.2.6 的发现像不像）。
    2. 新增收货地址接口 POST /api/addresses 的手机号约定是「1 开头的 11 位数字」，收货人 2～20 个字、详细地址 5～100 个字。给手机号设计 3 条有效、5 条无效的取值，写一条参数化用例（无效的返回业务码 5002）；注意其他字段不合法时返回的是 HTTP 422 而不是 5002，两套校验别混。有效用例测完把地址删掉（DELETE /api/addresses/{id}）。
    3. 把「订单取消后按状态筛选」写成用例：取消一张订单，然后 GET /api/orders?status=CANCELLED 能查到它、status=UNPAID 查不到。写完想想：状态筛选查不到，除了状态不对，还有什么可能？（提示：列表接口只返回自己的订单。）
    4. 给下单接口列一张判定表，条件三个：商品存在？库存够？数量合法？把所有组合和预期业务码列全，然后对照本章和第 4 章已有的下单用例，找出你列了但没人测过的组合（比如「数量和库存都没问题，但商品编号是 0」返回 2001），把它写成用例。
    5. 思考题：5.6.2 的库存时序用例，如果练习网站改成「支付时才扣库存」，用例会先在哪一行断言失败？顺着 finally 清理继续推：两笔订单都取消之后，库存会变成几？这个和初始值对不上的数字，说明了什么？

    5.11 自检清单¶

    • 能说出等价类和边界值各自解决什么问题，给 quantity 不看正文列出全部边界取值；
    • 会列判定表，知道什么情况下两个条件该合并成一行；
    • 能画出订单的状态图，说出全部合法迁移和四条非法迁移；
    • 会设计 token 和数据隔离的负面用例，能解释为什么别人的订单也返回「订单不存在」；
    • 会用「每次只让一个因素取边界」砍组合，说得出什么时候才该真的组合两个因素；
    • 能给自己的用例标 P0～P3，并用 pytest -m smoke 把 P0 挑出来；
    • 知道消耗型数据（库存、余额）怎么处理才能让用例反复跑。
