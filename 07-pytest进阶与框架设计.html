    7.1 conftest.py 的层级规则¶

    第 3 章说过：conftest.py 是文件名固定的特殊文件，pytest 会自动加载它，里面的夹具不需要 import 就能用。当时只建了一个，放在 tests/ 根目录。完整的规则是：

    conftest.py 放在哪个目录，就对哪个目录（含子目录）里的用例生效；用例用到同名夹具时，离得最近的那层优先。

    学完本章，工程里会有两处 conftest.py，后面的 UI 章节还会再加一处，正好是三层分工：

    文件 管什么 例子
    tests/conftest.py 全局夹具，所有用例都能用（第 4 章建的） api、guest、product、unpaid_order
    tests/adv/conftest.py 本章演示用的夹具（本章新建） watch_api、参数化的 guest
    tests/ui/conftest.py 只有 UI 用例用（第 11 章会建） logged_in_page（种 cookie 进浏览器）、失败截图的钩子

    动手加夹具时照这个思路放：所有用例都要用的放 tests/conftest.py，只有接口用例用的放 tests/api/conftest.py，只有某个子目录用的放那个子目录里。放得越准，能用它的人越清楚，误用越少。

    同名夹具就近覆盖：一个 5 行的实验¶

    规则第二条「离得最近优先」光背没用，跑个实验。本章的 tests/adv/conftest.py 里定义了一个夹具 who，它的子目录 tests/adv/deep/ 又有一个自己的 conftest.py，同样定义了 who：

    # tests/adv/conftest.py（节选）
@pytest.fixture
def who():
    return "tests/adv 的 conftest.py"

    # tests/adv/deep/conftest.py（整个文件就这么多）
"""更深一层目录的 conftest.py：它定义的夹具只对 tests/adv/deep 里的用例生效。"""
import pytest


@pytest.fixture
def who():
    return "tests/adv/deep 的 conftest.py"

    两个目录里各放一条用例，都断言自己拿到的 who 是哪一层的版本：

    # tests/adv/test_adv_who.py
"""同名的夹具，用例用到的到底是哪一层定义的？跑一跑就知道。"""


def test_who(who):
    assert who == "tests/adv 的 conftest.py"

    # tests/adv/deep/test_deep_who.py
"""同名的夹具，深层目录里的用例用到的是更深那一层的版本。"""


def test_who(who):
    assert who == "tests/adv/deep 的 conftest.py"

    坑

    **** 写了夹具却报 fixture 'xxx' not found，先查两件事：文件名是不是严格叫 conftest.py（少一个字母都不行）；文件放的位置是不是用例所在目录或它的上级目录。夹具放在平级的兄弟目录里，用例是看不见的。

    坑

    **** 同名覆盖是双刃剑。7.5 节会利用这个规则在 tests/adv 里放一个参数化版的 guest，只影响本章的用例；但如果你在不知情的目录里也定义了同名夹具，用例实际用的版本可能和你以为的不一样。拿不准就跑一次 --fixtures-per-test。

    7.2 夹具的作用域怎么选¶

    第 3 章 3.4 节列过 scope 的三种取值：function（默认，每条用例一次）、module（每个文件一次）、session（整轮一次）。这一节讲怎么选，以及选大了会出什么事。

    先看现在 tests/conftest.py 里的分工，每个作用域都有明确的理由：

    夹具 作用域 为什么
    config、base_url、account session 读文件、定账号，整轮的结果都一样，做一次就够
    api session 登录一次拿 token，整轮共用，省掉几百次登录请求
    guest function 每条用例一个干净的客户端，互不干扰
    product、unpaid_order function 造出来的数据每条用例独立，谁也不踩谁的数据

    一句话概括：只读的、放之四海皆准的用 session；要造数据、会被改动的用 function。 guest 不升级成 session 就是因为它是「可变的」：某条用例往它的请求头里塞个假 token，下一条用例就跟着遭殃。

    实验：两种作用域各被创建几次¶

    tests/adv/test_adv_scope.py 里有两个夹具，一个 session、一个 function，三个参数化的用例都用到它们，夹具被创建时打印一行字：

    """作用域实验：加 -s 运行，看两个夹具各被创建了几次。"""
import pytest


@pytest.fixture(scope="session")
def session_box():
    print("\n创建 session_box")
    return {}


@pytest.fixture
def function_box():
    print("\n创建 function_box")
    return {}


@pytest.mark.parametrize("n", [1, 2, 3])
def test_scope(n, session_box, function_box):
    assert session_box == {} and function_box == {}

    作用域选大了的风险：一次退出登录，全场连坐¶

    session 夹具整轮只有一份，意味着任何一条用例把它改坏，后面所有用例跟着遭殃。拿最典型的登录态做个真实的事故演示。新建一个临时文件（看完就删）：

    # tests/adv/test_adv_tmp_logout.py —— 演示完就删
"""临时文件：演示 session 夹具被一条用例改坏，后面的用例全部受连累。看完就删。"""
from common.api_client import ok


def test_logout_with_shared_client(api):
    ok(api.logout())                 # 错误示范：拿整轮共用的客户端去退出登录


def test_my_orders(api):
    ok(api.list_orders())


def test_my_balance(api):
    assert ok(api.me())["balance"] > 0

    闯祸的那条自己是绿的，被连累的两条全红了，而且报错指向的接口和真正的病灶隔着一个文件——这种「失败原因不在失败用例里」的问题，在实际项目里能耗掉一下午。演示完把这个文件删掉。

    正确的写法第 4 章已经做过：tests/api/test_login.py 里那条「退出登录后原来的 token 失效」的用例，自己新建了一个客户端去登录、退出，不碰共享的 api（第 4 章 4.6 节）。会破坏共享状态的操作，永远用专用数据。

    作用域选型的三条建议收个尾：

    1. 默认 function，有明确的复用理由再升级；
    2. session 夹具里的对象当成「只读的」来对待，用例不要改它；
    3. 拿不准时想想：两条用例同时用它，会不会互相影响？会就别共享。

    module 作用域（每个文件执行一次）介于两者之间，实际项目里出场率很低：一个文件里的用例共享一份数据，多数情况 function 已经够用。真想用 module 时先停一下，问自己这些用例为什么留在一个文件里——如果是同一组输入的重复，参数化是更好的答案。

    坑

    **** 作用域大的夹具不能依赖作用域小的：session 夹具里不能去要一个 function 夹具，pytest 会在用例启动前直接报错（ScopeMismatch，7.7 节有真实报错）。道理也简单：session 的东西整轮一份，function 的东西每条用例一份，前者没法等后者。

    7.3 工厂夹具：用例里要造多份数据¶

    unpaid_order 夹具很好用，但它一次只能给一条用例造一张订单。遇到「下三张单、支付其中一张、断言另外两张还能取消」这样的场景，要么在用例里连写三次下单，要么把夹具改成工厂夹具：夹具不再返回数据本身，返回一个造数函数，用例要几张调几次。

    tests/adv/test_adv_factory.py：

    """工厂夹具：夹具返回一个造数函数，用例要几张造几张。"""
import pytest

from common.api_client import ok


@pytest.fixture
def make_order(api, product):
    """造单工厂：调用一次造一张待支付订单。造出来的单在清理阶段统一处理。"""
    made = []

    def _make(quantity=1):
        order = ok(api.create_order([{"productId": product["id"], "quantity": quantity}]))
        made.append(order)
        return order

    yield _make
    for order in made:   # 清理：只有还没支付的才需要取消，把库存还回去
        if ok(api.get_order(order["orderNo"]))["status"] == "UNPAID":
            ok(api.cancel_order(order["orderNo"]))


def test_pay_one_leave_others_cancellable(api, make_order):
    """一次造 3 张单：支付其中 1 张，另外 2 张还能取消。"""
    orders = [make_order(), make_order(quantity=2), make_order(quantity=3)]
    assert len({o["amount"] for o in orders}) == 3       # 数量不同，金额也各不相同

    paid = ok(api.pay_order(orders[0]["orderNo"]))
    assert paid["status"] == "PAID"

    for order in orders[1:]:
        data = ok(api.cancel_order(order["orderNo"]))
        assert data["status"] == "CANCELLED"
    body = api.pay_order(orders[1]["orderNo"]).json()
    assert body["code"] == 3003                          # 已取消的订单不能再支付

    对照普通夹具看三个变化：

    • _make 是定义在夹具里面的函数，可以带参数（quantity），用例调用时才真正下单；
    • 每造一张单就记进 made 列表，清理阶段统一过一遍：还没支付的取消，把库存还回去，已经支付的和已取消的不动；
    • yield _make 交出去的是函数本身，不是调用结果。

    坑

    **** 工厂夹具有两种典型手误：一是 yield 后面忘了写 return _make——直接 yield 什么都不交，用例拿到 None，一调用就报 TypeError: 'NoneType' object is not callable；二是多打一对括号，写成 yield _make()，交出去的是当场造好的那一条数据，第二次调用就报 TypeError: 'dict' object is not callable。看到 object is not callable 先检查夹具交出去的是函数还是结果。

    7.4 autouse 夹具：自动给每条用例做的事¶

    到目前为止，用例都是把夹具名写进参数才能用它。autouse 夹具反过来：声明了 autouse=True，作用范围内每条用例都自动执行它，用例一个字都不用写。 适合做「每条用例都该有、但谁也不想每条都写」的事，比如记日志、记耗时、清理临时目录。

    本章在 tests/adv/conftest.py 里写了一个实用的例子：自动记下每条用例发过的每个接口请求，用例失败时把最慢的几个打印出来，省得你去猜失败是不是接口慢造成的。

    # tests/adv/conftest.py（节选）
@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_makereport(item, call):
    """把每条用例各阶段的结果记到用例对象上，夹具在清理阶段才能知道用例有没有失败。"""
    outcome = yield
    rep = outcome.get_result()
    setattr(item, f"rep_{rep.when}", rep)


@pytest.fixture(autouse=True)
def watch_api(request, api):
    """自动对每条用例生效：记下它发过的每个接口请求，失败时把最慢的几个打印出来。"""
    calls = []
    original = api.request

    def timed_request(method, path, **kwargs):
        start = time.perf_counter()
        resp = original(method, path, **kwargs)
        calls.append((f"{method} {path}", (time.perf_counter() - start) * 1000))
        return resp

    api.request = timed_request
    yield
    api.request = original
    rep = getattr(request.node, "rep_call", None)
    if rep is not None and rep.failed and calls:
        print("\n这条用例发过的接口请求，按耗时排最慢的 3 个：")
        for name, ms in sorted(calls, key=lambda c: c[1], reverse=True)[:3]:
            print(f"  {ms:6.0f} 毫秒  {name}")

    几个要点：

    • api.request 是客户端发所有请求的必经之路（第 4 章 4.3 节），把它临时换成一个会记耗时的版本，用例毫无感知；yield 之后再换回去；
    • 开头那个钩子把每条用例的结果记下来，夹具在清理阶段才能知道用例失败没有——yield 之后用例已经跑完，但结果不查是拿不到的。第 11 章做 UI 失败截图时还会用到同一个套路；
    • 只有失败时才打印，通过时一行输出都不添。

    7.5 参数化夹具：同一个夹具跑多份参数¶

    第 3 章 3.5 节的 parametrize 解决的是「同一份逻辑换数据」：登录失败的数据换四组，用例就跑四遍。参数化夹具解决的是另一件事：同一组用例，换的是准备出来的环境。

    最典型的场景是登录态。查「我的信息」这个接口，合法 token 应该查得到，假 token 和不带 token 都该被挡在门外——这三种情况下用例步骤完全一样，差的只是客户端处在什么状态。把 guest 参数化成三种客户端，一条用例就覆盖了三种登录态。

    tests/adv/conftest.py 里的这段定义，覆盖了外层的同名 guest（7.1 节刚讲过就近覆盖的规则，这就是一个实用场景）：

    # tests/adv/conftest.py（节选）
@pytest.fixture(params=[("合法token", True), ("假token", False), ("不带token", False)],
                ids=["合法token", "假token", "不带token"])
def guest(request, config, api):
    """本目录专用的客户端：同一个夹具名，按参数造出三种登录态的客户端。"""
    kind, _ = request.param
    client = ShopApi(config["base_url"], timeout=config["timeout"])
    if kind == "合法token":
        client.session.headers["token"] = api.token    # 借用 api 夹具的登录态
    elif kind == "假token":
        client.session.headers["token"] = "deadbeef" * 4
    return client

    夹具通过 request.param 拿到当前这组参数，ids 给每组起名字。用例本身一行参数都不用加，写法和普通夹具一样：

    xfail：已知缺陷先做标记¶

    测试过程中经常碰到开发暂时不修的缺陷。相关的用例删掉可惜（修复后还得靠它验证），留着又天天红。xfail 的语义是：这条用例会跑，但预计失败；失败了记 XFAIL，算正常；要是它通过了，记 XPASS，反而是个信号。

    演示用的例子是测试工程自己的一个小工具（真实项目里对应的是被测系统的缺陷）：

    # tests/adv/test_adv_skip_xfail.py（节选）
def apply_discount(amount, percent):
    """打折工具：percent 是减掉的百分比，比如 20 表示打八折。

    已知缺陷：计算结果用 int() 截断，丢了小数部分（缺陷单 #1024，开发还没修）。
    """
    return int(amount * (100 - percent) / 100)


@pytest.mark.xfail(reason="缺陷 #1024：折扣金额被截断丢了小数，开发修复后这条会变成 XPASS", strict=True)
def test_apply_discount_keeps_cents():
    assert apply_discount(199.0, 20) == pytest.approx(159.2)

    int() 把 159.2 截成了 159，断言失败，正好落进 xfail 的预期里，上一小节的输出里已经见过：XFAIL，汇总会带出 reason。

    关键是 strict=True。它的意思是：这条用例不允许悄悄变绿。哪天开发把 int() 改对了，用例通过，XPASS 会直接升级成 FAILED，逼着你来处理——多半是把标记删掉，让这条用例恢复成普通用例。演示一下缺陷修好后的样子（临时文件，看完就删）：

    # tests/adv/test_adv_tmp_xpass.py —— 演示完就删

    return round(amount * (100 - percent) / 100, 2)     # 开发已经修好：保留两位小数

    assert apply_discount(199.0, 20) == pytest.approx(159.2)

    assert apply_discount(199.0, 20) == pytest.approx(159.2)

    7.7 monkeypatch：用例里临时改环境变量和函数¶

    有时候要在用例运行期间临时改点东西：换个环境变量试试配置读取的逻辑，把某个接口的方法换成假返回试试业务函数。要求只有一条：用例结束后必须还原，不能影响后面的用例。 这件事 pytest 内置的 monkeypatch 夹具替你做好了，用例结束（包括失败的情况）自动还原。

    临时改环境变量：setenv¶

    第 4 章 4.4 节的配置读取按 TEST_ENV 环境变量找 config/<环境名>.yaml。写条用例验证「环境名指向不存在的文件时，报错要说清楚是哪个文件」：

    # tests/adv/test_adv_monkeypatch.py（节选）
def test_config_reads_chosen_env(monkeypatch):
    """临时把环境名换成 staging：配置文件不存在时，报错要说清楚是哪个文件没找到。"""
    load_config.cache_clear()                     # 配置读一次就会缓存，先清掉再实验
    monkeypatch.setenv("TEST_ENV", "staging")
    with pytest.raises(FileNotFoundError) as exc_info:
        load_config()
    assert "staging.yaml" in str(exc_info.value)

    monkeypatch.setenv(名字, 值) 临时设置环境变量，用例结束自动还原成原来的值。load_config.cache_clear() 是因为配置模块用了 @cache 缓存，不清掉的话读到的是上一轮的缓存结果。

    临时换函数：setattr¶

    更常用的场景是把依赖换成假的。order_summary 这个业务函数依赖 api.list_orders() 的返回，要测它不必真下一堆单，把方法临时换掉就行：

    # tests/adv/test_adv_monkeypatch.py（节选）
class FakeResponse:
    """假的接口返回：只实现业务函数用到的部分。"""

    def __init__(self, data):
        self.status_code = 200
        self.text = str(data)
        self._data = data

    def json(self):
        return {"code": 0, "msg": "ok", "data": self._data}


def order_summary(api):
    """业务函数：把订单列表整理成一句话。它只依赖 api.list_orders() 的返回。"""
    data = ok(api.list_orders())
    if not data["items"]:
        return "还没有订单"
    latest = data["items"][0]["orderNo"]
    return f"共 {data['total']} 张订单，最新一张是 {latest}"


def test_order_summary_with_fake_return(api, monkeypatch):
    """把 list_orders 换成假返回：不用真的下单，也能测业务函数。"""
    fake = FakeResponse({"total": 2, "items": [{"orderNo": "ORD0001"}, {"orderNo": "ORD0002"}]})
    monkeypatch.setattr(api, "list_orders", lambda status=None: fake)
    assert order_summary(api) == "共 2 张订单，最新一张是 ORD0001"


def test_order_summary_back_to_real(api, unpaid_order):
    """上一条用例结束后 list_orders 已经自动还原：能查到夹具刚造的那张单。"""
    assert unpaid_order["orderNo"] in order_summary(api)

    第二条用例是给「自动还原」做的证明：它跑在假返回那条之后，list_orders 已经是真方法，能查到夹具刚造的那张订单。整个文件运行：

session scoped request object. Requesting fixture stack:

    第二个：图省事直接赋值、不走 monkeypatch，还原就没人管了。把共享客户端的方法直接换掉：

    api.list_orders = lambda status=None: None      # 直接赋值，没人负责改回去

    7.9 用例的发现规则与组织¶

    pytest 怎么找出哪些是用例？三条规矩：

    • 文件名以 test_ 开头（或者以 _test 结尾）；
    • 用例是 test_ 开头的函数；
    • Test 开头的类也算一组候选，但类里不能写 __init__ 方法。

    第三条的限制最容易被忽略：类里写了 __init__，整个类会被跳过，只留一条警告：

    PytestCollectionWarning: cannot collect test class 'TestWithInit' because it has a __init__ constructor

    所以收用例时如果发现某几条怎么都不被执行，先看看它们是不是在带 __init__ 的类里。

    目录怎么分组¶

    pytest.ini 里的 testpaths = tests 限定了只在 tests 里找。到本章为止，工程的分组是这样：

    tests/
├─ conftest.py        全局夹具
├─ api/               接口用例
└─ adv/               本章演示（带自己的 conftest.py 和 deep 子目录）

    后面 UI 章节（第 8～11 章）会加一个 ui/ 目录放 UI 用例。分组按「怎么跑、要什么环境」来切，和被测系统的模块划分不是一回事：接口用例一秒几百条、不需要浏览器；UI 用例要开浏览器、慢；各自的专用夹具放在各自的 conftest.py 里。想让 pytest 自己交代一下找到了什么，用收集模式：

    (.venv) > pytest tests\adv --collect-only
collected 15 items

<Dir ch7>
  <Dir tests>
    <Dir adv>
      <Dir deep>
        <Module test_deep_who.py>
          <Function test_who>
      <Module test_adv_autouse.py>
        <Function test_me_still_works>
      <Module test_adv_factory.py>
        <Function test_pay_one_leave_others_cancellable>
      ...

    本章在 tests/adv 里放了几条演示用例，你自己的接口用例有多少条，把目录换成 tests\api 一跑便知。加 -q 后统计更快：pytest --collect-only -q 的最后一行就是总数。

    顺带说一类既不是用例也不是夹具的代码：造测试手机号的函数、拼签名的工具、计算折扣的方法。这类普通函数放 common/ 里，用例用 import 明明白白地引进来。conftest.py 只放夹具和钩子——它靠约定自动加载，塞太多普通函数进去，读用例的人就找不到函数是哪来的了。

    测试类什么时候用¶

    类可以把一组用例归在一起，最常见的用途是给整组打同一个标记——标记写在类上，类里每条用例都带上：

    # 在 tests/api 下临时新建验证（看完就删）
@pytest.mark.smoke                       # 标记写在类上，类里每条用例都带上
class TestProductDetail:
    def test_name(self, guest):
        assert ok(guest.get_product(1))["name"] == "蓝牙耳机"

    def test_price(self, guest):
        assert ok(guest.get_product(1))["price"] == 199.0

    pytest -m smoke --collect-only -q 里能看到两条都被选中了。除此之外不必刻意用类：目录和文件已经承担了分组职责，函数式用例读起来更短；类唯一的额外能力（classmethod、共享 self 属性）在测试里很少用得上，还容易诱导人写出用例之间的依赖。

    7.10 插件机制初识¶

    从第 3 章 3.2 节第一次运行 pytest 起，输出里就一直带着这行：

    plugins: allure-pytest-2.16.2, anyio-4.15.1, locust-2.47.0, playwright-0.10.0, xdist-3.8.0

    这就是 pytest 的插件机制在工作。规律很整齐：

    • 名字：插件包都叫 pytest-xxx（pytest-xdist、pytest-timeout、pytest-html），装进虚拟环境就自动生效，不需要在配置里注册；
    • 入口：插件的命令行参数和普通参数混在一起，pytest --help 里按来源分组。找某个功能是哪个插件提供的，看分组标题就行：
    reporting:
  --alluredir=DIR       Generate Allure report in the specified directory (may not exist)
  --clean-alluredir     Clean alluredir folder if it exists
...
Playwright:
  --browser={chromium,firefox,webkit}
  --browser-channel=BROWSER_CHANNEL
  --tracing={on,off,retain-on-failure}
...
distributed and subprocess testing:
  -n, --numprocesses numprocesses

    输出里那几个插件各管一摊：allure-pytest 第 4 章已经在用，其余几个后面才登场：

    插件 入口 用在哪
    allure-pytest --alluredir、allure.step、附件 第 4 章 4.11 节的报告
    pytest-xdist pytest -n 4、worker_id 夹具 并行执行（第 19 章 19.3 节）
    pytest-playwright --browser-channel、page 夹具、trace UI 用例（第 11 章 11.1 节）
    locust 压测工具安装时顺带注册的插件，用例里用不到 性能测试部分（第 13 章起）

    想加新插件时，先过三个问题：

    1. 内置参数真的不够用吗？ 比如「防止用例卡死」的诉求，requests 层的 timeout 加上 UI 层的等待策略已经盖住大半，剩下的才轮到 pytest-timeout；
    2. 收益能说清楚吗？ 像 pytest-randomly 那样「随机打乱用例顺序、专治用例间隐含依赖」，收益明确，值得；只是「听说大家都在用」的，缓一缓；
    3. 代价接受吗？ 每个插件多一份依赖，多一份和 pytest 版本、其他插件冲突的可能，流水线上多一个会坏的环节。

    插件装了就要写进 requirements.txt，别人（包括三个月后的你和流水线）才能复现同一套环境。

    坑

    **** 本机手动 pip install 了新插件、没写进 requirements.txt，本机越跑越顺，换台机器或流水线一跑就报 unrecognized arguments。装完插件立刻补依赖清单，把它当成收尾步骤。

    ┌─────────────────────────────────────────────────────────────┐
│ 用例层   tests/api/  tests/adv/  （UI 章节加 tests/ui/）      │

├─────────────────────────────────────────────────────────────┤
│ 业务封装层   common/api_client.py（ShopApi）   pages/（页面对象）│

    什么时候才值得抽象¶

    新手最容易犯的错是反向的：还没写几条用例，先花一周搭「大框架」——配置中心、关键字驱动、全量数据外部化。经验法则是：

    1. 重复三次再抽。 第一次直接写，第二次容忍重复，第三次出现时你已经知道三种用法哪里一样哪里不一样，抽出来的接口才对；
    2. 抽象要还债。 每一层封装都让排查多跳一跳：用例红了，要先穿过夹具层、业务层才能看到请求。没有复用收益的抽象是纯负债；
    3. 先让用例好读。 新同事打开一条用例，不问代码就能说出它在测什么，这一条比任何设计模式都优先。

    判断「该不该再抽一层」，问三个问题：这段逻辑有几个用例在用？它变了要改几处？新人不看注释看得懂吗？三个答案分别是「多」「一处」「看得懂」，抽象才算赚钱。

    拿这套工程验一遍：接口地址变了，改 ShopApi 的一个方法，一处；换测试环境，改一份配置文件，一处；来了新业务场景，加一条用例，公共层零改动。每一层只对一种变化负责，变化来了就只有一个去处——这就是分层分对了的样子。

    7.13 常见的坑¶

    坑

    **** session 夹具里的可变状态，并行执行时每个进程各有一份，指望它做全工程共享的计数或汇总必出错。实测：8 条用例往 session 夹具的字典里累加，单进程总数是 8；用 pytest -n 4 并行跑，断言 count == 8 的那条每次都挂，报错是 这个进程只看到了 2 次累加——每个进程各建了一份夹具，各数各的。并行时的几个进程各有各的内存，彼此看不到对方的数据（并行执行的细节在第 19 章 19.3 节）。

    坑

    **** autouse 夹具滥用。第一宗罪是让用例「看不出」自己依赖了什么：读用例的人从参数列表里完全看不到它。第二宗罪是代价放大：作用范围里每条用例都执行一遍，里面一次网络请求、一次 sleep，全套用例每条都要付。autouse 只留给「对每条用例都必要且用例无需关心」的事，比如记耗时、清理临时目录。

    坑

    **** 工厂夹具忘了把函数交出去。yield 后面什么都不写，用例拿到 None，一调用就报 TypeError: 'NoneType' object is not callable；多写一对括号变成 yield _make()，交出去的是当场造好的那一条数据，第二次调用报 TypeError: 'dict' object is not callable。记住口诀：yield 的是函数本身，不是函数的返回值。

    坑

    **** monkeypatch 出了用例就失效，这是特性不是缺陷。反过来，绕开 monkeypatch 直接赋值（api.list_orders = ...），出了用例没人还原，共享的 session 客户端从此带着假方法跑完全场，后面的用例报出与自身无关的错误。临时替换一律走 monkeypatch；另外它是 function 作用域，session 夹具里用不了，硬用会在用例启动前报 ScopeMismatch。

    坑

    **** 参数化的夹具，每个参数各起一份实例。把 guest 参数化成三种登录态，三条用例拿到的是三个不同的客户端，--setup-show 里能看到三次 SETUP F guest[...]。在参数化夹具里做昂贵的事（登录、造大批数据），开销按「用例数 × 参数数」计算，先算这笔账再决定参数化什么。

    坑

    **** 同名夹具就近覆盖，你以为用的是这一层，实际用的是更近的那一层。tests/adv 里参数化的 guest 只对本目录生效，但如果你忘了它的存在，看着全局的 guest 定义去理解本目录的用例，会对不上。排查方法固定：pytest --fixtures-per-test，每个夹具来自哪个文件哪一行，直接写在输出里。

    坑

    **** 作用域大的夹具依赖作用域小的夹具，pytest 直接拒绝启动：在 session 夹具的参数里写上 function 作用域的夹具（monkeypatch 就是一个），报 ScopeMismatch: You tried to access the function scoped fixture ... with a session scoped request object。session 的东西整轮一份，等不起每条用例变一次的东西。

    坑

    **** --lf 依据的是 .pytest_cache 里的上次失败记录，删除或改名用例后记录不会跟着清。再跑时看到 run-last-failure: N known failures not in selected tests 属正常；反过来，交接工程前清一下 .pytest_cache（已在 .gitignore），别让你的失败清单影响下一个人第一次运行的结果。

    7.14 练习¶

    1. 把 make_order 工厂改成支持指定商品：加一个 product_id 参数，不传时用默认商品。写一条用例，用中性笔和马克杯各下一单，断言两张订单的金额各是单价乘数量，再确认清理阶段两张单都处理了（用 -o log_cli=true 看日志）。
    2. 写一个 autouse 夹具：给每条用例计时，超过 1 秒的打印一条警告（用例名加耗时），放进 tests/adv/conftest.py，用 -s 验证它对每条用例都生效。
    3. 把 apply_discount 里的 int() 改成保留两位小数的写法，跑 pytest tests\adv\test_adv_skip_xfail.py，看 XPASS(strict) 怎么变成 FAILED；把 xfail 标记删掉再跑一次，确认这条用例转绿。
    4. 在 test_adv_monkeypatch.py 里加一条用例：用 monkeypatch.setenv("TEST_ENV", "local") 加 load_config.cache_clear()，断言读出来的 base_url 是本机练习网站的地址，跑完确认环境变量已还原。
    5. 组合筛选：依次运行 pytest -m "not concurrency" -q、pytest tests\adv -k "discount or race" -v、pytest --collect-only -q，分别说清每条命令选中了哪些用例、为什么。

    7.15 自检清单¶

    • 能说清 conftest.py 的层级规则，会用 --fixtures-per-test 查一个夹具到底来自哪一层；
    • 能给 config、api、guest、unpaid_order 说出各自的作用域和理由，知道 session 夹具被一条用例改坏会发生什么；
    • 会写工厂夹具，知道清理代码放在哪、什么时机执行；
    • 能说出 autouse 夹具适合做什么、什么时候不该用；
    • 会用参数化夹具让一组用例跑多种环境，分得清它和 parametrize 的分工；
    • 分得清 skip 和 xfail 各自的语义，知道 strict=True 防的是什么；
    • 会用 monkeypatch 临时改环境变量和函数，知道它和直接赋值的区别；
    • 记得住 -x、--lf、--tb=short、-s、--durations 各自解决什么问题。

    到这里，接口自动化的小框架就定型了：用例层只写业务，夹具层管前置和清理，业务封装层对齐接口，配置和数据各自独立，pytest 的进阶能力把运行条件、排查效率都接管起来。下一章我们打开浏览器，开始 UI 自动化——这一章搭好的夹具和分层会原样复用，UI 用例只写页面上的事。
