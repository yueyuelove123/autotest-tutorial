    第 8 章 UI 自动化基础¶

    本章目标

    • 知道 UI 自动化适合做什么、不适合做什么；
    • 写出第一个 UI 脚本，会用录制工具生成代码；
    • 掌握定位元素的推荐写法；
    • 会常用的页面操作；
    • 理解自动等待，会用 expect 做断言，不写 sleep；
    • 把 UI 脚本写成 pytest 用例。

    8.1 UI 自动化适合做什么¶

    UI 自动化是让程序像人一样操作浏览器：打开页面、点按钮、填表单，再检查页面显示得对不对。它最接近用户的真实使用，但也最慢、最容易受页面改动影响。所以要用在刀刃上：

    适合 不适合
    核心业务流程的冒烟检查：登录、下单、支付 接口层就能测的业务规则（各种参数校验、金额计算）
    页面上的交互逻辑：弹窗、提示、按钮的可用与禁用、跳转 还在频繁改版的页面
    前后端的衔接：页面有没有调对接口、有没有正确显示返回的数据 一次性的需求、很少再回归的功能
    每次发版都要回归的固定流程 验证码、人机验证、需要人眼判断的视觉效果

    一条原则：能在接口层测的，不放到 UI 层测。 一条 UI 用例的耗时顶得上几十条接口用例，页面一改还要跟着维护。

    8.2 认识 Playwright¶

    Playwright 是微软开源的浏览器自动化工具，支持 Chromium（Chrome、Edge 的内核）、Firefox、WebKit（Safari 的内核）三种浏览器，有 Python、JavaScript、Java、.NET 四种语言的版本。和老牌的 Selenium 相比：

    Playwright Selenium
    等待 每次操作前自动等元素就绪 要自己写显式等待，漏写一处就可能时好时坏
    安装 pip install 加一个浏览器就能用 早年要单独配浏览器驱动，4.6 版以后会自动下载
    调试 自带录制、单步调试、操作录像回放 依赖第三方工具
    网络 能拦截、修改、模拟接口请求 能力有限
    生态 新项目的主流选择 历史最久，老项目和资料最多，浏览器覆盖更广

    新项目、新手入门选 Playwright 更省心。公司里已经有大量 Selenium 代码的，学会 Playwright 再看 Selenium 也很快，核心思路是一样的。

    8.3 第一个 UI 脚本¶

    确认练习网站在运行，新建 scratch/first_ui.py：

    # 第一个 UI 脚本：打开浏览器登录，确认进入商品页，截一张图
from playwright.sync_api import expect, sync_playwright

with sync_playwright() as p:
    # channel="chrome" 用本机装的 Chrome；headless=False 能看到浏览器；slow_mo 让每步慢 500 毫秒，方便看清
    browser = p.chromium.launch(channel="chrome", headless=False, slow_mo=500)
    page = browser.new_page()
    page.goto("http://127.0.0.1:8000/login.html")
    page.get_by_label("用户名").fill("alice")
    page.get_by_label("密码").fill("alice123")
    page.get_by_role("button", name="登录").click()
    expect(page.get_by_test_id("welcome")).to_have_text("欢迎，alice")
    page.screenshot(path="first_ui.png")
    print("登录成功，截图保存在 first_ui.png")
    browser.close()

    (.venv) > python scratch\first_ui.py
登录成功，截图保存在 first_ui.png

    你会看到 Chrome 自己打开、填好用户名密码、点登录、跳到商品页，然后关掉。工程根目录下多了一张截图。（没装 Chrome 的，按第 1 章 1.5 节「浏览器」那一段改掉 channel="chrome"。）

    逐行看：

    代码 作用
    sync_playwright() 启动 Playwright。sync 表示同步写法，一行执行完再执行下一行，最好理解
    p.chromium.launch(...) 启动浏览器。headless=True（默认）不显示窗口，跑得更快，适合正式执行；调试时用 False
    browser.new_page() 打开一个新标签页
    page.goto(地址) 打开网址，会等页面加载完
    page.get_by_label("用户名") 找到标签文字是「用户名」的输入框
    .fill("alice") 清空输入框再填入内容
    page.get_by_role("button", name="登录") 找到名字是「登录」的按钮
    .click() 点击
    expect(...).to_have_text(...) 断言元素的文字，会自动等待，最多等 5 秒
    page.screenshot(path=...) 截图

    Playwright 里有三层概念：浏览器（browser）里可以开多个互相隔离的上下文（context，相当于一个独立的无痕窗口，cookie 互不相通），上下文里可以开多个页面（page，标签页）。browser.new_page() 是自动建一个上下文再开页面的简写。

    8.4 录制：让工具帮你写代码¶

    不知道代码怎么写的时候，可以先录制：

    (.venv) > playwright codegen --channel chrome --target python-pytest http://127.0.0.1:8000/login.html

    会打开两个窗口：一个浏览器，一个代码窗口。你在浏览器里登录、搜索、购买，代码窗口里就会实时生成对应的代码。工具栏上还有几个断言按钮（检查可见、检查文字、检查输入值），点一下再点页面元素，就会生成一条断言。

    --target python-pytest 生成 pytest 用例的写法，加 -o scratch/recorded.py 可以直接保存到文件。

    录出来的代码只能当草稿：

    • 会录下多余的操作，比如多点了一下输入框；
    • 定位写法不一定合适，个别地方会用位置或者很长的文字；
    • 断言很少，需要你自己补上真正要检查的东西；
    • 没有分层，直接用会和第 4 章接口自动化之前一样难维护。

    推荐的用法：录一遍，看看每一步该用什么定位写法，再按本章和下一章的写法整理成正式用例。

    8.5 定位元素（重点）¶

    UI 用例失败，最常见的原因是找不到元素或找错了元素。定位写得好，页面小改也不受影响；写得不好，开发调一下布局用例就全挂。

    8.5.1 推荐的定位方式¶

    Playwright 推荐按用户看到的样子去找元素，而不是按页面代码的结构。按推荐程度排序：

    写法 什么时候用 练习网站上的例子
    get_by_role(角色, name=名称) 首选。按钮、链接、输入框、标题、表格行等都有角色 page.get_by_role("button", name="搜索")、page.get_by_role("link", name="我的订单")
    get_by_label(文字) 有标签文字的表单项 page.get_by_label("关键词")、page.get_by_label("状态")
    get_by_placeholder(文字) 输入框里的灰色提示文字 page.get_by_placeholder("商品名称或编号")
    get_by_text(文字) 没有交互的普通文字 page.get_by_text("商品列表")
    get_by_test_id(值) 开发专门给测试加的属性 data-testid page.get_by_test_id("welcome")
    locator("css 选择器") 上面都不好用时 page.locator("#keyword")
    locator("xpath=...") 最后的手段 page.locator("xpath=//input[@id='keyword']")

    常用的角色：button（按钮）、link（链接）、textbox（输入框）、checkbox（复选框）、combobox（下拉框）、heading（标题）、row（表格行）、cell（单元格）、dialog（弹窗）、alert（警告提示）、status（状态提示）。

    get_by_text 和 name= 默认是模糊匹配：page.get_by_text("耳机") 能找到「蓝牙耳机」和「头戴式耳机」两个；要精确匹配加 exact=True，page.get_by_text("蓝牙耳机", exact=True)。

    data-testid 值得和开发约定。 它不会因为改文案、改样式而变化，是最稳定的定位方式。练习网站给欢迎语、余额、商品行、订单行都加了 data-testid。

    8.5.2 缩小范围：先找到行，再找行里的按钮¶

    商品列表每一行都有一个「购买」按钮，要点的是「无线鼠标」那一行的：

    row = page.get_by_test_id("product-row").filter(has_text="无线鼠标")   # 包含「无线鼠标」的那一行
row.get_by_role("button", name="购买").click()                         # 这一行里的购买按钮

    filter(has_text=...) 从一组元素里筛出包含某段文字的，再在它里面继续找。这种「先定位到容器，再在容器里找」的写法非常常用。

    8.5.3 严格模式：找到多个会报错¶

    如果直接写 page.get_by_role("button", name="购买").click()，会报错：

    Locator.click: Error: strict mode violation: get_by_role("button", name="购买") resolved to 10 elements:
    1) <button type="button">购买</button> aka get_by_role("row", name="SKU0001 蓝牙耳机 ¥199.00 100000 购买").get_by_role("button")
    2) <button type="button">购买</button> aka get_by_role("row", name="SKU0002 头戴式耳机 ¥399.00 100000 购买").get_by_role("button")
    ...

    页面上有 10 个「购买」按钮，Playwright 不知道你要点哪个，干脆报错，而不是随便点一个。这是好事：随便点一个，用例可能「通过」了但测的根本不是你想测的东西。报错信息里还贴心地给出了每个元素更精确的写法。

    解决办法是缩小范围（上一节的写法）。.first、.nth(2) 也能取第一个、第三个，但按位置取很脆弱，列表顺序一变就点错了，尽量少用。

    8.5.4 不推荐的写法¶

    page.locator("xpath=/html/body/main/table/tbody/tr[4]/td[5]/button")   # 绝对路径，页面结构一变就失效
page.locator(".css-1x2y3z")                                          # 自动生成的样式名，每次构建都可能变
page.locator("table tr:nth-child(4) button")                         # 按位置，数据一变就点错行

    8.5.5 怎么找到元素的信息¶

    • 在页面上右键要定位的元素，选「检查」，开发者工具会定位到它的代码，看看它有没有 id、data-testid、<label>；
    • 用 playwright codegen 打开页面，点工具栏的 Pick locator，鼠标移到元素上就会显示推荐的定位写法。

    8.6 常用操作¶

    操作 写法
    打开网址 page.goto("http://127.0.0.1:8000/products.html")
    点击、双击 locator.click()、locator.dblclick()
    输入（先清空） locator.fill("耳机")
    一个字一个字地输入 locator.press_sequentially("耳机", delay=100)，用于要监听每次按键的输入框
    按键 locator.press("Enter")、locator.press("Control+A")
    下拉框选择 locator.select_option(label="已取消")，也可以按 value= 选
    勾选、取消勾选 locator.check()、locator.uncheck()
    鼠标悬停 locator.hover()
    上传文件 locator.set_input_files("data/avatar.png")
    拖拽 locator.drag_to(另一个 locator)
    读文字、读输入框的值 locator.inner_text()、locator.input_value()
    后退、刷新 page.go_back()、page.reload()
    截图 page.screenshot(path="a.png", full_page=True)、locator.screenshot(path="b.png")

    把 8.5、8.6 两节的写法，连同下一节要讲的等待，放进一个完整的脚本里试一试。新建 scratch/ui_basics.py：

    # 第 8 章的定位、操作和等待示例：先登录，再在商品页、订单页上试
from playwright.sync_api import expect, sync_playwright

with sync_playwright() as p:
    # 这里不加 slow_mo：每步都慢半秒的话，数据早就加载完了，看不出等待和不等待的区别
    browser = p.chromium.launch(channel="chrome", headless=False)
    page = browser.new_page(base_url="http://127.0.0.1:8000")
    page.goto("/login.html")
    page.get_by_label("用户名").fill("alice")
    page.get_by_label("密码").fill("alice123")
    page.get_by_role("button", name="登录").click()
    expect(page.get_by_test_id("welcome")).to_have_text("欢迎，alice")

    # 等待：页面刚打开就数商品行数，和用 expect 等到之后再数
    page.goto("/products.html")
    print("刚打开时的行数：", page.get_by_test_id("product-row").count())
    expect(page.get_by_test_id("product-row")).to_have_count(10)
    print("expect 等到之后的行数：", page.get_by_test_id("product-row").count())

    # 缩小范围：先找到「无线鼠标」那一行，再找这一行里的购买按钮
    row = page.get_by_test_id("product-row").filter(has_text="无线鼠标")
    print("这一行的内容：", row.inner_text().replace("\t", " | "))
    print("这一行里购买按钮的个数：", row.get_by_role("button", name="购买").count())

    # 操作：在搜索框里按回车，和点「搜索」按钮效果一样
    page.get_by_label("关键词").fill("耳机")
    page.get_by_label("关键词").press("Enter")
    expect(page.get_by_test_id("product-row")).to_have_count(2)
    print("搜索「耳机」后的行数：", page.get_by_test_id("product-row").count())

    # 操作：订单页的下拉框
    page.goto("/orders.html")
    page.get_by_label("状态").select_option(label="已取消")
    print("下拉框现在的值：", page.get_by_label("状态").input_value())

    browser.close()

    browser.new_page(base_url=...) 设置了网站地址，之后 goto 里只写路径就行。运行：

    (.venv) > python scratch\ui_basics.py
刚打开时的行数： 0
expect 等到之后的行数： 10
这一行的内容： SKU0004 | 无线鼠标 | ¥89.00 | 100000 | 购买
这一行里购买按钮的个数： 1
搜索「耳机」后的行数： 2
下拉框现在的值： CANCELLED

    （库存那一列的数字会随着你下过的订单变化。）

    8.7 等待与断言（重点）¶

    8.7.1 页面是一点一点出来的¶

    打开商品页时，页面先显示「加载中…」，浏览器再去调商品接口，等接口返回后才把商品画出来。这中间有几十到几百毫秒的空档。脚本执行得比人快得多，如果在这个空档里去找商品，就找不到。

    上面脚本的前两行输出就是证据：同一个页面，刚打开时数到 0 行，用 expect 等过之后数到 10 行。因为 count() 是立刻数一下当前有几个，不会等；而 expect(...).to_have_count(10) 会反复检查，直到真的有 10 行，或者超过 5 秒判失败。

    8.7.2 Playwright 的自动等待¶

    • 操作会自动等：click()、fill() 这类操作执行前，Playwright 会等元素出现在页面上、可见、不再移动、可以操作、没有被别的东西挡住，满足了才动手，最多等 30 秒；
    • expect 断言会自动重试：条件不满足就隔一会儿再查，默认最多等 5 秒；
    • 立即返回、不等待的方法：count()、is_visible() 这类方法只看此刻的状态，马上给出结果；
    • 会等元素、但不等结果的方法：inner_text()、input_value() 会先等元素出现，可元素一出现就把当时的文字交给你，不会等文字变成你期望的样子。

    后两类拿来读数据没问题，拿来做断言就会时好时坏，断言一律交给 expect。

    常用的 expect 断言：

    断言 含义
    expect(locator).to_be_visible() / to_be_hidden() 可见 / 不可见（不存在也算不可见）
    expect(locator).to_have_text("...") 文字完全等于
    expect(locator).to_contain_text("...") 文字包含
    expect(locator).to_have_count(2) 匹配到的元素个数
    expect(locator).to_have_value("...") 输入框的值
    expect(locator).to_be_enabled() / to_be_disabled() 可用 / 禁用
    expect(locator).to_have_attribute("href", "/orders.html") 属性值
    expect(page).to_have_url(re.compile(r"/products\.html$")) 当前网址
    expect(page).to_have_title("商品列表 - 迷你商城") 网页标题
    expect(locator).not_to_be_visible() 前面加 not_ 就是反过来

    8.7.3 三种错误写法¶

    # 错误 1：固定等几秒。慢的时候 3 秒不够还是失败，快的时候白白多等
time.sleep(3)
assert page.get_by_text("下单成功").is_visible()

# 错误 2：用立即返回的方法做断言，页面没出来就判失败
assert page.get_by_test_id("product-row").count() == 10

# 错误 3：点完按钮马上断言跳转后的网址，页面还没跳过去
page.get_by_role("button", name="登录").click()
assert page.url.endswith("/products.html")

    对应的正确写法：

    expect(page.get_by_role("status")).to_contain_text("下单成功")
expect(page.get_by_test_id("product-row")).to_have_count(10)
expect(page).to_have_url(re.compile(r"/products\.html$"))

    记住一句话：UI 用例里不写 time.sleep，断言一律用 expect。

    8.7.4 断言失败时的样子¶

    下面这次故意把期望值写错，并且把超时设成了 2 秒（expect(...).to_have_text("余额：¥0.00", timeout=2000)）：

    E       AssertionError: Locator expected to have text '余额：¥0.00'
E       Actual value: 余额：¥99977.50
E       Call log:
E         - Expect "to_have_text" get_by_test_id("balance") with timeout 2000ms
E         - waiting for get_by_test_id("balance")
E           20 × locator resolved to <span id="balance" data-testid="balance">余额：¥99977.50</span>
E              - unexpected value "余额：¥99977.50"

    期望什么、实际是什么、在等待的 2 秒里检查了 20 次，都写得清清楚楚。

    8.7.5 超时时间¶

    • 单个断言等久一点：expect(locator).to_be_visible(timeout=10_000)，单位是毫秒；
    • 单个操作：locator.click(timeout=10_000)；
    • 整个页面的默认值：page.set_default_timeout(10_000)。

    超时不是越长越好。真出了问题，每条用例都要等满超时时间才失败，一轮跑下来会很慢。默认值够用就别改，确实慢的地方单独加长。

    8.8 写成 pytest 用例¶

    第 1 章装的 pytest-playwright 插件提供了一个现成的夹具 page：每条用例开始时自动打开一个干净的浏览器页面，结束后自动关掉。

    先在 pytest.ini 的 addopts 里加上 --browser-channel=chrome，让所有 UI 用例都用本机的 Chrome：

    addopts = -ra --browser-channel=chrome

    新建 tests/ui/test_login_ui.py：

    """登录页的 UI 用例（第一版）。"""
import re

from playwright.sync_api import Page, expect


def test_login_success(page: Page):
    page.goto("/login.html")
    page.get_by_label("用户名").fill("bob")
    page.get_by_label("密码").fill("bob123")
    page.get_by_role("button", name="登录").click()
    expect(page).to_have_url(re.compile(r"/products\.html$"))
    expect(page.get_by_test_id("welcome")).to_have_text("欢迎，bob")


def test_login_wrong_password(page: Page):
    page.goto("/login.html")
    page.get_by_label("用户名").fill("bob")
    page.get_by_label("密码").fill("wrong-password")
    page.get_by_role("button", name="登录").click()
    expect(page.get_by_role("alert")).to_have_text("用户名或密码错误")
    expect(page).to_have_url(re.compile(r"/login\.html$"))

    page.goto("/login.html") 只写了路径：第 4 章在 conftest.py 里写的 base_url 夹具，pytest-playwright 也会读，自动在前面补上网站地址。

    运行：

    (.venv) > pytest tests\ui -v
tests/ui/test_login_ui.py::test_login_success[chromium] PASSED           [ 50%]
tests/ui/test_login_ui.py::test_login_wrong_password[chromium] PASSED    [100%]

    用例名后面的 [chromium] 表示用的是 Chromium 系的浏览器。默认不显示浏览器窗口，想看着它跑：

    (.venv) > pytest tests\ui --headed --slowmo 500

    8.9 常见的坑¶

    现象 原因与解决
    Executable doesn't exist，提示运行 playwright install 没指定用本机的 Chrome，也没下载 Playwright 自带的浏览器。加 --browser-channel=chrome，或者执行 playwright install chromium
    strict mode violation 定位到了多个元素，用 filter 缩小范围
    Timeout 30000ms exceeded，等待某个元素 元素一直没出现：定位写错了、页面没跳到预期的地方、元素在别的分页里。用 --headed 看着跑一遍
    有时过有时不过 多半是用了 sleep、count()、is_visible() 做断言，换成 expect
    找不到明明看得见的元素 元素可能在 iframe（页面里嵌的另一个页面）里，要先用 page.frame_locator(...) 进去，第 10 章 10.7 节讲
    中文按钮名找不到 检查按钮文字里有没有空格、全角半角符号；name= 默认模糊匹配，可以只写一部分

    8.10 练习¶

    1. 用 codegen 录一段「登录 → 搜索键盘 → 购买 1 个」的操作，对照本章的写法整理成一条用例。
    2. 写一条用例：搜索「不存在的商品」，断言页面显示「没有找到相关商品」，并且一行商品都没有。
    3. 写一条用例：商品列表在第 1 页时「上一页」按钮是禁用的，点「下一页」后显示「第 2 页」。（提示：to_be_disabled()、to_contain_text()）
    4. 把 8.7.3 的三种错误写法各写一条用例跑跑看，体会为什么它们不可靠。
