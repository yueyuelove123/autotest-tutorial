    第 2 章 认识练习网站与 HTTP 基础¶

    本章目标

    • 在自己电脑上跑起练习网站，手工把业务走一遍；
    • 弄懂一次接口请求由哪几部分组成，能看懂状态码；
    • 会用浏览器开发者工具看页面发出的接口请求；
    • 会手工调接口，知道一个接口应该从哪几个方面去测。

    2.1 把练习网站放进工程¶

    学自动化需要一个被测系统。随便找个公网网站来练有几个问题：网站随时会改版或下线，你没法控制里面的数据，更不能拿去做性能测试（那等于攻击别人的网站）。所以本教程准备了一个小商城，在你自己电脑上运行，接口、UI、性能三块都对着它练。

    第一步：复制。 把参考代码里的 autotest-demo/shop 整个文件夹复制到你的工程根目录下（参考代码就是教程目录里的 autotest-demo/；看网站版的，在首页下载 autotest-demo.zip，解压后就是这个文件夹）：

    autotest-demo/
├─ .venv/
├─ shop/               ← 复制过来的练习网站
│  ├─ app.py
│  └─ static/
└─ requirements.txt

    练习网站是用 FastAPI 写的，第 1 章装依赖时已经一起装好了。你不需要看懂它的代码。

    第二步：启动。 在工程根目录、激活虚拟环境后执行：

    (.venv) > python -m uvicorn shop.app:app --port 8000
INFO:     Started server process [9780]
INFO:     Waiting for application startup.
INFO:     Application startup complete.
INFO:     Uvicorn running on http://127.0.0.1:8000 (Press CTRL+C to quit)

    看到最后一行就启动成功了。这个命令行窗口要一直开着，关掉窗口或按 Ctrl+C 网站就停了。后面跑测试时，再新开一个命令行窗口（记得进入工程目录、激活虚拟环境）。

    第三步：打开。 浏览器访问 http://127.0.0.1:8000，会自动跳到登录页。127.0.0.1 指你自己这台电脑，8000 是端口号，可以理解成这台电脑上的第 8000 号门。

    练习网站的账号：

    账号 密码 用途
    alice alice123 主账号，用例默认用它
    bob bob123 登录类用例专用，会被反复登录
    user001～user100 test123 账号池，并行执行和性能测试用

    每个账号初始余额 100000 元。商品一共 25 件，其中「限量版手办」只有 3 个库存，其余都是 100000 个。数据都放在内存里，停掉网站再启动就恢复成初始状态，练习时把数据弄乱了，重启一下就好。

    2.2 手工走一遍业务¶

    自动化测试是把手工测试的步骤交给程序去做，所以先自己手工走一遍：

    1. 用 alice 登录，进入商品列表，右上角显示「欢迎，alice」和余额；
    2. 搜索「耳机」，列表里剩下两款耳机；
    3. 搜索「中性笔」，点「购买」，在弹窗里把数量改成 2，点「确认下单」，底部出现「下单成功，订单号：SO……」；
    4. 点提示里的「去支付」进入我的订单，这一单状态是「待支付」，点「支付」，状态变成「已支付」，右上角余额减少 5 元；
    5. 再买一单，在订单页点「取消」，浏览器弹出确认框，点「确定」后状态变成「已取消」；
    6. 回到商品页看中性笔的库存：支付的那单扣掉了库存，取消的那单库存还回来了。

    后面几章就是把这些步骤和检查点写成自动运行的程序。

    2.3 HTTP 基础¶

    你在页面上点「登录」时，页面会给服务器发一条请求，服务器处理完回一条响应，页面再根据响应决定显示什么。这一来一回用的规则叫 HTTP 协议。页面背后的这些请求就是接口，接口测试就是绕过页面，直接给服务器发请求、检查响应。

    2.3.1 一次请求长什么样¶

    登录时浏览器发出的请求，原样写出来是这样的：

    POST /api/login HTTP/1.1
Host: 127.0.0.1:8000
Content-Type: application/json

{"username": "alice", "password": "alice123"}
    组成部分 这个例子里 说明
    请求方法 POST 常用的有 GET（查询）、POST（提交、新建）、PUT（修改）、DELETE（删除）
    地址 http://127.0.0.1:8000/api/login 协议://主机:端口/路径，后面还可以跟 ? 和查询参数
    请求头 Content-Type: application/json 一些附加信息，比如请求体是什么格式、登录凭证
    请求体 {"username": ...} 提交给服务器的数据，最常见的是 JSON 格式；GET 请求一般没有请求体

    地址里的查询参数长这样：/api/products?keyword=耳机&page=1&size=10，? 后面是参数，参数之间用 & 隔开。中文放进地址时会被编码，耳机 实际发出去是 %E8%80%B3%E6%9C%BA，后面在压测报告里还会见到它。

    2.3.2 一次响应长什么样¶

    HTTP/1.1 200 OK
content-type: application/json

{"code":0,"msg":"ok","data":{"token":"fc87585c716e220c05ec7371815622fb","username":"alice"}}

    第一行的 200 是状态码，告诉你这次请求处理得怎么样；后面是响应头和响应体。常见的状态码：

    状态码 含义 常见场景
    200 成功 最常见
    201 已创建 有些系统新建数据成功时返回
    301、302、307 跳转 访问首页被带到登录页
    400 请求有问题 参数格式不对
    401 没有登录 没带登录凭证，或者凭证失效了
    403 没有权限 登录了，但不允许做这件事
    404 找不到 地址写错了，或者数据不存在
    422 参数校验没过 必填项没填、数字超出范围
    429 请求太频繁 被限流了
    500 服务器内部错误 后端代码出了异常，基本可以判定是缺陷
    502、503、504 网关错误、服务不可用、网关超时 服务挂了、忙不过来或者处理太慢

    记个大概：2 开头是成功，3 开头是跳转，4 开头是请求方的问题，5 开头是服务器的问题。

    2.3.3 业务码：HTTP 200 不等于成功¶

    很多系统不管业务成功与否都返回 HTTP 200，再在响应体里用一个业务码区分结果。比如练习网站密码输错时：

    HTTP/1.1 200 OK

{"code":1001,"msg":"用户名或密码错误","data":null}

    HTTP 层面是成功的，业务层面是失败的。写接口用例时，状态码和业务码要一起检查，只看状态码会把大量失败当成成功。

    2.4 用浏览器开发者工具看接口¶

    页面调了哪些接口、传了什么、回了什么，用浏览器自带的开发者工具就能看到：

    1. 打开登录页，按 F12，切到 Network（网络） 面板；
    2. 勾上 Preserve log（保留日志），否则登录后页面一跳转，记录就被清掉了；
    3. 点筛选栏的 Fetch/XHR，只看接口请求，过滤掉图片、样式这些；
    4. 用 alice 登录，列表里会出现 login、products、me 几条请求。点 login：
    5. Headers（标头）：请求地址、请求方法、状态码、请求头和响应头；
    6. Payload（载荷）：请求体，能看到提交的用户名和密码；
    7. Response（响应）：服务器返回的内容；
    8. Timing（时间）：这次请求花了多少时间。
    9. 点 products 那条，看请求头里有一个 token，值就是登录时拿到的那一串。
    10. 切到 Application（应用）→ Cookies，能看到页面存下的 token 和 username 两个 cookie。

    在某条请求上点右键，选 Copy（复制），可以把这条请求复制成命令，贴到命令行里就能重新发一遍，排查问题时很好用。Windows 上要选对格式：Copy as PowerShell 贴进 PowerShell，Copy as cURL (cmd) 贴进 cmd 窗口。（Windows 自带的 PowerShell 里，curl 是另一个命令 Invoke-WebRequest 的别名，把 cURL 格式贴进去会报参数错误。）

    以后拿到一个新系统，第一件事就是打开开发者工具把业务点一遍，弄清楚每一步调了哪些接口。 接口文档不全、和实际对不上的时候，这里看到的才是真实情况。

    2.5 登录态：Cookie、Session 和 Token¶

    HTTP 本身不记事，服务器收到每一条请求都不知道是谁发的。所以登录之后，每次请求都要带上一个「我是谁」的凭证。常见做法有三种：

    • Cookie：服务器让浏览器存一小段数据，之后浏览器访问同一个网站时自动带上。
    • Session：用户信息存在服务器上，浏览器的 cookie 里只存一个编号（Session ID），服务器按编号去查。
    • Token：登录成功后服务器发一个字符串，客户端之后每次请求都放在请求头里带上。常见的请求头写法是 Authorization: Bearer xxx，也有系统自己起名字，比如 token: xxx。

    练习网站用的是 token：

    登录接口返回 token ──► 页面把 token 存进 cookie ──► 之后每次调接口，页面从 cookie 取出 token 放进请求头 token 里

    这件事对自动化很重要：

    • 接口自动化里，登录后要自己把 token 放进请求头；
    • UI 自动化里，可以先用接口登录拿到 token，再直接写进浏览器的 cookie，跳过登录页（第 11 章）；
    • 有的系统同一个账号只允许一处登录，新的登录会让旧 token 失效。练习网站用 SHOP_SINGLE_SESSION=1 启动就是这种模式，第 18 章会看到它对性能测试的影响。

    2.6 练习网站的接口¶

    浏览器打开 http://127.0.0.1:8000/docs 可以看到自动生成的接口文档。

    说明

    文档页的样式和脚本要从国外的公共资源站加载，网络不通时会白屏。这时可以直接看下面的表，或者打开 http://127.0.0.1:8000/openapi.json 看原始的接口描述。

    方法 地址 说明 要登录
    POST /api/login 登录，请求体 {"username", "password"}，返回 token 和用来续期的 refreshToken 否
    POST /api/logout 退出登录，当前 token 失效 是
    GET /api/me 当前用户名、昵称、邮箱、余额 是
    GET /api/products 搜索商品，参数 keyword、page（≥1）、size（1～50） 否
    GET /api/products/{id} 商品详情 否
    POST /api/orders 下单并占用库存，请求体 {"items": [{"productId": 13, "quantity": 2}]}，数量 1～999 是
    GET /api/orders 我的订单（最近 50 条），可选参数 status 是
    GET /api/orders/{orderNo} 订单详情 是
    POST /api/orders/{orderNo}/pay 支付订单，从余额扣款 是
    POST /api/orders/{orderNo}/cancel 取消待支付的订单，归还库存 是
    GET /api/health 健康检查，网站活着就返回 UP 否

    下面这些接口在第 5、6 章讲接口测试的常见场景时才用到，现在知道有它们就行：

    方法 地址 说明 要登录
    POST /api/token/refresh 用 refreshToken 换一对新的 token 否
    PUT /api/users/me 修改昵称（2～20 个字） 是
    POST / GET /api/users/avatar 上传头像（jpg 或 png，不超过 200 KB）/ 查看头像 是
    GET /api/orders/export 把我的订单导出成 CSV 文件 是
    POST / GET / PUT / DELETE /api/addresses、/api/addresses/{id} 收货地址的增、查、改、删 是
    GET /api/stats/orders 订单统计，给合作方用的开放接口，要带签名 否（要验签）
    POST /api/reports/stock 提交生成库存报表的任务，要过几秒才生成好 是
    GET /api/tasks/{taskId}、/api/tasks/{taskId}/download 查报表任务的状态 / 下载生成好的报表 是

    所有接口都返回同样的结构：

    {"code": 0, "msg": "ok", "data": {...}}
    code HTTP 状态码 含义
    0 200 成功
    40101 401 没登录，或者 token 不对
    40102 401 登录过期了（第 6 章讲 token 续期时用到）
    422 422 参数校验没过，data 里写了哪个字段、什么原因
    1001 200 用户名或密码错误
    1002 200 用户名和密码不能为空
    2001 200 商品不存在
    2002 200 库存不足
    3001 200 订单不存在（看别人的订单也是这个结果）
    3002 200 余额不足
    3003 200 订单状态不允许这个操作（比如已支付的订单再支付）

    头像、地址、开放接口、报表任务各自还有几个错误码（4001～4003、5001～5002、4011～4014、6001～6002），用到时在第 6 章细讲。

    可以看到这个系统两种做法都有：没登录和参数错误用 HTTP 状态码表示，其余业务错误统一返回 200、靠 code 区分。你以后遇到的真实系统也可能是任意一种，先看清楚再写断言。

    2.7 手工调接口¶

    写自动化之前，先手工调通接口，确认请求怎么发、响应长什么样。

    用接口文档页调（最方便）：

    1. 打开 http://127.0.0.1:8000/docs，展开 POST /api/login，点 Try it out；
    2. 把请求体改成 {"username": "alice", "password": "alice123"}，点 Execute；
    3. 下面的 Response body 里能看到 token，把它复制下来；
    4. 点页面右上角的 Authorize，把 token 贴进去，点 Authorize 再关掉弹窗；
    5. 展开 GET /api/me，Try it out → Execute，就能看到 alice 的余额了。不填 token 直接调，会得到 401。

    用接口调试工具调：Postman、Apifox 这类工具功能更全，能保存请求、管理环境、批量运行，工作中很常用。用法和上面类似：选方法、填地址、在 Body 里选 JSON 填请求体、在 Headers 里加 token。有兴趣可以装一个试试，本教程不依赖它们。

    2.8 一个接口要测哪些方面¶

    手工调通只是第一步。设计接口用例时，可以按下面这张清单逐项过一遍：

    方面 要测什么 练习网站上的例子
    正常功能 参数正确时返回成功，返回的数据正确 正确的账号密码能登录，返回的用户名对得上
    参数校验 必填项缺失、类型错误、空值、超长、边界值 不传密码、size=0、size=50、size=51、page=abc
    登录与权限 不带凭证、凭证错误或失效、访问别人的数据 不带 token 查余额、退出后再用旧 token、查别人的订单
    业务规则 系统规定不允许的情况都被拦住了 库存不足、余额不足、已支付的订单再支付或取消
    数据正确性 操作之后，相关的数据跟着正确变化 下单扣库存、支付扣余额、取消还库存
    重复与并发 同一个操作重复提交、多人同时操作 同一订单连续支付两次、同时支付十次（第 18 章）
    返回结构 字段齐全、类型正确，前端和其他系统依赖它 商品详情必须有 id、sku、name、price、stock
    性能 响应时间、能承受多大访问量 第 7、8 章

    设计参数校验用例时，有两个常用方法：

    • 等价类：把输入分成几类，每类挑一个代表。比如每页条数分成「1～50 之间」「小于 1」「大于 50」「不是数字」四类，每类测一个就够了；
    • 边界值：问题最容易出在边上。每页条数的边界是 1 和 50，就测 0、1、50、51 这几个值。

    拿登录接口举例，按这张清单能列出这些用例，下一章就把它们写成代码：

    编号 用例 预期
    1 正确的用户名和密码 HTTP 200，code 为 0，返回 token 和用户名
    2 密码错误 code 为 1001，提示用户名或密码错误
    3 账号不存在 code 为 1001，提示和密码错误一样（不暴露账号是否存在）
    4 用户名为空 code 为 1002
    5 密码为空 code 为 1002
    6 请求体里没有密码字段 HTTP 422，指出缺少 password
    7 不带 token 调需要登录的接口 HTTP 401
    8 退出登录后用旧 token 调接口 HTTP 401

    2.9 常见的坑¶

    现象 原因与解决
    启动时报 [Errno 10048] error while attempting to bind on address ('127.0.0.1', 8000) 8000 端口被占用了，多半是之前启动的网站还开着。关掉那个窗口，或者换个端口 --port 8001
    测试报错 Connection refused、Max retries exceeded 练习网站没启动，或者启动它的窗口被关了
    改了练习网站的启动参数没生效 要先 Ctrl+C 停掉再重新启动
    接口文档页白屏 加载不了国外的资源，看 2.6 节的表格
    No module named 'shop' 没在工程根目录执行启动命令，先 cd 到 autotest-demo

    2.10 练习¶

    1. 用开发者工具找到「下单」和「支付」两个请求，记下它们的方法、地址、请求体和响应体。
    2. 在接口文档页用 GET /api/products 查第 3 页、每页 10 条，看返回了几条、total 是多少，想想为什么。
    3. 试着调 POST /api/orders，买 4 个「限量版手办」，看返回什么。
    4. 照着 2.8 节的清单，给「支付订单」接口列一张用例表，至少 6 条。

    2.11 自检清单¶

    • 能启动练习网站，知道停掉它数据会恢复成初始状态；
    • 能说出一次请求由哪几部分组成，GET 和 POST 有什么区别；
    • 知道 401、404、422、500 分别是什么意思；
    • 明白为什么断言要同时检查 HTTP 状态码和业务码；
    • 会用开发者工具找到某个按钮背后调用的接口；
    • 能按清单从多个方面给一个接口设计用例。
