    第 11 章 UI 自动化进阶¶

    本章目标

    • 用好 pytest-playwright 的参数和夹具；
    • 用页面对象模式组织 UI 代码；
    • 用接口登录跳过登录页，用接口准备测试数据；
    • 会等待接口响应、拦截和伪造接口返回；
    • 会处理浏览器弹窗、新标签页、iframe、上传下载；
    • 会用操作录像（trace）排查失败，让失败截图进 Allure 报告；
    • 知道 UI 用例为什么时好时坏，以及怎么治。

    11.1 pytest-playwright 的参数和夹具¶

    11.1.1 命令行参数¶

    参数 作用
    --headed 显示浏览器窗口
    --slowmo 500 每个操作之间停 500 毫秒
    --browser chromium / firefox / webkit 换浏览器内核，可以写多次，一条用例在几个浏览器上各跑一遍
    --browser-channel chrome / msedge 用本机安装的 Chrome 或 Edge
    --device "iPhone 15" 模拟手机：屏幕尺寸、触屏、手机浏览器标识
    --base-url http://... 网站地址（本工程由 base_url 夹具提供，不用写）
    --screenshot only-on-failure 失败时截图，也可以是 on、off
    --video retain-on-failure 录屏，只留失败用例的
    --tracing retain-on-failure 记录操作录像，只留失败用例的（11.7 节详细讲）
    --output test-results 截图、录屏、操作录像放在哪，默认就是 test-results

    截图、录屏、操作录像都存在 test-results/ 下，每条用例一个文件夹。这个文件夹在每次运行开始时会被清空，要留存就在跑完后拷走。

    把常用的参数写进 pytest.ini：

    addopts = -ra --strict-markers --browser-channel=chrome --tracing=retain-on-failure --screenshot=only-on-failure

    这里顺便加了 --strict-markers：用了没在 markers 里登记的标记就直接报错，防止把标记名写错了还不知道，第 19 章 19.2 节细讲。

    11.1.2 夹具¶

    夹具 是什么
    page 一个新标签页，每条用例一个，用完自动关闭
    context page 所在的浏览器上下文，每条用例一个，用例之间的 cookie 互不影响
    browser 浏览器，整轮测试共用一个
    browser_context_args 创建上下文时的参数，覆盖它可以改窗口大小、语言、时区等

    想让所有用例都用 1440×900 的窗口、中文环境，在 conftest.py 里覆盖 browser_context_args：

    @pytest.fixture(scope="session")
def browser_context_args(browser_context_args):
    return {**browser_context_args, "viewport": {"width": 1440, "height": 900}, "locale": "zh-CN"}

    只想改某一条用例，用标记：

    @pytest.mark.browser_context_args(viewport={"width": 390, "height": 844})
def test_mobile_layout(page):
    ...

    11.2 页面对象模式¶

    11.2.1 遇到的问题¶

    第 8 章的两条登录用例里，「找到用户名框、填写、找到密码框、填写、点登录」写了两遍。用例多了以后，同一个按钮的定位写法会散落在几十个地方；开发改了一下按钮文字，你得一个个找出来改。

    11.2.2 页面对象¶

    页面对象模式（Page Object Model，简称 POM）的做法是：每个页面写一个类，页面上的元素和能做的操作都收在这个类里，用例只调用这些操作、做断言。和第 4 章接口客户端的思路一样，都是分层。

    新建 pages 文件夹（里面放一个空的 __init__.py），写三个页面对象。

    pages/login_page.py：

    """登录页的页面对象：页面上有什么元素、能做什么操作，都写在这里。"""
from playwright.sync_api import Page


class LoginPage:
    URL = "/login.html"

    def __init__(self, page: Page):
        self.page = page
        self.username = page.get_by_label("用户名")
        self.password = page.get_by_label("密码")
        self.submit = page.get_by_role("button", name="登录")
        self.error = page.get_by_role("alert")

    def open(self):
        self.page.goto(self.URL)
        return self

    def login(self, username: str, password: str):
        self.username.fill(username)
        self.password.fill(password)
        self.submit.click()

    pages/products_page.py：

    """商品列表页的页面对象。"""
from playwright.sync_api import Page


class ProductsPage:
    URL = "/products.html"

    def __init__(self, page: Page):
        self.page = page
        self.welcome = page.get_by_test_id("welcome")
        self.balance = page.get_by_test_id("balance")
        self.keyword = page.get_by_label("关键词")
        self.search_button = page.get_by_role("button", name="搜索")
        self.rows = page.get_by_test_id("product-row")
        self.state = page.locator("#state")
        self.dialog = page.get_by_role("dialog")
        self.toast = page.get_by_role("status")

    def open(self):
        self.page.goto(self.URL)
        return self

    def search(self, keyword: str):
        self.keyword.fill(keyword)
        self.search_button.click()

    def row(self, name: str):
        """名称里包含 name 的那一行商品。"""
        return self.rows.filter(has_text=name)

    def buy(self, name: str, quantity: int = 1):
        self.row(name).get_by_role("button", name="购买").click()
        self.dialog.get_by_label("数量").fill(str(quantity))
        self.dialog.get_by_role("button", name="确认下单").click()

    pages/orders_page.py：

    """我的订单页的页面对象。"""
from playwright.sync_api import Page


class OrdersPage:
    URL = "/orders.html"

    def __init__(self, page: Page):
        self.page = page
        self.balance = page.get_by_test_id("balance")
        self.status_filter = page.get_by_label("状态")
        self.rows = page.get_by_test_id("order-row")
        self.toast = page.get_by_role("status")

    def open(self):
        self.page.goto(self.URL)
        return self

    def filter_by_status(self, text: str):
        """按状态筛选，text 是下拉框里显示的文字，比如「已取消」。"""
        self.status_filter.select_option(label=text)

    def row(self, order_no: str):
        return self.rows.filter(has_text=order_no)

    def pay(self, order_no: str):
        self.row(order_no).get_by_role("button", name="支付").click()

    def cancel(self, order_no: str):
        # 取消前页面会弹出浏览器自带的确认框，先说好「出现了就点确定」，再去点按钮
        self.page.once("dialog", lambda dialog: dialog.accept())
        self.row(order_no).get_by_role("button", name="取消").click()

    在 __init__ 里写定位不会马上去页面上找元素。定位器是惰性的，每次对它做操作或断言时才去找，所以页面刷新、列表重新渲染之后照样能用。

    11.2.3 用页面对象重写用例¶

    tests/ui/test_login_ui.py：

    """登录页的 UI 用例。"""
import re

import allure
import pytest
from playwright.sync_api import expect

from pages.login_page import LoginPage
from pages.products_page import ProductsPage


@allure.feature("UI-登录")
@allure.title("输入正确的账号密码，登录后进入商品页")
@pytest.mark.smoke
def test_login_success(page, config):
    acc = config["accounts"]["login"]
    LoginPage(page).open().login(acc["username"], acc["password"])
    expect(page).to_have_url(re.compile(r"/products\.html$"))
    expect(ProductsPage(page).welcome).to_have_text(f"欢迎，{acc['username']}")


@allure.feature("UI-登录")
@allure.title("密码错误时提示「用户名或密码错误」，停留在登录页")
def test_login_wrong_password(page):
    login = LoginPage(page).open()
    login.login("bob", "wrong-password")
    expect(login.error).to_have_text("用户名或密码错误")
    expect(page).to_have_url(re.compile(r"/login\.html$"))


@allure.feature("UI-登录")
@allure.title("没登录时打开订单页，会被带回登录页")
def test_redirect_when_not_logged_in(page):
    page.goto("/orders.html")
    expect(page).to_have_url(re.compile(r"/login\.html$"))

    开发把登录按钮的文字改成「立即登录」，只需要改 LoginPage 里的一行。

    11.2.4 页面对象的几条约定¶

    • 方法按业务动作起名：login()、buy()、pay()，而不是 click_button_3()；
    • 页面对象里不写断言，断言留在用例里。同一个操作，不同用例要检查的东西不一样；
    • 一个页面一个类；页面上有独立的大组件（比如顶部导航栏、通用弹窗），可以单独拆成组件类；
    • 页面对象里不写测试数据，账号、商品名这些从参数传进来。

    11.3 登录态复用¶

    每条 UI 用例都从登录页开始，会带来两个问题：慢，每条用例多花一两秒；登录页一出问题，所有用例都失败，看报告完全不知道是哪里坏了。

    11.3.1 用接口登录，把 token 种进浏览器¶

    第 2 章讲过，练习网站登录后把 token 存在 cookie 里。那就先用接口登录拿到 token，直接写进浏览器的 cookie，跳过登录页。新建 tests/ui/conftest.py：

    """UI 用例专用的夹具和钩子。"""
import allure
import pytest


@pytest.fixture
def logged_in_page(page, api, base_url):
    """已登录的页面：把接口登录拿到的 token 种进浏览器，省掉每条用例都走一遍登录页。

    页面会同时检查 token 和 username 两个 cookie，少种一个就当成没登录、跳回登录页。
    """
    page.context.add_cookies([
        {"name": "token", "value": api.token, "url": base_url},
        {"name": "username", "value": api.username, "url": base_url},
    ])
    return page


@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_makereport(item, call):
    """用例失败时截一张整页图，挂进 Allure 报告。"""
    outcome = yield
    report = outcome.get_result()
    page = item.funcargs.get("page")
    if report.when == "call" and report.failed and page is not None:
        allure.attach(page.screenshot(full_page=True), name="失败截图", attachment_type=allure.attachment_type.PNG)

    （第二个函数是失败截图，11.8 节讲。）

    api 是第 4 章写的已登录接口客户端，浏览器和接口用的是同一个 token。需要登录的用例把参数 page 换成 logged_in_page 就行。

    坑

    只种 token 不够。 实测只种 token、不种 username，打开商品页会直接被带回登录页。真实系统也经常这样：页面脚本会同时检查好几个 cookie 或本地存储里的值。怎么知道要种哪些？ 先在浏览器里正常登录一次，打开开发者工具的 Application（应用）面板，把 Cookies 和 Local Storage 里登录后新出现的东西都记下来，一个不落地种上。

    坑

    有的系统同一账号只允许一处登录。 新的登录会让旧 token 失效。这种系统里，浏览器和接口一定要共用同一次登录拿到的 token，像上面这样；要是浏览器又走了一遍登录页，接口那边的 token 就作废了。

    11.3.2 另一种做法：保存登录状态文件¶

    登录过程很复杂（单点登录、要扫码、要手工过验证）时，可以登录一次，把浏览器的登录状态存成文件，之后直接加载：

    # 登录一次后保存（cookie 和本地存储都会存进去）
context.storage_state(path="auth.json")

# 之后创建上下文时加载
context = browser.new_context(storage_state="auth.json")

    pytest-playwright 里可以用 11.1.2 节的方法，在 browser_context_args 里加上 "storage_state": "auth.json"。

    auth.json 里是明文的登录凭证，不要上传到代码仓库，第 19 章会把它加进忽略清单。

    11.4 接口造数，页面操作，接口核对¶

    测订单页的「支付」按钮，需要先有一张待支付订单。在页面上从头买一单也能造出来，但这样做：慢；商品页出了问题，订单页的用例也跟着失败，报告里分不清到底是哪里坏了。

    更好的做法是三段式：

    1. 用接口准备数据：快、稳定，准备阶段失败了一眼就能看出来；
    2. 在页面上做被测的操作：这才是这条 UI 用例真正要测的；
    3. 页面断言加接口核对：页面显示对了，再用接口确认后台数据也对了。页面显示「已支付」不代表钱真的扣了。

    tests/ui/test_orders_ui.py：

    """订单页的 UI 用例：订单用接口造好，页面只验页面上的操作和展示。"""
import allure
import pytest
from playwright.sync_api import expect

from common.api_client import ok
from pages.orders_page import OrdersPage


@allure.feature("UI-订单")
@allure.title("在订单页支付待支付订单，状态变成已支付，余额减少")
@pytest.mark.smoke
def test_pay_in_page(logged_in_page, api, unpaid_order):
    order_no = unpaid_order["orderNo"]
    balance_before = ok(api.me())["balance"]
    orders = OrdersPage(logged_in_page).open()
    expect(orders.row(order_no)).to_contain_text("待支付")

    orders.pay(order_no)

    expect(orders.toast).to_contain_text(f"支付成功，订单号：{order_no}")
    expect(orders.row(order_no)).to_contain_text("已支付")
    expect(orders.row(order_no).get_by_role("button", name="支付")).to_have_count(0)
    expect(orders.balance).to_have_text(f"余额：¥{balance_before - unpaid_order['amount']:.2f}")
    assert ok(api.get_order(order_no))["status"] == "PAID"     # 再用接口核对后台数据


@allure.feature("UI-订单")
@allure.title("在订单页取消订单，确认弹窗后状态变成已取消")
def test_cancel_in_page(logged_in_page, api, unpaid_order):
    order_no = unpaid_order["orderNo"]
    orders = OrdersPage(logged_in_page).open()

    orders.cancel(order_no)

    expect(orders.row(order_no)).to_contain_text("已取消")
    assert ok(api.get_order(order_no))["status"] == "CANCELLED"


@allure.feature("UI-订单")
@allure.title("按状态筛选「已取消」，列表里只剩已取消的订单")
def test_filter_by_status(logged_in_page, api, product):
    order = ok(api.create_order([{"productId": product["id"], "quantity": 1}]))
    ok(api.cancel_order(order["orderNo"]))           # 用接口造一张已取消的订单
    orders = OrdersPage(logged_in_page).open()

    orders.filter_by_status("已取消")

    expect(orders.row(order["orderNo"])).to_be_visible()
    expect(orders.rows.filter(has_text="待支付")).to_have_count(0)
    expect(orders.rows.filter(has_text="已支付")).to_have_count(0)

    unpaid_order、product 都是第 4 章在 tests/conftest.py 里写的夹具，接口用例和 UI 用例共用。

    11.5 等待接口响应、拦截接口¶

    11.5.1 等某个接口的响应¶

    在页面上点「确认下单」后，想拿到新订单的订单号。页面提示里有，但从文字里抠不可靠；更好的办法是等下单接口的响应，从响应里拿：

    with page.expect_response(lambda r: r.url.endswith("/api/orders") and r.request.method == "POST") as info:
    products.buy(product["name"], quantity=2)
order_no = info.value.json()["data"]["orderNo"]

    with 块里的操作触发了请求，with 结束时会等到符合条件的响应回来，info.value 就是这个响应。这同时也验证了「点按钮确实调了下单接口」。

    11.5.2 拦截接口，伪造返回¶

    想测「商品接口出错时页面怎么提示」，总不能真去把后端弄坏。Playwright 可以拦截页面发出的请求，直接返回你给的结果：

    @allure.feature("UI-商品")
@allure.title("商品接口出错时，页面提示加载失败")
def test_load_error(logged_in_page):
    page = logged_in_page
    # 拦截商品接口，直接返回 500，模拟后端出故障（不用真的把服务弄坏）
    page.route("**/api/products*", lambda route: route.fulfill(status=500, body="Internal Server Error"))
    products = ProductsPage(page).open()
    expect(products.state).to_have_text("加载失败，请稍后重试")
    expect(products.rows).to_have_count(0)

    page.route(地址规则, 处理函数) 里，地址规则中 ** 匹配任意字符，* 匹配除 / 以外的任意字符。处理函数里常用的几种做法：

    写法 作用
    route.fulfill(status=500, body="...") 不发给服务器，直接返回指定结果
    route.fulfill(json={"code": 0, "data": {...}}) 返回伪造的 JSON，用来造特殊数据：超长商品名、库存为 0、空列表
    route.abort() 让请求失败，模拟断网
    route.continue_() 放行，可以顺便改请求头或请求体

    tests/ui/test_products_ui.py：

    """商品页的 UI 用例。"""
import allure
import pytest
from playwright.sync_api import expect

from common.api_client import ok
from pages.products_page import ProductsPage


@allure.feature("UI-商品")
@allure.title("搜索「耳机」，列表里只剩两款耳机")
def test_search(logged_in_page):
    products = ProductsPage(logged_in_page).open()
    products.search("耳机")
    expect(products.rows).to_have_count(2)        # 会自动等列表刷新，不用 sleep
    expect(products.rows.first).to_contain_text("耳机")


@allure.feature("UI-商品")
@allure.title("在页面上购买，提示下单成功，后台生成待支付订单")
@pytest.mark.smoke
def test_buy_from_page(logged_in_page, api, product):
    page = logged_in_page
    products = ProductsPage(page).open()
    products.search(product["name"])
    # 一边点按钮，一边等下单接口的响应，从响应里拿订单号
    with page.expect_response(lambda r: r.url.endswith("/api/orders") and r.request.method == "POST") as info:
        products.buy(product["name"], quantity=2)
    order_no = info.value.json()["data"]["orderNo"]
    try:
        expect(products.toast).to_contain_text(f"下单成功，订单号：{order_no}")
        expect(products.dialog).to_be_hidden()
        # 页面说成功不算数，再用接口核对后台数据
        order = ok(api.get_order(order_no))
        assert order["status"] == "UNPAID"
        assert order["items"][0]["quantity"] == 2
    finally:
        ok(api.cancel_order(order_no))            # 清理：取消订单，归还库存


@allure.feature("UI-商品")
@allure.title("购买数量填 0，弹窗里提示数量范围，不会下单")

    11.6 弹窗、新标签页、iframe、上传下载¶

    11.6.1 浏览器自带的弹窗¶

    alert、confirm、prompt 这三种是浏览器自带的弹窗，不属于页面元素，用定位器找不到。要提前告诉 Playwright「弹窗出现了怎么处理」：

    page.once("dialog", lambda dialog: dialog.accept())        # 点确定；dialog.dismiss() 是点取消
page.get_by_role("button", name="取消").click()             # 这一步会弹出确认框

    page.once 只处理下一个弹窗，page.on 处理之后所有的弹窗。还可以用 dialog.message 读弹窗里的文字。

    坑

    不处理弹窗不会报错，而是默默点了取消。 Playwright 的默认行为是自动关掉弹窗（相当于点取消）。实测订单页不注册处理函数直接点「取消」，用例不报错，订单却还是待支付。所以遇到「点了按钮没反应」，先想想是不是有个确认框被自动关掉了。

    页面自己画的弹窗（比如练习网站的购买弹窗）就是普通的页面元素，正常定位就行：page.get_by_role("dialog")。

    11.6.2 新标签页¶

    点链接打开了新标签页时，要等这个新页面出现，再在新页面上操作：

    page.goto("/lab.html")
with page.context.expect_page() as info:
    page.get_by_test_id("open-tab").click()          # 练习场上的「点我打开新标签页」
new_page = info.value
new_page.wait_for_load_state()
expect(new_page.get_by_test_id("from")).to_have_text("link")

    11.6.3 iframe¶

    页面里嵌套的另一个页面（常见于支付、富文本编辑器、第三方组件）叫 iframe。里面的元素不能直接定位，要先进入 iframe：

    frame = page.frame_locator("#inner")                # 用 CSS 找到练习场里的 iframe
expect(frame.get_by_test_id("from")).to_have_text("frame")

    11.7 调试¶

    UI 用例失败了，最难的是搞清楚「当时页面上到底是什么样」。几种手段：

    11.7.1 看着它跑¶

    (.venv) > pytest tests\ui\test_orders_ui.py --headed --slowmo 500

    11.7.2 单步调试¶

    (.venv) > $env:PWDEBUG = "1"
(.venv) > pytest tests\ui\test_orders_ui.py::test_pay_in_page

    会打开浏览器和 Playwright Inspector（调试器）窗口，可以一步步执行、看每一步定位到了哪个元素、在调试器里试写定位。在代码里写一行 page.pause()，跑到这里也会停下来打开调试器。调试完记得 Remove-Item Env:PWDEBUG 去掉这个环境变量。

    11.7.3 操作录像（trace）¶

    pytest.ini 里配了 --tracing=retain-on-failure，用例失败时 Playwright 会在 test-results/用例名/ 下留一个 trace.zip。打开它：

    (.venv) > playwright show-trace test-results\tests-ui-test-orders-ui-py-test-pay-in-page-chromium\trace.zip

    这是排查 UI 用例最有用的工具：

    • 左边是每一步操作的列表，点一步就能看到这一步前后页面的截图；
    • 能看到每一步的页面结构快照，可以在里面选元素、试定位；
    • 有这条用例期间所有的网络请求和响应，以及浏览器控制台的报错。

    不想装任何东西，也可以把 trace.zip 拖到 https://trace.playwright.dev 打开，文件只在你的浏览器里解析，不会上传。

    同一个文件夹里还有失败瞬间的截图 test-failed-1.png。

    11.8 失败截图进 Allure 报告¶

    test-results 里的截图只在本机，而且下次运行就清空了。把截图挂进 Allure 报告，别人看报告就能看到失败瞬间的页面。11.3.1 节 tests/ui/conftest.py 里的第二个函数就是干这个的：

    @pytest.hookimpl(hookwrapper=True)
def pytest_runtest_makereport(item, call):
    """用例失败时截一张整页图，挂进 Allure 报告。"""
    outcome = yield
    report = outcome.get_result()
    page = item.funcargs.get("page")
    if report.when == "call" and report.failed and page is not None:
        allure.attach(page.screenshot(full_page=True), name="失败截图", attachment_type=allure.attachment_type.PNG)

    这是一个钩子：pytest 在每条用例的每个阶段（准备、执行、清理）结束时都会调用它。yield 之后能拿到这个阶段的结果，如果是执行阶段（call）失败了，并且这条用例用到了浏览器页面，就截一张整页图挂进报告。用的是 logged_in_page 也没关系，它依赖 page，item.funcargs 里一样能取到。

    11.9 为什么 UI 用例时好时坏¶

    同一条用例，代码没改，有时通过有时失败，这种用例叫不稳定用例（英文 flaky）。它是 UI 自动化最大的敌人：大家会渐渐不再相信失败结果，真正的缺陷就被放过了。常见原因：

    原因 表现 怎么治
    时机 用了 sleep、count()、is_visible() 判断，页面慢一点就失败 一律用 expect，操作依赖 Playwright 的自动等待
    数据 依赖别的用例留下的数据，或者数据被别的用例改了 每条用例用接口自己造数据、自己清理
    共享账号 几条用例同时操作一个账号的余额、购物车 断言变化量；并行时每个进程用不同账号（第 19 章）
    提示自动消失 提示条几秒后消失，断言太晚就找不到了 断言紧跟在操作后面
    定位不唯一 按位置定位，列表顺序一变就点错 用文字、data-testid 精确定位
    环境 测试环境慢、偶尔超时、被别人重启 和开发、运维约定稳定的测试环境；监控环境的可用性
    动画 元素还在移动、还在渐显 Playwright 会等元素稳定；个别情况和开发约定测试时关掉动画

    还可以用 pytest-rerunfailures 插件让失败的用例自动重跑一次（pip install pytest-rerunfailures，运行时加 --reruns 1）。重跑只是兜底，不是解决办法：每一条靠重跑才通过的用例都要记下来、找到原因修好，否则真正的偶发缺陷也会被重跑掩盖。

    11.10 UI 用例写多少¶

    UI 用例不是越多越好。一个参考：

    • 每个核心页面的主流程各一两条（登录、搜索、下单、支付、取消）；
    • 页面特有的交互和提示（弹窗、禁用状态、错误提示）；
    • 接口层已经覆盖的业务规则，UI 层不再重复测。

    本工程的 UI 用例只有 10 条，接口用例有 27 条（第 8 章还会再加 1 条），这个比例是正常的。

    11.12 常见的坑¶

    现象 原因与解决
    种了 cookie 还是被带回登录页 页面还依赖别的 cookie 或本地存储，照 11.3.1 的方法找全
    点了按钮没反应，也不报错 有浏览器确认框被自动关掉了，提前用 page.once("dialog", ...) 处理
    test-results 里的截图不见了 每次运行开始会清空它，要留存就跑完后拷走，或者挂进 Allure 报告
    失败用例没有 trace.zip 没加 --tracing=retain-on-failure；通过的用例不保留
    page.route 没拦住请求 地址规则写错了，* 不匹配 /；不确定时先用 page.on("request", print) 把请求地址打印出来看
    找不到 iframe 里的元素 要先 frame_locator 进入 iframe
