    第 3 章 接口自动化基础¶

    本章目标

    • 用 requests 发出第一个接口请求；
    • 用 pytest 把请求写成用例，会运行、会看结果；
    • 会写有效的断言；
    • 会用夹具（fixture）做前置准备和清理；
    • 会用参数化和数据文件，一份代码跑多条用例。

    开始之前，确认练习网站在另一个命令行窗口里运行着（第 2 章 2.1 节）。

    3.1 第一个接口请求¶

    新建 scratch/first_request.py：

    # 第一个接口请求：登录，然后用拿到的 token 查自己的余额
import requests

BASE = "http://127.0.0.1:8000"

resp = requests.post(f"{BASE}/api/login", json={"username": "alice", "password": "alice123"}, timeout=10)
print("状态码：", resp.status_code)
print("响应体：", resp.json())

token = resp.json()["data"]["token"]
me = requests.get(f"{BASE}/api/me", headers={"token": token}, timeout=10)
print("我的信息：", me.json())

    运行：

    (.venv) > python scratch\first_request.py
状态码： 200
响应体： {'code': 0, 'msg': 'ok', 'data': {'token': '26fd77004104ff198b7674870f0667ca', 'username': 'alice'}}
我的信息： {'code': 0, 'msg': 'ok', 'data': {'username': 'alice', 'balance': 100000.0}}

    token 每次登录都不一样；如果你已经在页面上支付过订单，余额会比 100000 少。

    逐行看一下：

    写法 作用
    requests.post(地址, ...) / requests.get(地址, ...) 发 POST / GET 请求，其他方法有 put、delete
    json={...} 把字典转成 JSON 放进请求体，并自动加上请求头 Content-Type: application/json
    params={...} 查询参数，会拼到地址的 ? 后面，GET 请求常用
    headers={...} 请求头，这里用来带上 token
    timeout=10 最多等 10 秒，超时就报错。一定要写，不写的话服务器不回应，程序会一直卡着
    resp.status_code HTTP 状态码
    resp.json() 把响应体按 JSON 解析成字典
    resp.text 响应体的原始文字，响应不是 JSON 时用它看内容
    resp.elapsed.total_seconds() 这次请求花了多少秒

    坑

    json= 和 data= 不一样。 data={...} 发的是表单格式（username=alice&password=alice123），接口要的是 JSON 就会报参数错误。接口文档写的是 JSON，就用 json=。

    3.2 从脚本到用例：pytest 入门¶

    上面的脚本只是把结果打印出来，对不对还要人去看。自动化测试要做到：程序自己判断对错，最后告诉你几条通过、几条失败、失败在哪。 这就是测试框架 pytest 的工作。

    3.2.1 pytest 的规矩¶

    • 用例文件名以 test_ 开头，比如 test_login.py；
    • 用例是以 test_ 开头的函数；
    • 用 Python 自带的 assert 做检查，不用学额外的写法。

    3.2.2 第一个用例文件¶

    新建 tests/api/test_login.py，把第 2 章列的登录用例写两条进去：

    import requests

BASE = "http://127.0.0.1:8000"


def test_login_success():
    resp = requests.post(f"{BASE}/api/login", json={"username": "bob", "password": "bob123"}, timeout=10)
    assert resp.status_code == 200
    body = resp.json()
    assert body["code"] == 0
    assert body["data"]["username"] == "bob"
    assert len(body["data"]["token"]) == 32


def test_login_wrong_password():
    resp = requests.post(f"{BASE}/api/login", json={"username": "bob", "password": "wrong-password"}, timeout=10)
    assert resp.status_code == 200
    body = resp.json()
    assert body["code"] == 1001
    assert body["msg"] == "用户名或密码错误"

    登录类用例统一用 bob，不用 alice：后面 alice 会被别的用例拿来下单支付，把「登录」这种会被反复执行的动作放到专门的账号上，账号之间不会互相影响。

    运行：

    • plugins 那一行是装好的 pytest 插件，第 1 章装依赖时一起装上的，不用管。

    怎么读：

    • > 指向失败的那一行；
    • E 开头的行是原因：实际值是 '用户名或密码错误'，期望值是 '密码错误'；- 是期望的，+ 是实际的；

    看完记得改回来。每写完一条新用例，都故意把期望值改错跑一次，确认它真的会失败。 一条永远不会失败的用例没有任何价值，这个习惯能帮你发现写错的断言。

    3.2.4 常用的运行方式¶

    命令 作用
    pytest 运行当前目录下找得到的全部用例
    pytest tests\api 运行某个目录
    pytest tests\api\test_login.py::test_login_success 只运行某一条
    pytest -v 每条用例单独一行显示
    pytest -q 安静模式，只显示点和汇总
    pytest -s 显示用例里 print 的内容（默认会被吞掉）
    pytest -k wrong 只运行名字里包含 wrong 的用例（这里会选中 test_login_wrong_password）。3.5 节加上中文编号后，也可以写 -k 密码
    pytest -x 遇到第一条失败就停
    pytest --lf 只重跑上一次失败的用例

    3.2.5 配置文件 pytest.ini¶

    每次都要敲的参数可以写进工程根目录的 pytest.ini：

    [pytest]
# 只在 tests 目录里找用例
testpaths = tests
# -ra：最后汇总列出所有没通过的用例
addopts = -ra

    pytest.ini 所在的目录就是 pytest 认定的工程根目录（输出里的 rootdir）。之后在工程根目录直接敲 pytest 就行。

    3.3 断言要断什么¶

    断言写得好不好，决定了用例能不能真的发现问题。几条原则：

    1. 状态码和业务码都要断。 只断 status_code == 200，业务失败也会被当成成功。
    2. 断关键数据，别只断「有返回」。 assert body["data"] 只说明有数据，不说明数据对。要断具体的值：用户名是不是 bob、商品数量是不是 2、余额是不是少了订单金额。
    3. 每次都会变的值，断格式不断具体值。 token、订单号、时间每次都不一样，断它的长度、开头、格式即可，比如 len(token) == 32。
    4. 断言写上说明。 assert 条件, "说明"，失败时一眼就知道在检查什么。
    5. 小数用 pytest.approx 比较。 计算机算小数有误差，0.1 + 0.2 == 0.3 的结果是 False，金额比较写成 assert after == pytest.approx(before - amount)。

    常用的断言写法：

    assert body["code"] == 0                                  # 相等
assert body["code"] != 500                                # 不相等
assert "耳机" in product["name"]                           # 包含
assert len(items) == 2                                    # 数量
assert isinstance(product["price"], float)                # 类型
assert all("耳机" in p["name"] for p in items)             # 每一个都满足
assert body["data"] is None                               # 是 None
assert after == pytest.approx(before - 5)                 # 小数近似相等
assert order["status"] == "PAID", f"订单状态不对：{order}"   # 带说明

    3.4 夹具（fixture）：前置准备和清理¶

    3.4.1 遇到的问题¶

    再写几条需要登录的用例，你会发现每条用例开头都要先登录拿 token；测支付的用例还得先下一单，测完还要把订单处理掉。这些重复的准备和收尾工作，交给 pytest 的夹具（fixture）。

    3.4.2 写夹具¶

    新建 tests/conftest.py。这个文件名是固定的，pytest 会自动加载它，里面的夹具 tests 目录下的用例都能直接用，不需要 import：

    import pytest
import requests

BASE = "http://127.0.0.1:8000"


@pytest.fixture(scope="session")
def base_url():
    return BASE


@pytest.fixture(scope="session")
def token(base_url):
    """登录一次，整轮测试共用这个 token。"""
    resp = requests.post(f"{base_url}/api/login", json={"username": "alice", "password": "alice123"}, timeout=10)
    assert resp.json()["code"] == 0, "登录失败，后面的用例没法跑"
    return resp.json()["data"]["token"]


@pytest.fixture
def unpaid_order(base_url, token):
    """准备一张待支付订单，用例结束后取消掉。"""
    headers = {"token": token}
    resp = requests.post(f"{base_url}/api/orders", json={"items": [{"productId": 13, "quantity": 1}]},
                         headers=headers, timeout=10)
    order = resp.json()["data"]
    yield order        # 把订单交给用例；用例跑完后，接着执行下面的清理代码
    requests.post(f"{base_url}/api/orders/{order['orderNo']}/cancel", headers=headers, timeout=10)

    （13 号商品是中性笔，2.5 元，用它下单花钱最少。）

    3.4.3 用夹具¶

    新建 tests/api/test_order.py。用例函数的参数写夹具的名字，pytest 就会先执行夹具，把结果传进来：

    import pytest
import requests


def test_me(base_url, token):
    resp = requests.get(f"{base_url}/api/me", headers={"token": token}, timeout=10)
    assert resp.status_code == 200
    assert resp.json()["data"]["username"] == "alice"


def test_pay_order(base_url, token, unpaid_order):
    headers = {"token": token}
    before = requests.get(f"{base_url}/api/me", headers=headers, timeout=10).json()["data"]["balance"]

    resp = requests.post(f"{base_url}/api/orders/{unpaid_order['orderNo']}/pay", headers=headers, timeout=10)

    assert resp.json()["code"] == 0
    after = requests.get(f"{base_url}/api/me", headers=headers, timeout=10).json()["data"]["balance"]
    assert after == pytest.approx(before - unpaid_order["amount"])

    test_pay_order 读起来是三段：准备（记下支付前的余额）、操作（支付）、检查（余额少了订单金额）。这个结构叫 AAA（Arrange 准备、Act 操作、Assert 断言），用例写成这样最好读。

    3.4.4 夹具的要点¶

    • 依赖：夹具也可以用别的夹具，token 用了 base_url，unpaid_order 用了前两个。
    • yield 前后：yield 之前是准备，之后是清理。不管用例成功还是失败，清理代码都会执行。
    • 作用范围 scope：决定夹具多久执行一次。
    scope 执行时机 适合
    function（默认） 每条用例执行一次 每条用例都要一份新的数据，比如订单
    module 每个用例文件执行一次 一个文件里共用的数据
    session 整轮测试只执行一次 登录、读配置这类全局只要一份的东西

    用 --setup-show 可以看到夹具的执行顺序：

    (.venv) > pytest tests\api\test_order.py --setup-show
SETUP    S base_url
SETUP    S token (fixtures used: base_url)
        tests/api/test_order.py::test_me (fixtures used: base_url, token) .
        SETUP    F unpaid_order (fixtures used: base_url, token)
        tests/api/test_order.py::test_pay_order (fixtures used: base_url, token, unpaid_order) .
        TEARDOWN F unpaid_order
TEARDOWN S token
TEARDOWN S base_url

    （实际输出里还夹着几行 pytest-playwright 插件自带的夹具，这里省略了。）S 是 session，F 是 function：token 整轮只登录一次，unpaid_order 在需要它的用例前创建、用完马上清理。

    说明

    这一版的清理代码不检查结果：test_pay_order 把订单支付了，再取消会失败（已支付的订单不能取消），这里正好不在乎。第 4 章会写得更严谨：只有还没支付的订单才去取消。

    3.5 参数化：一份代码跑多条用例¶

    第 2 章列了四种登录失败的情况，写成四个函数的话代码几乎一样，只是用户名、密码和期望的业务码不同。这时用参数化：

    import pytest
import requests

BASE = "http://127.0.0.1:8000"


@pytest.mark.parametrize(
    "username, password, code",
    [
        ("bob", "wrong-password", 1001),
        ("nobody", "bob123", 1001),
        ("", "bob123", 1002),
        ("bob", "", 1002),
    ],
    ids=["密码错误", "账号不存在", "用户名为空", "密码为空"],
)
def test_login_fail(username, password, code):
    resp = requests.post(f"{BASE}/api/login", json={"username": username, "password": password}, timeout=10)
    assert resp.status_code == 200
    assert resp.json()["code"] == code

    parametrize 的第一个参数是参数名，第二个是一组组的数据，每一组生成一条用例；ids 给每条用例起个名字。存成 tests/api/test_login_fail.py 运行：

    tests/api/test_login_fail.py::test_login_fail[\u5bc6\u7801\u9519\u8bef] PASSED [ 25%]
tests/api/test_login_fail.py::test_login_fail[\u8d26\u53f7\u4e0d\u5b58\u5728] PASSED [ 50%]
...

    中文名字被转成了 \u 开头的编码，看不懂。在 pytest.ini 里加一行就能原样显示（选项名很长，照抄即可）：

    [pytest]
testpaths = tests
addopts = -ra
# 参数化用例的编号里有中文时原样显示
disable_test_id_escaping_and_forfeit_all_rights_to_community_support = true

    tests/api/test_login_fail.py::test_login_fail[密码错误] PASSED           [ 25%]

    3.6 数据驱动：把测试数据放进文件¶

    用例多了以后，测试数据和代码混在一起不好维护。把数据单独放进文件，代码只负责「读数据、发请求、做断言」，这种做法叫数据驱动。加一条用例只需要在数据文件里加几行，不懂代码的同事也能维护。

    3.6.1 YAML 格式¶

    数据文件常用 YAML，它比 JSON 好读好写。新建 data/login_cases.yaml：

    # 登录失败的几种情况：一条数据就是一条用例。加用例只改这里，不用动代码。
- title: 密码错误
  username: bob
  password: wrong-password
  code: 1001
  msg: 用户名或密码错误

- title: 账号不存在
  username: nobody
  password: bob123
  code: 1001
  msg: 用户名或密码错误

- title: 用户名为空
  username: ""
  password: bob123
  code: 1002
  msg: 用户名和密码不能为空

- title: 密码为空
  username: bob
  password: ""
  code: 1002
  msg: 用户名和密码不能为空

    YAML 的几条规矩：

    • - 开头表示列表里的一项，键: 值 表示字典（冒号后面要有一个空格）；
    • 用缩进表示层级，只能用空格，不能用 Tab；
    • 字符串一般不用加引号，空字符串要写成 ""；
    • # 后面是注释。

    读出来就是一个「字典组成的列表」，和第 1 章学的数据结构一模一样。

    3.6.2 读数据文件做参数化¶

    把 tests/api/test_login_fail.py 改成：

    from pathlib import Path

import pytest
import requests
import yaml

BASE = "http://127.0.0.1:8000"
# __file__ 是当前这个文件的路径。parents[0] 是它所在的 tests/api，parents[1] 是 tests，parents[2] 是工程根目录
DATA_FILE = Path(__file__).parents[2] / "data" / "login_cases.yaml"
CASES = yaml.safe_load(DATA_FILE.read_text(encoding="utf-8"))


@pytest.mark.parametrize("case", CASES, ids=[c["title"] for c in CASES])
def test_login_fail(case):
    resp = requests.post(
        f"{BASE}/api/login",
        json={"username": case["username"], "password": case["password"]},
        timeout=10,
    )
    assert resp.status_code == 200
    body = resp.json()
    assert body["code"] == case["code"]
    assert body["msg"] == case["msg"]

    为什么不直接写 open("data/login_cases.yaml")？相对路径是相对于「运行命令时所在的文件夹」的，在工程根目录运行没问题，换到 tests 目录里运行就找不到文件了。用 __file__ 从当前文件的位置去推算，在哪运行都对。

    3.6.3 什么时候用数据驱动¶

    • 适合：同一个接口、同样的检查逻辑、只是输入输出不同的一批用例，比如各种参数校验、各种登录失败；
    • 不适合：步骤不同、检查逻辑不同的用例。硬塞进一个数据文件，只会在代码里写满 if，比直接写几个函数还难懂。

    数据文件也可以用 JSON、CSV 或 Excel（读 Excel 用 openpyxl 库），道理都一样。

    3.8 常见的坑¶

    现象 原因与解决
    collected 0 items 文件名或函数名没以 test_ 开头，或者不在 testpaths 指定的目录里
    单独跑某条用例就失败，一起跑就通过 用例之间有依赖，比如 B 用了 A 创建的数据。每条用例的数据都要自己准备，用夹具
    程序卡住不动 请求没写 timeout，服务器又一直不回应
    接口返回 422 参数错误，但参数看着没问题 把 json= 写成了 data=
    换个环境用例全挂 把 token、订单号、商品编号写死在代码里了。token 用夹具现取，数据现造
    金额断言偶尔失败，差 0.0000001 小数用 pytest.approx 比较
    import file mismatch 不同目录下有同名的用例文件（比如两个 test_login.py），改成不同的名字
    用例里 print 的内容看不到 加 -s 参数
    fixture 'xxx' not found 夹具名拼错了，或者 conftest.py 放的位置不对（要放在用例所在目录或它的上级目录）

    3.9 练习¶

    1. 在 test_login.py 里加一条用例：登录后调 /api/logout，再用旧 token 调 /api/me，断言返回 401。
    2. 用参数化写「搜索参数非法」的用例：page=0、size=0、size=51、page=abc 都应该返回 HTTP 422。
    3. 写一个夹具 paid_order：下单并支付，把订单交给用例。用它写一条用例：已支付的订单再支付，返回业务码 3003。
    4. 搜索「耳机」，断言返回 2 个商品，并且每个商品名称都包含「耳机」。

    3.10 自检清单¶

    • 知道 json=、params=、headers=、timeout= 各自的作用；
    • 能看懂 pytest 失败时的输出，找到是哪一行、期望值和实际值分别是什么；
    • 会用 -v、-s、-k、--lf 这几个参数；
    • 能说出夹具的 scope 有哪几种，yield 后面的代码什么时候执行；
    • 会用 parametrize 和 YAML 数据文件写一组用例；
    • 每条新用例都故意改错跑过一次，确认它会失败。
