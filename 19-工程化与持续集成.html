    第 19 章 工程化与持续集成¶

    本章目标

    • 用标记给用例分组，按需要跑不同的一批；
    • 并行执行用例，处理好并行带来的数据冲突；
    • 用 Git 管理测试代码；
    • 接入流水线：推代码、每天定时自动跑，结果自动通知到群里；
    • 知道 LoadRunner 的压测怎样接进流水线；
    • 知道怎样让自动化长期发挥作用，以及接下来学什么。

    19.1 回顾：最终的工程¶

    autotest-demo/
├─ shop/                 练习网站（被测系统）
├─ scratch/              入门练手的脚本
├─ common/               基础层与业务层：接口客户端、读配置
├─ config/               配置层：各环境的地址和账号
├─ data/                 测试数据
├─ pages/                UI 的页面对象
├─ tests/
│  ├─ conftest.py        全局夹具
│  ├─ api/               接口用例
│  ├─ adv/               pytest 进阶的演示用例（第 7 章）
│  ├─ ui/                UI 用例
│  └─ selenium/          Selenium 版的 UI 用例（第 12 章）
├─ lr/                   LoadRunner 脚本（第 15、18 章）
├─ perf/                 Locust 写的日常冒烟压测（19.5.2）
├─ tools/                小工具：结果通知、生成测试图片、汇总 LoadRunner 结果、记录进程内存、运行压测
├─ .github/workflows/    流水线配置
├─ allurerc.yaml         报告配置
├─ pytest.ini            pytest 配置
├─ requirements.txt      依赖清单
└─ .gitignore            不上传的文件

    贯穿全书的几条原则，在这里再说一遍：

    • 分层：用例只写业务步骤和断言；怎么发请求、怎么操作页面、连哪个环境，各有各的地方；
    • 数据自己造、自己清，用例之间互不依赖；
    • 断言要能真正发现问题：状态码和业务码都断，断变化量，每条用例故意改错跑一次；
    • 不写死：地址、账号、口令都不写在代码里。

    19.2 用标记给用例分组¶

    19.2.1 打标记¶

    前面的用例上已经有 @pytest.mark.smoke、@pytest.mark.concurrency 这样的标记。标记要先在 pytest.ini 里登记：

    markers =
    smoke: 冒烟用例，每次改动后最先跑的那一小批
    concurrency: 并发类用例

    addopts 里的 --strict-markers 会让没登记的标记直接报错：把 smoke 手误写成 smok，如果不报错，这条用例就悄悄地不在冒烟用例里了。

    19.2.2 按标记运行¶

    (.venv) > pytest -m smoke -v
collecting ... collected 160 items / 152 deselected / 8 selected
tests/api/test_design_combo.py::test_same_product_lines_merge PASSED     [ 12%]
tests/api/test_design_status.py::test_unpaid_to_paid PASSED              [ 25%]
tests/api/test_login.py::test_login_success PASSED                       [ 37%]
tests/api/test_order_flow.py::test_purchase_flow PASSED                  [ 50%]
tests/api/test_products.py::test_search_by_keyword PASSED                [ 62%]
tests/ui/test_login_ui.py::test_login_success[chromium] PASSED           [ 75%]
tests/ui/test_orders_ui.py::test_pay_in_page[chromium] PASSED            [ 87%]
tests/ui/test_products_ui.py::test_buy_from_page[chromium] PASSED        [100%]
====================== 8 passed, 152 deselected in 5.16s ======================

上面是学完全部章节、参考代码里的数字（共 160 条用例）。你自己的工程里条数不一样很正常，看被选中的是不是冒烟用例就行。
    命令 跑哪些
    pytest -m smoke 只跑冒烟用例
    pytest -m "not concurrency" 除了并发用例都跑
    pytest -m "smoke and not concurrency" 冒烟用例里去掉并发的
    pytest tests\api 按目录：只跑接口用例

    常见的分法：冒烟用例几分钟内跑完，每次提交代码都跑；全量回归每天跑一次；并发、稳定性这类又慢又重的放在晚上跑。

    19.3 并行执行¶

    19.3.1 开启并行¶

    用例多了一轮要跑很久，可以用 pytest-xdist 插件开多个进程同时跑：

    (.venv) > pytest -n 4

    -n 4 开 4 个进程，-n auto 按 CPU 核数开。每个进程叫一个 worker，编号是 gw0、gw1、gw2、gw3，用例会被分配到这几个进程里同时执行。

    19.3.2 并行带来的数据冲突¶

    串行能过的用例，并行时可能失败。 原因都是同一个：几个进程同时动了同一份数据。

    冲突一：共享账号的余额。 4 个进程都用 alice，进程 A 刚记下支付前的余额，进程 B 就支付了一单，A 再查余额时少了两单的钱，「余额少了订单金额」的断言就失败了。解决办法是每个进程用账号池里不同的账号，修改 tests/conftest.py 里的 account 夹具：

    @pytest.fixture(scope="session")
def worker_index(worker_id):
    """当前进程的编号。worker_id 由 pytest-xdist 提供：不并行时是 master，并行时是 gw0、gw1……"""
    return 0 if worker_id == "master" else int(worker_id.removeprefix("gw"))


@pytest.fixture(scope="session")
def account(config, worker_id, worker_index):
    """本进程用的账号。

    一个进程跑全部用例时用主账号；并行执行（pytest -n 4）时每个进程各用账号池里的一个，
    免得几个进程同时改同一个账号的余额，让余额断言互相干扰。
    """
    if worker_id == "master":
        return config["accounts"]["main"]
    pool = config["accounts"]["pool"]
    return {"username": f"{pool['prefix']}{worker_index + 1:03d}", "password": pool["password"]}

    worker_id 是 pytest-xdist 提供的夹具。gw0 用 user001，gw1 用 user002，以此类推。

    冲突二：共享商品的库存。 账号分开以后再跑，编写本教程时实测还是失败了一条：

    FAILED tests/api/test_order_flow.py::test_purchase_flow - assert 99932 == (99...

    这条用例断言「下单 3 件后库存少了 3」。可是库存是所有用户共享的，别的进程也在买中性笔、取消中性笔的订单，库存的变化就不止 3 了。解决办法同样是数据隔离：每个进程用不同的商品。修改 product 夹具：

    # 便宜、库存充足的商品。并行执行时每个进程用不同的一件：库存是所有用户共享的，
# 几个进程同时买同一件商品，「库存少了 3 件」这种断言就会互相干扰
CHEAP_PRODUCTS = ["中性笔", "笔记本", "毛巾", "收纳盒", "跳绳", "马克杯", "运动水壶", "USB-C 数据线"]


@pytest.fixture
def product(api, worker_index):
    """下单类用例用的商品。"""
    name = CHEAP_PRODUCTS[worker_index % len(CHEAP_PRODUCTS)]
    items = ok(api.search_products(keyword=name))["items"]
    assert items, f"练习网站里应该有「{name}」这个商品"
    return items[0]

    test_purchase_flow 和 UI 用例 test_buy_from_page 在第 4、11 章里已经是通过 product 夹具拿商品的，没有写死商品名，所以只改夹具就够了，用例不用动。改完连跑 3 次 pytest -n 4，全部通过。

    只隔离断言库存的用例还不够。后来又遇到一次失败，是取消订单那条用例：库存比下单前多了 2 件。原因是另一条用例「一单买两种商品」写死了中性笔：它自己不断言库存，可它下单、取消的那一刻，正好夹在 0 号进程读库存的两次之间。参考代码已经把它换成了保温杯和雨伞，这两件不在上面的商品表里。所以你自己写的用例里，只要写死了表里的商品下单，不管断言不断言库存，都要改成用 product 夹具，或者换成表外的商品。

    这个教训值得记住：并行之前，先把每条用例碰到的共享数据列出来：账号、余额、库存、优惠券、配置项、全局开关……能按进程隔离的就隔离。实在没法隔离的（比如整个系统只有一个全局配置），可以让碰它的用例在同一个进程里按顺序跑：给这些用例打上 @pytest.mark.xdist_group(name="全局配置")，运行时加 --dist loadgroup。

    冲突三：Selenium 用例。 编写本教程时，把第 12 章的 3 条 Selenium 用例和其他用例一起 pytest -n 4，大约每四五轮就有一轮失败一条：搜索用例等不到结果，现场记录下来是输入框里没打进字、或者点了搜索却没发出请求。串行单独跑它们三轮全过；只把它们放进同一个进程（上面的 xdist_group）也还偶尔失败。根本原因没有查到，处理办法是把它们和其他用例分开跑：

    (.venv) > pytest -n 4 --ignore=tests\selenium
(.venv) > pytest tests\selenium

    --ignore 让 pytest 不去收集这个目录。这也是一个很实际的经验：并行之前，先确认每一类用例在并行下都稳定，不稳定的那一类单独串行跑，比为了它放弃整个并行划算。

    19.3.3 并行能省多少时间¶

    实测参考代码里除 Selenium 外的 157 条用例：串行约 40 秒，4 个进程并行约 19 秒，省了一半多。每个进程启动 Python、打开浏览器本身要几秒，用例很少的时候这部分开销占大头，并行省不了多少；用例越多、单条越慢（比如几百条 UI 用例），并行的收益越明显。

    19.4 用 Git 管理代码¶

    测试代码和开发的代码一样，要放进代码仓库：能看到每次改了什么、能回退、能多人协作、流水线能拉取。

    19.4.1 不上传哪些文件¶

    在工程根目录建 .gitignore，列出不进仓库的文件：

    # 虚拟环境和 Python 运行时生成的缓存
.venv/
__pycache__/
.pytest_cache/

# 运行产物：报告、截图、操作录像，每次运行都会重新生成
reports/
test-results/
first_ui.png

# 带真实地址和账号的环境配置、浏览器登录状态文件，不上传
config/*.yaml
!config/local.yaml
auth.json

# LoadRunner 脚本回放、编译时生成的文件，每次回放都会重新生成
lr/*/result1/
lr/*/data/
lr/*/*.idx
lr/*/*.ci
lr/*/*.bak
lr/*/*.pickle
lr/*/pre_cci.c
lr/*/combined_*.c
lr/*/output.txt
lr/*/logfile.log
lr/*/options.txt
lr/*/mdrv*
lr/*/ReplaySummaryReport.xml
lr/*/CompilerLogMetadata.xml

    config/*.yaml 表示 config 目录下所有 yaml 文件都不上传，!config/local.yaml 把本机练习网站的配置排除在外（它里面只有练习账号）。lr/*/ 开头的几行是 VuGen 回放脚本时在脚本目录里生成的日志、编译中间文件和备份，* 匹配任意一个脚本目录；脚本本身（.usr、.c、.prm、.dat、运行时设置等）照常上传。

    19.4.2 基本操作¶

    先到 https://git-scm.com/ 下载安装 Git（安装选项保持默认即可；在 VS Code 里用终端的，装完要把 VS Code 整个关掉重开）。第一次用 Git，先告诉它你是谁，提交记录里会写上这个名字和邮箱，只需要设置一次：

    > git config --global user.name "你的名字"
> git config --global user.email "你的邮箱"

    然后在工程根目录：

    > git init                                   # 把这个文件夹变成 Git 仓库（只需一次）
> git add .                                  # 把改动加入暂存区（.gitignore 里列的会被跳过）
> git status                                 # 看看要提交哪些文件，确认没有口令、没有报告
> git commit -m "接口用例：补充余额不足的场景"      # 提交，说明写清楚这次改了什么

    不设置名字和邮箱的话，git commit 会报 Author identity unknown。

    放到远程仓库（GitHub、GitLab、Gitee 或公司自己的代码平台，先在网页上建一个空仓库）：

    > git branch -M main                         # 把当前分支改名为 main
> git remote add origin 远程仓库的地址
> git push -u origin main

    git init 建出来的分支默认叫 master，现在的代码平台一般用 main 作主分支，所以先改个名，否则推送时会报 src refspec main does not match any。

    之后每次改完：git add .、git commit -m "说明"、git push。

    提交前一定看一眼 git status。 口令一旦推到远程仓库，即使后来删了，历史记录里也还在，只能去改口令。

    19.5 持续集成¶

    19.5.1 是什么¶

    持续集成（CI）的意思是：每次有人推代码，自动拉取代码、自动跑测试，几分钟后就知道这次改动有没有把东西弄坏。一串自动执行的步骤叫流水线，常用的工具有 GitHub Actions、GitLab CI、Jenkins。

    流水线判断一步成功还是失败，看的就是退出码：pytest 有用例失败时退出码不是 0，流水线据此把这一步标红。性能测试接进流水线时同理，判定不达标就让命令返回非 0 的退出码。

    19.5.2 GitHub Actions¶

    在工程里建 .github/workflows/autotest.yml，推到 GitHub 上就会自动生效：

    # GitHub Actions 流水线示例：推代码、提合并请求、每天定时，自动跑接口和 UI 用例、日常压测，并保存报告。
# 这份文件没有在真实的流水线上跑过，用之前按你们的实际情况检查和调整。
name: autotest

on:
  push:
  pull_request:
  schedule:
    - cron: "0 1 * * *"       # 每天 UTC 1 点，也就是北京时间 9 点
  workflow_dispatch:           # 允许在网页上手动点击运行

jobs:
  test:
    runs-on: ubuntu-latest     # GitHub 提供的 Ubuntu 运行环境自带 Chrome 和 Node.js
    steps:
      - uses: actions/checkout@v7

      - uses: actions/setup-python@v7
        with:
          python-version: "3.13"

      - name: 安装依赖
        run: pip install -r requirements.txt

      - name: 启动练习网站
        run: |
          nohup python -m uvicorn shop.app:app --port 8000 --no-access-log > shop.log 2>&1 &
          for i in $(seq 1 30); do curl -sf http://127.0.0.1:8000/api/health && break; sleep 1; done

      - name: 接口和 UI 用例
        # token 续期用例要在特殊模式的网站上跑，Selenium 用例并行时不稳定（19.3.2），这一步先排除
        run: pytest -n 4 -m "not token_ttl" --ignore=tests/selenium --alluredir=reports/allure-results --junitxml=reports/junit.xml

      - name: Selenium 用例
        run: pytest tests/selenium --alluredir=reports/allure-results

      - name: 日常压测
        run: locust -f perf/locustfile.py --headless -u 50 -r 10 -t 1m --host http://127.0.0.1:8000 --html reports/perf/daily.html

      - name: 生成 Allure 报告
        if: always()           # 前面失败了也要生成报告，失败的时候才最需要看报告
        run: npx -y allure@3 generate reports/allure-results

      - name: 发送结果通知
        if: always()
        env:
          WECOM_WEBHOOK: ${{ secrets.WECOM_WEBHOOK }}   # 群机器人地址存在仓库的 Secrets 里，不写进文件
        run: python tools/notify.py reports/junit.xml

      - name: 保存报告
        if: always()
        uses: actions/upload-artifact@v7
        with:
          name: reports
          path: |
            reports/
            test-results/

    要点：

    • on 定义什么时候触发：推代码、提合并请求、定时（cron 用的是 UTC 时间，北京时间要减 8 小时）、手动；
    • 流水线运行在 Linux 上，命令是 Linux 的写法；
    • 启动练习网站那一步：后台启动，再每秒探测一次健康检查接口，最多等 30 秒。真实项目里被测系统一般已经部署在测试环境了，这一步换成「设置 TEST_ENV 和口令」即可；
    • if: always()：前面的步骤失败了也继续执行，保证报告和通知一定有；
    • 口令、群机器人地址这类敏感信息存在仓库设置的 Secrets 里，用 ${{ secrets.名字 }} 引用，不写进文件；
    • 日常压测那一步用的是 Locust：一个用 Python 写压测脚本的开源工具（第 13 章 13.5.3 节、第 18 章 18.8 节）。流水线的机器是临时创建的 Linux 机器，LoadRunner 是 Windows 程序，还要按虚拟用户数授权，放不进来；Locust 用 pip 一装就能跑。参考代码的 perf/locustfile.py 是一个混合场景，50 个用户跑 1 分钟，P95 超过目标或失败率超过 1% 时退出码为 1，作用相当于每天一次的冒烟压测，提早发现性能明显变差。完整的压测仍然在压测机上用 LoadRunner 做（19.5.4 节）；
    • 跑完在这次运行的页面上可以下载 reports 压缩包，里面有 Allure 报告、压测报告、失败用例的操作录像。

    19.5.3 Jenkins¶

    国内公司用 Jenkins 的很多。流水线写在工程根目录的 Jenkinsfile 里，结构和上面类似（Linux 执行机的写法，同样只演示结构，没有在真实的 Jenkins 上跑过）：

    pipeline {
    agent any
    triggers { cron('H 9 * * *') }                     // 每天 9 点左右定时跑
    stages {
        stage('准备环境') {
            steps { sh 'python3 -m venv .venv && .venv/bin/pip install -r requirements.txt' }
        }
        stage('启动练习网站') {
            steps {
                // Jenkins 会在一个 sh 步骤结束时清理它启动的后台进程，加上 JENKINS_NODE_COOKIE=dontKillMe 才能留到后面的阶段
                sh 'JENKINS_NODE_COOKIE=dontKillMe nohup .venv/bin/python -m uvicorn shop.app:app --port 8000 --no-access-log > shop.log 2>&1 &'
                sh 'for i in $(seq 1 30); do curl -sf http://127.0.0.1:8000/api/health && break; sleep 1; done'
            }
        }
        stage('接口和 UI 用例') {
            steps { sh '.venv/bin/pytest -n 4 -m "not token_ttl" --ignore=tests/selenium --alluredir=reports/allure-results --junitxml=reports/junit.xml' }
        }
        stage('日常压测') {
            steps { sh '.venv/bin/locust -f perf/locustfile.py --headless -u 50 -r 10 -t 1m --host http://127.0.0.1:8000 --html reports/perf/daily.html' }
        }
    }
    post {
        always {
            junit 'reports/junit.xml'                   // Jenkins 自带的用例结果展示
            archiveArtifacts artifacts: 'reports/**, test-results/**', allowEmptyArchive: true
            sh 'pkill -f "uvicorn shop.app:app" || true'  // 跑完把练习网站停掉，免得一直占着端口
        }
    }
}

    --junitxml 生成的 junit.xml 是一种通用的结果格式，Jenkins、GitLab 等工具都能直接读，在页面上展示每条用例的结果和历史趋势。

    19.5.4 LoadRunner 压测接进流水线¶

    LoadRunner 的压测一般在专门的压测机上做：一台装好 LoadRunner 的 Windows 电脑，作为 Jenkins 的一个执行节点（GitHub Actions 里叫自托管的运行器）。流水线要做的事，就是在这台机器上用命令行运行场景、检查结果、按检查结果给出退出码。

    第 16 章 16.12 节说过，Wlrun.exe 的退出码说明不了业务结果；第 17 章 17.10 节的 lr_summary.py 加 --check 能按事务失败和 SLA 给出退出码。参考代码的 tools/run_lr.ps1 把这两步接在一起：

    param(
    [Parameter(Mandatory = $true)][string]$Scenario,     # 场景文件（.lrs）的完整路径
    [Parameter(Mandatory = $true)][string]$ResultRoot,   # 结果放在哪个文件夹下
    [int]$TimeoutMinutes = 60                            # 场景最多跑多久，超时就结束 Controller
)

if (-not $env:LR_PATH) {
    Write-Host "找不到环境变量 LR_PATH，这台机器上没有装 LoadRunner，或者装完没有重开命令行窗口"
    exit 2
}

# 每次用一个新的结果目录：-ResultName 指向已有的目录时会被直接覆盖
$name = [IO.Path]::GetFileNameWithoutExtension($Scenario) + "_" + (Get-Date -Format "yyyyMMdd_HHmmss")
$result = Join-Path $ResultRoot $name
Write-Host "运行场景 $Scenario，结果放在 $result"

$wlrun = Join-Path $env:LR_PATH "bin\Wlrun.exe"
$p = Start-Process $wlrun -ArgumentList "-TestPath", $Scenario, "-ResultName", $result, "-Run" -PassThru
if (-not $p.WaitForExit($TimeoutMinutes * 60 * 1000)) {
    Stop-Process -Id $p.Id -Force
    Write-Host "超过 $TimeoutMinutes 分钟还没有结束，已经强制结束 Controller"
    exit 2
}

# Wlrun.exe 的退出码不反映事务结果（第 16 章 16.12 节），这里只看结果文件有没有生成
if (-not (Get-ChildItem $result -Filter *.lrr -ErrorAction SilentlyContinue)) {
    Write-Host "结果目录里没有 .lrr 文件，场景没有正常跑完"
    exit 2
}

# 优先用工程里虚拟环境的 Python
$python = if (Test-Path ".venv\Scripts\python.exe") { ".venv\Scripts\python.exe" } else { "python" }
& $python tools/lr_summary.py $result --check
exit $LASTEXITCODE

    退出码 0 表示没有失败的事务、SLA 全部达标，1 表示检查不通过，2 表示场景没有正常跑完。先在本机试一下，在工程根目录执行：

    > powershell -NoProfile -ExecutionPolicy Bypass -File tools\run_lr.ps1 -Scenario D:\work\autotest-demo\lr\scenarios\demo16.lrs -ResultRoot D:\work\lr-results
运行场景 D:\work\autotest-demo\lr\scenarios\demo16.lrs，结果放在 D:\work\lr-results\demo16_20261024_124724
结果 demo16_20261024_124724，场景持续 228 秒，统计全程
HTTP 状态码：200 共 1943 次
……（中间是第 17 章 17.10.3 节那样的事务表和 SLA 表）
检查通过：没有失败的事务，SLA 全部达标
> $LASTEXITCODE
0

    -ExecutionPolicy Bypass 让这一次运行不受系统脚本执行策略的限制，Windows 默认不允许直接运行 .ps1 文件。实测把练习网站停掉再运行，虚拟用户在登录这一步就全部失败，几秒钟场景就结束了，lr_summary.py 列出失败的事务，退出码是 1。

    Jenkins 里给压测机加一个标签（比如 loadrunner），流水线里单独写一个阶段在它上面运行（同样只演示结构，没有在真实的 Jenkins 上跑过）：

            stage('LoadRunner 压测') {
            agent { label 'loadrunner' }                 // 只在装了 LoadRunner 的 Windows 压测机上运行
            steps {
                bat 'powershell -NoProfile -ExecutionPolicy Bypass -File tools\\run_lr.ps1 -Scenario D:\\work\\autotest-demo\\lr\\scenarios\\demo16.lrs -ResultRoot D:\\work\\lr-results'
            }
        }

    Windows 节点上执行命令用 bat，不用 sh；Groovy 的字符串里反斜杠要写两个。完整的压测动辄几十分钟到几小时，一般不放在每次推代码都跑的流水线里，而是每天夜里定时跑一次，或者上线前手动触发。

    19.6 结果通知¶

    流水线跑完要让人知道结果。企业微信、钉钉、飞书的群都可以添加群机器人：在群设置里添加一个机器人，会得到一个 Webhook 地址，往这个地址发一条 HTTP 请求，群里就会出现一条消息。

    tools/notify.py 读取 pytest 生成的 junit.xml，拼成一条消息发到企业微信群：

    """把测试结果发到企业微信群。

用法：
    pytest --junitxml=reports/junit.xml
    python tools/notify.py reports/junit.xml
群机器人的地址放在环境变量 WECOM_WEBHOOK 里；没设置时只把要发的内容打印出来，不发送。
"""
import os
import sys
import xml.etree.ElementTree as ET

import requests


def read_junit(path):
    """从 pytest 生成的 junit.xml 里读出总数、失败数、跳过数、耗时和失败用例名。"""
    root = ET.parse(path).getroot()
    suite = root if root.tag == "testsuite" else root.find("testsuite")
    total = int(suite.get("tests"))
    failed = int(suite.get("failures")) + int(suite.get("errors"))
    skipped = int(suite.get("skipped"))
    failed_names = [
        f"{case.get('classname')}.{case.get('name')}"
        for case in suite.iter("testcase")
        if case.find("failure") is not None or case.find("error") is not None
    ]
    return total, failed, skipped, float(suite.get("time")), failed_names


def build_message(total, failed, skipped, seconds, failed_names):
    title = "全部通过" if failed == 0 else f"有 {failed} 条失败"
    lines = [
        f"### 自动化测试结果：{title}",
        f"> 总数 {total}，通过 {total - failed - skipped}，失败 {failed}，跳过 {skipped}，耗时 {seconds:.0f} 秒",
    ]
    lines += [f"- {name}" for name in failed_names[:10]]
    if len(failed_names) > 10:
        lines.append(f"- 还有 {len(failed_names) - 10} 条，详见测试报告")
    return "\n".join(lines)


def main():
    if len(sys.argv) != 2:
        sys.exit("用法：python tools/notify.py <junit.xml 的路径>")
    text = build_message(*read_junit(sys.argv[1]))
    webhook = os.getenv("WECOM_WEBHOOK")
    if not webhook:
        print("没有设置 WECOM_WEBHOOK，只打印不发送：\n" + text)
        return
    resp = requests.post(webhook, json={"msgtype": "markdown", "markdown": {"content": text}}, timeout=10)
    body = resp.json()
    if resp.status_code != 200 or body.get("errcode") != 0:   # 企业微信出错时 HTTP 也是 200，要看 errcode
        sys.exit(f"发送失败：{resp.text}")
    print("已发送到企业微信群")


if __name__ == "__main__":
    main()

    不设置 WECOM_WEBHOOK 时只打印，方便先在本机看看效果：

    (.venv) > pytest tests\api -q --junitxml=reports/junit.xml
(.venv) > python tools\notify.py reports\junit.xml
没有设置 WECOM_WEBHOOK，只打印不发送：

> 总数 108，通过 103，失败 0，跳过 5，耗时 16 秒

    想看看有失败时消息长什么样，临时建一个必定失败的用例 tests/api/test_tmp_fail.py：

    def test_tmp_fail():
    assert 1 == 2

    再跑一遍上面两条命令：

- tests.api.test_tmp_fail.test_tmp_fail

    看完把 test_tmp_fail.py 删掉。

    注意发送结果的判断：企业微信出错时 HTTP 状态码也是 200，要看响应里的 errcode 是不是 0。和第 2 章讲的一样，HTTP 200 不等于成功，这条规矩在写工具脚本时同样适用。钉钉、飞书的机器人用法类似，只是请求体的格式不同，看它们各自的文档。

    19.7 让自动化长期发挥作用¶

    自动化写出来不难，难的是一直有用。几条经验：

    1. 失败当天就处理。 每一次红色都要有结论：是产品缺陷就提缺陷单，是用例问题就修用例，是环境问题就找人修环境。没人看的失败，几天后就没人再相信这套自动化了；
    2. 不稳定的用例要么修好，要么先拿出来。 不能让「偶尔失败一下很正常」成为常态；
    3. 用例跟着需求走。 需求改了，相关用例当天就改；功能下线了，用例也删掉。过时的用例比没有用例更糟糕，它会给人错误的信心；
    4. 关注执行时间。 冒烟用例控制在几分钟，全量回归控制在一小时以内，超了就并行、精简或拆分；
    5. 报告要让别人看得懂。 用例标题写清楚「在什么情况下，期望什么结果」，失败信息写清楚期望值和实际值；
    6. 用 AI 提效，执行交给脚本。 AI 很适合帮你写脚本初稿、解释看不懂的报错、根据需求补充用例场景；日常回归则交给写好的确定性脚本去跑，一条用例几十毫秒，结果稳定可重复。

    19.8 接下来学什么¶

    学完这份教程，你已经具备了自动化测试的完整基础。往下可以按兴趣选方向深入：

    • App 自动化：Appium、uiautomator2，思路和 UI 自动化相通，多了设备管理；
    • 接口安全测试：越权访问、注入、敏感信息泄露，可以从 OWASP Top 10 开始；
    • Mock 与契约测试：WireMock 搭模拟服务，Pact 做服务之间的接口约定检查；
    • 性能深入：Prometheus 加 Grafana 的监控、SkyWalking 的调用链分析、数据库和应用的调优；
    • Linux 和 Docker：测试环境和流水线基本都跑在 Linux 和容器里；
    • 测试平台：把用例管理、执行、报告做成网页平台，给整个团队用；
    • 业务理解：最好的测试用例来自对业务的深刻理解，这一点任何工具都替代不了。

    19.9 练习¶

    1. 给所有 UI 用例加一个 ui 标记（登记在 pytest.ini 里），用 pytest -m "not ui" 只跑接口用例。
    2. 用 pytest -n 2、-n 4、-n auto 各跑一次，记录耗时，看看哪个最快。
    3. 把练习网站换成用 SHOP_SINGLE_SESSION=1 启动，再跑几次 pytest -n 4。编写教程时实测连跑 5 次都全部通过，但这不代表没有隐患：想一想哪几条用例理论上会互相影响，在什么时机下它们才会失败，怎么改才能彻底避免。（提示：好几条登录类用例都用 bob，有的登录完还要接着用这个 token。）做完记得去掉开关，按默认方式重启练习网站。
    4. 在 GitHub 上建一个仓库，把工程推上去，看流水线能不能跑通；跑不通就根据日志修。
    5. 建一个只有自己的企业微信群，加一个群机器人，把测试结果真正发一次。
    6. 在本机用 tools\run_lr.ps1 运行第 16 章的 demo16，记下退出码；再把 account.dat 里第一个账号的密码改错，运行一次，看退出码和输出有什么不同，最后改回来。
