    第 9 章 元素定位详解¶

    本章目标

    • 理解定位器（Locator）的工作方式：惰性求值与严格模式；
    • 把 get_by_* 家族完整用一遍，知道每种写法适合什么元素；
    • 会写常用的 CSS 选择器，分清哪些是标准 CSS、哪些是 Playwright 的扩展；
    • 知道 XPath 什么时候才值得用，会写按文本定位和按轴定位；
    • 会用 filter 和 first / nth / last 在列表里精确定位；
    • 能给团队定一套稳定的定位约定；
    • 会用 count()、调试器、浏览器开发者工具快速验证定位写法。

    9.1 定位器是什么¶

    第 8 章 8.5 节已经用过最常用的几种定位写法，这一章把它们讲透。

    先纠正一个容易有的误解。下面这行代码执行的时候，什么都没有发生：

    row = page.get_by_test_id("order-row").filter(has_text="SO20261022000027")

    get_by_test_id(...) 不会马上去页面上找元素，它只是把「怎么找」记下来，返回一个定位器（Locator）对象。真正去找元素的时刻，是对它做操作或断言的那一刻：.click()、.inner_text()、expect(...)。这个特点叫惰性求值。

    它带来两个直接的好处：

    • 页面刷新、列表重新渲染之后，定位器照样能用。每次操作都按描述重新找一遍，不会攥着一个已经从页面上删掉的旧元素；
    • 定位器可以先定义、后使用。第 11 章讲页面对象模式，__init__ 里定义的全是定位器，靠的就是这个特性。

    第二个关键设定是严格模式（strict mode）。对一条定位器做操作或断言时，如果它在页面上命中了多个元素，Playwright 不猜你要哪一个，直接报错。在练习场页面（/lab.html，不需要登录）上故意写一条宽泛的定位试试：

    page.get_by_role("button").click(timeout=2000)

    Locator.click: Error: strict mode violation: get_by_role("button") resolved to 7 elements:
    1) <button id="logout" type="button">退出</button> aka get_by_role("button", name="退出")
    2) <button type="button" id="btn-alert" data-testid="btn-alert">弹提示框</button> aka get_by_test_id("btn-alert")
    3) <button type="button" id="btn-confirm" data-testid="btn-confirm">弹确认框</button> aka get_by_test_id("btn-confirm")
    4) <button type="button" id="btn-prompt" data-testid="btn-prompt">弹输入框</button> aka get_by_test_id("btn-prompt")
    5) <button type="button" id="btn-hover" data-testid="btn-hover">把鼠标放上来</button> aka get_by_test_id("btn-hover")
    6) <button type="button" id="btn-dblclick" data-testid="btn-dblclick">…</button> aka get_by_test_id("btn-dblclick")
    7) <button type="button" id="btn-submit" data-testid="btn-submit">提交</button> aka get_by_test_id("btn-submit")

    页面上有 7 个按钮，Playwright 一个一个列出来，aka 后面还给出每个元素更精确的定位写法——照着抄一条就行。这条报错是定位写错了时最有用的提示，值得学会读。

    反过来，定位器一个元素都没命中时，定位本身不报错，操作会一直等元素出现，等到超时：

    Locator.click: Timeout 2000ms exceeded.
Call log:
  - waiting for get_by_role("button", name="不存在的按钮")
    行为 多个命中 零个命中
    click() 这类操作 严格模式报错 等到超时
    expect(...) 断言 严格模式报错 等到超时
    count()、all() 不受限，照实返回 返回 0 或空列表

    count() 和 all() 故意不受严格模式约束，它们就是用来看「现在到底有几个」的，9.7 节调试时会用到。

    9.2 get_by_* 家族¶

    第 8 章给过一张推荐顺序表，这一节把每个方法在练习网站上真实跑一遍。总的原则：先问用户怎么看这个元素（它是什么角色、带什么标签、显示什么文字），再问代码里它长什么样（有什么属性、嵌在哪个位置）。

    9.2.1 get_by_role：按角色和名称，首选¶

    按钮、链接、输入框、复选框、下拉框、标题、表格行，浏览器都给它们定了角色（role），get_by_role 按角色加名称来找。把练习场扫一遍：

    page.goto("/lab.html")
print(page.get_by_role("button").count())                    # 7
print(page.get_by_role("link").count())                      # 5
print(page.get_by_role("checkbox").count())                  # 1
print(page.get_by_role("radio").count())                     # 2
print(page.get_by_role("combobox").count())                  # 1
print(page.get_by_role("textbox").count())                   # 2（键盘输入框 + 日期框）
print(page.get_by_role("heading", level=2).count())          # 5

    name= 参数匹配的是元素的可访问名称：按钮和链接取文字，输入框取关联的 label。它默认模糊匹配，exact=True 转成完整匹配：

    print(page.get_by_role("button", name="双击我").count())           # 1，按钮文字是「双击我（0 次）」
print(page.get_by_role("button", name="双击我", exact=True).count())  # 0，完整相等匹配不上

    双击按钮的文字是「双击我（0 次）」，里面的计数一变，完整匹配就失效，模糊匹配不受影响。要匹配变化的文字，用正则：

    import re
expect(page.get_by_role("button", name=re.compile(r"双击我（\d+ 次）"))).to_have_count(1)

    get_by_role 还能带状态筛选，把「是什么」和「是什么状态」一句话写完：

    page.get_by_role("checkbox", checked=False)          # 没勾选的复选框
page.get_by_role("button", name="上一页", disabled=True)   # 禁用状态的上一页按钮（商品页第 1 页时）
page.get_by_role("dialog", include_hidden=True)      # 连隐藏的弹窗也算进来（默认不算）

    怎么知道某个元素的角色和名称？两个办法：在开发者工具里看元素有没有语义标签（button 天生就是 button 角色）；或者打印可访问性快照，它就是 Playwright 眼中的页面：

    print(page.locator("main").aria_snapshot())

    - main:
  - heading "交互练习场" [level=1]
  - heading "浏览器自带弹窗" [level=2]
  - button "弹提示框"
  - button "弹确认框"
  - button "弹输入框"
  - heading "各种输入控件" [level=2]
  - paragraph:
    - text: 城市
    - combobox "城市":
      - option "请选择" [selected]
      - option "上海"
      ...

    快照里每行的角色和名称就是 get_by_role 的参数。这也是检查页面语义好不好用的办法：一个按钮在快照里连名字都没有，屏幕阅读器同样读不出它，多半是页面写得有问题。

    9.2.2 get_by_label：按标签文字找表单项¶

    练习网站的登录页用的是 label for="id" 加 input id 的写法，商品页的关键词搜索框也是；练习场的控件则把 input 直接包在 <label> 里。两种写法 get_by_label 都认得：

    page.get_by_label("键盘按键", exact=True)   # 练习场的键盘输入框
page.get_by_label("同意协议")              # 复选框

    有一个细节要留意：label 包裹写法里，label 里的全部文字都算标签文字。练习场「城市」的 label 长这样：

    <label>城市
  <select id="city" data-testid="city">
    <option value="">请选择</option>
    ...
  </select></label>

    label 里除了「城市」两个字，还包着下拉框的全部选项文字，所以完整匹配匹配不上：

    print(page.get_by_label("城市").count())            # 1，模糊匹配命中
print(page.get_by_label("城市", exact=True).count())  # 0，完整相等匹配不上

    遇到 exact=True 突然找不到元素，先想想是不是有额外的文字混进了匹配范围。

    9.2.3 get_by_placeholder：按提示文字找输入框¶

    输入框里那段灰色提示文字：

    print(page.get_by_placeholder("在这里敲键盘").count())   # 1，练习场的键盘输入框

    提示文字经常随产品文案改动，有 label 或角色可用时优先用它们，placeholder 放在靠后的位置。

    9.2.4 get_by_text：按文字找，当心超配¶

    get_by_text 找所有文字包含目标内容的元素，同样默认模糊、可加 exact=True。它适合找不需要操作的展示文字，但文字太短时会大量超配。订单页上试一下：

    page.goto("/orders.html")
t = page.get_by_text("支付")
print(t.count())                          # 30
print(sorted(set(t.all_inner_texts())))   # ['已支付', '待支付', '支付']

    「支付」两个字同时命中了按钮「支付」、「待支付」、「已支付」，共 30 个元素。按文字定位时把文字写长一点，或者先定位到容器再往里找（9.5 节）。

    9.2.5 get_by_test_id：按测试专用属性找¶

    get_by_test_id("btn-submit") 找的是带 data-testid="btn-submit" 属性的元素。这个属性不参与样式和逻辑，唯一用途就是给自动化测试定位，是最稳定的定位方式，9.6 节专门讲怎么在团队里推行。默认认 data-testid 属性，个别团队用别的名字时可以全局改：

    p.selectors.set_test_id_attribute("data-qa")   # 之后 get_by_test_id 认 data-qa

    9.2.6 get_by_alt_text：按图片说明找¶

    图片的 alt 属性是图片加载不出来时的替代文字，也是屏幕阅读器读图片的依据。个人中心页的头像图就带 alt="头像"：

    page.goto("/profile.html")
print(page.get_by_alt_text("头像").count())   # 1

    9.2.7 get_by_title：按悬浮提示找¶

    title 属性是鼠标放上去显示的气泡提示。练习网站没有带 title 的元素，用 set_content 造一小段页面演示（set_content 的意思是「把这段 HTML 当作当前页面」，造演示页面、复现问题都很方便）：

    page.set_content('<span title="库存数量">128</span>')
print(page.get_by_title("库存数量").inner_text())   # 128

    9.2.8 小结¶

    写法 找什么 练习网站上的例子
    get_by_role 有角色的元素，首选 get_by_role("button", name="提交")
    get_by_label 有标签的表单项 get_by_label("同意协议")
    get_by_placeholder 带提示文字的输入框 get_by_placeholder("在这里敲键盘")
    get_by_text 展示文字，当心超配 get_by_text("没有找到相关商品")
    get_by_test_id 测试专用属性，最稳 get_by_test_id("order-row")
    get_by_alt_text 图片 get_by_alt_text("头像")
    get_by_title 悬浮提示 页面上暂无，较少用

    前四种在元素没有语义标签、没有 label 时会失效，那时候再落到下一节的 CSS。

    9.3 CSS 选择器¶

    locator("...") 里直接写 CSS 选择器。CSS 是前端的基本功，这一节只过自动化常用的那些，全部例子都在订单页和商品页实测。

    基础写法：#id 按 id、.class 按类名、tag 按标签、[attr] 和 [attr='值'] 按属性，可以自由组合：

    page.locator("#status")                    # 订单页的状态下拉框
page.locator("select#status")              # 再限定必须是 select 标签
page.locator(".pager button")              # 商品页翻页区里的全部按钮（上一页、下一页）
page.locator("[data-testid='order-row']")  # 属性选择器，等价于 get_by_test_id
page.locator("#status option:checked")     # 下拉框当前选中的选项，文字是「全部」

    属性匹配三件套，^= 开头、$= 结尾、*= 包含：

    page.locator("[data-testid^='order']")   # data-testid 以 order 开头
page.locator("[data-testid$='row']")     # 以 row 结尾
page.locator("[data-testid*='der']")     # 包含 der

    后代与直接子代：空格表示「里面任何层级」，> 表示「直接子级」。订单页的表格体 tbody 下直接放着数据行：

    page.locator("tbody > tr")       # 直接子级
page.locator("#rows tr")         # 后代，这里与上面等价

    位置：:nth-child(n) 从 1 数起。它有个容易踩的地方——在每个父容器里各数一遍，所以 table tr:nth-child(1) 会同时命中表头行和第一行数据：

    print(page.locator("table tr:nth-child(1)").count())   # 2：thead 的表头行 + tbody 的第一行

    按位置定位本来就不稳（数据一变就错位），这里知道它怎么数数就行。

    按内容选元素的三个伪类，补上普通 CSS 按内容选元素的短板：

    写法 含义 出处
    :has-text('文字') 元素内部（任何层级）包含这段文字 Playwright 独有的扩展
    :has(里层选择器) 元素内部能找到匹配里层选择器的元素 标准 CSS，较新的浏览器才支持
    :is(选择器组) 自身匹配组里任意一个 标准 CSS，较新的浏览器才支持 
    page.locator("tr[data-testid='order-row']:has-text('待支付')")     # 含「待支付」的数据行
page.locator("tr:has(button)")                                     # 里面有按钮的行
page.locator("button:is(#prev, #next)")                            # 上一页或下一页按钮

    :has-text() 是 Playwright 的扩展，浏览器本身不认识。拿浏览器原生的查找接口一试便知：

    page.evaluate("document.querySelectorAll('button:has-text(提交)').length")

    Page.evaluate: SyntaxError: Failed to execute 'querySelectorAll' on 'Document': 'button:has-text(提交)' is not a valid selector.

    所以它只能写在 locator() 里，别写进样式表，也别指望 page.evaluate 认识它。同样的原生接口换成 section:has(button) 就认，返回 3——:has() 和 :is() 是标准 CSS，较新的浏览器原生支持；但老浏览器内核（比如一些嵌入设备里的网页组件）未必有，离开 Playwright、换个工具或环境时不一定能用。同一个选择器「locator() 里能用、原生接口不认」时，先想到扩展伪类。

    坑

    两种写法混着用。 :has-text('待支付') 和 filter(has_text="待支付") 效果一样，后者是定位器的正式方法，还能和 has=、has_not= 自由组合。团队里统一用一种，别在同一个工程里两种混写。

    9.4 XPath：留到最后再用¶

    XPath 是另一种查询语言，能做 CSS 做不到的两件事：按文本找、按相对关系（轴）找。但它读写都费劲，页面结构一改就断，原则是：CSS 能办到就别上 XPath。

    写法是在 locator() 里加 xpath= 前缀（以 // 或 .. 开头时前缀可以省略）：

    page.locator("xpath=//th")                          # 等价于 page.locator("//th")
page.locator("xpath=//button")                      # 全部按钮

    语法速查：// 从任意层级找，@属性名 取属性，text() 精确文本，contains() 部分匹配，[n] 第几个（从 1 数起），following-sibling:: 后面的同级元素。

    订单表格是 XPath 的主场。订单页要登录、还要有订单，下面的例子用了两个现成的夹具：第 4 章写的已登录接口客户端 api（用来造订单），和第 11 章 11.3 节要讲的 logged_in_page（把接口拿到的登录态种进浏览器，省掉每次走登录页），这里先直接用。实测时造好的订单号是 SO20261022000027（订单号按日期和流水号生成，你自己造出来的号会不一样，照着换成自己的）：

    # 订单号精确等值的行，取第 3 格（金额）
page.locator("xpath=//tr[td[1]='SO20261022000027']/td[3]")         # ¥2.50
# contains 按部分文本找行，取第 5 格（下单时间）
page.locator("xpath=//tr[contains(., 'SO20261022000027')]/td[5]")  # 2026-10-22 16:44:03
# 轴：表头「状态」右边那个表头
page.locator("xpath=//th[text()='状态']/following-sibling::th[1]") # 下单时间
# 待支付那一行的最后一个单元格（操作列，放着支付和取消按钮）
page.locator("xpath=//tr[td[1]='SO20261022000027']/td[contains(text(),'待支付')]/following-sibling::td[last()]")

    contains(., '...') 里的 . 表示整行元素的全部文字，比逐格判断短得多。following-sibling::tr[1] 能拿到「下一行」，是表格逐行比对时的常用轴。

    坑

    contains() 是部分匹配，会超配。 //td[contains(text(),'支付')] 同时命中「待支付」「已支付」两种单元格。用 XPath 按文本找，文本要给足，或者用完整等值的写法 //td[text()='待支付']。

    坑

    绝对路径 XPath 是一次性的。 /html/body/main/section[1]/button[3] 这种从页面根一路数下来的写法，今天在练习场上确实能找到「弹输入框」按钮，开发在中间加一个 div 就全部失效。看到路径里有 /html/body，直接重写。

    9.5 链式与过滤：在列表里精确定位¶

    真实页面上到处都是列表：商品列表、订单列表、表格行。定位列表里的目标分两步：先筛出容器，再在容器里面找。第 8 章 8.5 节见过一次，这里展开。

    9.5.1 filter：从一组元素里筛选¶

    filter() 在现有定位器的基础上继续筛，可以串多次。四种常用参数：

    rows = page.get_by_test_id("order-row")        # 全部订单行

rows.filter(has_text="SO20261022000027")            # 按文字筛：包含这段文字的行
rows.filter(has_text=re.compile(r"×[2-9]"))         # 文字支持正则：商品列是「中性笔 ×3」这种 2～9 件的行
rows.filter(has_not_text="已取消")                   # 反向：不包含
rows.filter(has=page.get_by_role("button", name="支付"))    # 行里找得到支付按钮的
rows.filter(has_not=page.get_by_role("button", name="支付"))  # 行里没有支付按钮的

    has= 里的定位器是相对外层元素找的：上面最后一行的意思是「在这行的范围内找得到『支付』按钮」。文字筛不动的场景它都能写，比如「有附件图标的工单」「没有头像的用户行」。

    9.5.2 链式定位¶

    筛选和定位可以一直链下去，范围逐步收窄。订单页的完整例子：造一张待支付订单（product 也是第 4 章写的夹具，给出一件便宜的商品），按订单号筛出行，在行内找按钮：

    order = ok(api.create_order([{"productId": product["id"], "quantity": 1}]))
no = order["orderNo"]
page.goto("/orders.html")
rows = page.get_by_test_id("order-row")
expect(rows.first).to_be_visible()                    # 先等列表渲染出来

row = rows.filter(has_text=no)                        # 这一单的行
expect(row).to_have_count(1)                          # 订单号唯一，应该恰好一行
expect(row.get_by_role("button", name="支付")).to_have_count(1)
expect(row.get_by_role("cell").nth(3)).to_have_text("待支付")   # 行内第 4 格是状态

    行定位器 row 是惰性的，支付之后页面重新渲染，同一条 row 再去读，读到的是渲染后的新内容：

    row.get_by_role("button", name="支付").click()
expect(row).to_contain_text("已支付")                  # 重新渲染后状态变了
expect(row.get_by_role("button", name="支付")).to_have_count(0)   # 支付按钮消失了

    9.5.3 first、nth、last¶

    一条定位器命中多个元素时，.first、.last、.nth(n) 取第几个（从 0 数起）。它们常见于「列表有固定顺序」的场景，比如最新一条订单永远在最上面：

    rows.first.get_by_role("cell").nth(0).inner_text()   # 第一行第一格：订单号
rows.last                                            # 最后一行
rows.nth(99).count()                                 # 0：越界不报错，就是匹配不到

    坑

    按位置定位是脆的。 nth(2) 依赖「第三行永远是它」，排序一变、插一条数据就点错行，而且用例照样通过——点错了元素但没人发现，比报错更糟。能用文字、订单号、data-testid 筛的，不用位置；确实要按位置的（比如验证默认排序），在断言里把顺序本身测出来。

    配套的 all() 把命中元素逐个变成定位器，适合遍历：

    for cell in row.get_by_role("cell").all():
    print(cell.inner_text())

    注意 all() 不等待、有多少算多少，前面先 expect(rows.first).to_be_visible() 把列表等出来再用它。

    9.6 定位策略的取舍¶

    9.6.1 脆定位的三个特征¶

    回看已经踩过的坑，脆定位几乎都落在三类：

    1. 动态生成的 id 或类名。前端框架构建时生成的 css-1x2y3z 这类哈希类名，每次发版都可能变；id 里带序号的（input-847），加一个字段就变；
    2. 装饰性类名与位置。.text-red 表达的是样式意图（红字），开发调成橙色用例就挂；nth(2)、table tr:nth-child(1) 表达的是位置，数据一变就错位；
    3. 绝对路径 XPath。/html/body/main/div[2]/…，页面加个容器就全部失效。

    它们的共同点：把定位建立在与业务无关的细节上。样式会改、位置会挪、结构会重排，只有「这是个提交按钮」「这是订单 SO20261022000027 的行」这种业务含义不会轻易变。

    9.6.2 data-testid：给测试留的门¶

    data-testid 的做法来自前端测试工具 Testing Library 的约定：开发在写页面时，给自动化测试需要触碰的元素加一个 data-testid 属性，值用稳定的业务名（order-row、btn-submit），不参与样式和逻辑，改版时也没人会动它。Playwright 的 get_by_test_id 默认就认这个属性。

    它和语义定位不冲突：有角色、有 label 的元素优先语义定位（顺便验证了页面语义没坏），列表行、状态徽标这类「不好用一句话描述」的元素用 data-testid。练习网站两者都有，对比着体会。

    9.6.3 团队落地建议¶

    定位约定要写成文档，光靠口头约定很难长期执行：

    • 定优先级：写进团队文档，比如「role → label → testid → CSS → XPath（评审才放行）」，和 9.2 节的顺序一致；
    • 向开发提需求：新页面提测时，列表行、按钮、输入框要带 data-testid，命名用业务名。这条写进提测标准，比事后补便宜得多；
    • 评审看定位：用例代码评审时专看一眼定位写法，出现 /html/body、哈希类名、裸 nth() 就退回。定位是 UI 用例维护成本的大头，值得在评审里花时间。

    9.7 调试定位器¶

    定位写不出来或者行为不符合预期时，按下面的顺序排查，基本都能就地解决。

    第一步：用 count() 验证。 count() 立刻返回当前命中的个数，是定位器世界的 print：

    print(page.get_by_test_id("order-row").count())          # 0 是还没渲染出来，有一个数就是查出来了
print(page.get_by_text("支付").count())                   # 30：超配了，文字太短

    命中 0 个，要么定位写错、要么元素还没出现（配合 expect(...).to_be_visible() 分辨）；命中多个，缩小范围。

    第二步：用调试器看命中。 代码里加一行 page.pause()，或者在运行前设置环境变量 PWDEBUG=1：

    (.venv) > $env:PWDEBUG = "1"
(.venv) > pytest tests\ui\test_orders_ui.py::test_pay_in_page

    会打开浏览器和 Playwright Inspector（调试器）窗口：可以一步步执行，看每一步定位到了哪个元素；在调试器里试写定位表达式，命中的元素会在浏览器里高亮显示，命中几个、每个是什么一目了然。设置了 PWDEBUG=1 时 Playwright 会自动用有头模式启动浏览器，不用再加 --headed；只写 page.pause() 不设环境变量的话，必须自己加 --headed，否则无头模式下这行什么都不做、直接往下走。调试完记得去掉环境变量。录制工具 playwright codegen 的 Pick locator 按钮也能干这件事：点一下再悬停到元素上，直接给出推荐的定位写法。

    第三步：浏览器开发者工具。 设置 PWDEBUG=console 再加 --headed 运行，Playwright 会往页面里注入一个 playwright 对象。在浏览器窗口按 F12 打开开发者工具的 Console 面板，就能用 Playwright 同一套定位引擎：

    playwright.$$("button")                                         // 按选择器找，练习场上返回 7 个按钮
playwright.selector(document.querySelector("#btn-submit"))      // 反查选择器：internal:testid=[data-testid="btn-submit"s]
playwright.generateLocator(document.querySelector("#btn-submit"), "python")   // 反查 Python 写法

    最后一句返回 get_by_test_id("btn-submit")，对页面上任何元素都能反查出推荐的 Python 定位写法，非常好用。配合浏览器原生的 document.querySelectorAll("选择器")（控制台里可以简写成 $$("选择器")），可以区分「CSS 本身写得对不对」和「是不是用了 Playwright 扩展伪类」——9.3 节证明 :has-text() 不被浏览器认识，用的就是原生接口。

    顺手一招：aria_snapshot。 9.2.1 节的快照也能在调试时打印，定位不到元素时先看快照里有没有它、角色和名称是什么，比在 DOM 树里翻快得多。

    9.8 常见的坑¶

    坑

    用 .first 把严格模式报错压下去。 严格模式报错了，说明这条定位本来就是模糊的。加 .first 只是不报错了，点的可能还是错的元素，用例照样通过。正确做法是照报错里的 aka 提示加条件，把范围缩到唯一。

    坑

    get_by_text 的文字太短。 「支付」命中 30 个元素（9.2.4 节）。按文字定位把文字给足，或者先定位容器再往里找。

    坑

    label 包裹写法下 exact=True 匹配不上。 「城市」的 label 里包着下拉框的全部选项文字，完整匹配失效（9.2.2 节）。exact 找不到时，先打印 aria_snapshot() 看可访问名称到底是什么。

    坑

    把 :has-text() 写进普通 CSS。 它是 Playwright 独有的扩展，document.querySelectorAll 和样式表都不认识，直接报 is not a valid selector。同一段选择器在 locator() 里能用、在开发者工具里不能用时，先想想是不是扩展伪类。

    坑

    nth-child 在每个父容器里各数一遍。 table tr:nth-child(1) 命中表头行和第一行数据（9.3 节）。要全表唯一，选择器里把父容器写死：tbody > tr。

    坑

    XPath 的 contains() 超配。 contains(text(),'支付') 同时命中「待支付」「已支付」。文本给足或用 text() 等值匹配。

    坑

    ElementHandle 在页面重渲染后失效。 page.query_selector(...) 返回的是元素句柄，攥住的是「当时那个元素」。实测在订单页先拿一行的句柄，再在页面上支付这一单：定位器读到的状态是「已支付」，句柄读到的还是「待支付」——它指向的旧元素已经从页面上摘掉了；拿句柄去点按钮，直接报 Element is not attached to the DOM。测试代码一律用定位器（Locator），别用 ElementHandle。

    坑

    一个元素一个写法到处复制。 同一个按钮的定位散落在二十个用例里，改一次文案改二十处。收进页面对象（第 11 章 11.2 节），一个页面一个类，定位只写一遍。

    9.9 练习¶

    1. 在练习场上分别用 get_by_role、get_by_label、get_by_test_id 定位「提交」按钮，各打印一次 count()，体会三种写法的长短。
    2. 打印商品页 main 的 aria_snapshot()，找到「下一页」按钮的角色和名称，然后写断言：第 1 页时它是禁用的，点一下之后「第 2 页」出现。
    3. 在订单页分别用 CSS（:has-text）和 XPath（contains + 轴）定位一张待支付订单的「取消」按钮，两种写法各点一次（用接口造两张订单）。
    4. 故意写一条命中多个元素的定位触发严格模式报错，照着 aka 提示改成唯一定位；再故意写一条命中零个的，看超时报错长什么样。

    9.10 自检清单¶

    • 能说出定位器的惰性求值是什么，它为什么让定位器可以提前定义；
    • 遇到 strict mode violation 时知道怎么读报错、怎么缩小范围；
    • 能按推荐顺序说出 get_by_* 家族各方法适合的元素；
    • 能解释「城市」的 label 为什么 exact=True 匹配不上；
    • 知道 :has-text()、:has()、:is() 里哪个是 Playwright 独有的扩展、哪两个是标准 CSS；
    • 能写出「按订单号筛行、行内找支付按钮」的链式定位；
    • 能说出脆定位的三个特征，以及 data-testid 约定怎么在团队落地；
    • 调试定位时会用 count()、调试器和开发者工具这三招。
