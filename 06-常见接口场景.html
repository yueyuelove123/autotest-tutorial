    第 6 章 常见接口场景¶

    本章目标

    • 会测文件上传和文件下载：multipart 请求体怎么打包、二进制响应怎么断言、CSV 的编码怎么验证；
    • 会调带签名的开放接口，说得清签名和时间戳各自防什么、四种验签失败怎么逐个测；
    • 会处理 token 过期：说得清 40101、40102、40103 的区别，会手动刷新，会把自动续期收进客户端；
    • 会测异步任务：提交、轮询、下载三步，轮询代码带超时和状态断言；
    • 会测水平越权，掌握「把路径里的编号换成别人的」这套方法，并且真抓一次缺陷；
    • 把新接口从手工调试到封装、再到用例的完整流程走熟，以后面对任何新场景都有固定的入手动作。

    前四章搭好了接口自动化的架子：requests 发请求、pytest 组织用例、接口客户端收拢公共代码，第 5 章的设计方法回答「测什么」。这一章处理实战里最常见的五类场景：上传下载、签名、token 过期、异步任务、越权。它们的共同点是，接口文档往往只写「正常调用怎么发」，而坑全在文档没写的部分：请求体怎么打包、时间戳用秒还是毫秒、任务没跑完来下载怎么办、别人的编号能不能操作。

    每一类场景都按同一套流程走：先看文档或页面代码，写个小脚本手工调通，封装成客户端方法，最后用正反用例把实测到的行为钉住。做完这一章，你会发现这五类陌生的场景用的竟是同一套动作，6.7 节把它总结成清单。

    本章的演示会用到练习网站的三个环境变量开关：SHOP_TASK_LATENCY（6.5 节）、SHOP_TOKEN_TTL（6.4 节）、SHOP_IDOR_BUG（6.6 节）。每个开关用完都要去掉再重启网站，这是本章最重要的纪律，忘了做，后面的用例会成片失败，而且失败原因看起来莫名其妙。另外本章在 pytest.ini 的 markers 里登记了两个新标记：

    concurrency: 并发类用例
    token_ttl: 要在 SHOP_TOKEN_TTL 开着的网站上跑的用例
    idor: 越权类用例，拿自己的 token 动别人的数据

    6.1 文件上传¶

    6.1.1 表单里有文件时，请求体长什么样¶

    前面章节的请求体都是 JSON：json={...} 一行搞定，Content-Type 是 application/json。上传文件是另一套格式，叫 multipart/form-data（多部分表单）。页面上的「上传头像」按钮用浏览器的 FormData 把文件装进请求体，交给浏览器打包；写自动化时，requests 的 files= 参数做的是同一件事。

    它到底把字节拼成了什么样？不真的发出去，用 prepare() 组装一下再看（存成 scratch/multipart_peek.py）：

    """不真的发出去，只看看 requests 把文件打包成了什么样子。"""
import requests

req = requests.Request(
    "POST", "http://127.0.0.1:8000/api/users/avatar",
    files={"file": ("avatar.png", b"(PNG-BYTES)", "image/png")},
).prepare()                      # prepare() 只组装请求，不发送

print("Content-Type:", req.headers["Content-Type"])
print("----- 请求体 -----")
print(req.body.decode())

----- 请求体 -----
--0f499c969ce90ada06549ddb01abbeaf
Content-Disposition: form-data; name="file"; filename="avatar.png"
Content-Type: image/png

(PNG-BYTES)
--0f499c969ce90ada06549ddb01abbeaf--

    三件事值得注意：

    • boundary（边界线）：一串随机字符，用来隔开请求体里的每个部分，开头、结尾各一条，也在 Content-Type 头里声明。它必须每次随机生成，你自己编一个固定的，理论上文件内容里可能恰好出现同样的字符串，边界就乱了；
    • 文件类型由你声明：第三行 Content-Type: image/png 来自 files= 元组的第三项。requests 不打开文件看内容，也不根据扩展名猜类型，你写什么它发什么；
    • 表单字段名是 file：第二行 name="file"，服务端按这个名字取文件。写错了服务端会说「缺 file 字段」，返回 422。

    files= 支持几种写法，差别在类型怎么来：

    写法 类型从哪来
    {"file": 文件对象} 或 {"file": (文件名, 内容)} requests 按扩展名猜，猜不出来就写成 application/octet-stream（意思是不明的二进制）
    {"file": (文件名, 内容, 类型)} 你声明，最稳

    练习网站只收 image/jpeg 和 image/png，前两种写法因为类型被猜成别的，全部被 4001 拒绝。养成三项写全的习惯，不赌服务端认不认猜测的类型。

    坑

    不要手工设置 Content-Type。 网上有人这样写：headers={"Content-Type": "multipart/form-data"}。这会把 requests 自动生成的、带 boundary 的头整个覆盖掉，服务端找不到边界线，直接报错。实测：

    400 {"detail":"Missing boundary in multipart."}

    说明

    规矩只有一条：multipart 的 Content-Type 永远让 requests（或浏览器）自己生成，代码里不写。

    说明

    提示： 上传功能还需要一个叫 python-multipart 的库，FastAPI 收 multipart 请求全靠它，第 1 章的 requirements.txt 里已经带了它。哪个环境是后来补建的、没装这个库，练习网站启动时会直接报错说明：RuntimeError: Form data requires "python-multipart" to be installed.，照提示 pip install python-multipart 就好。requests 这边不需要任何额外的库。

    上传要有图片文件。不用现找一张，PNG 格式允许小到几十字节：下面这个字节串是一张 1×1 像素的红色图片，一共 69 个字节，用 bytes.fromhex 从十六进制还原：

PNG = bytes.fromhex(
    "89504e470d0a1a0a"
    "0000000d4948445200000001000000010802000000907753de"
    "0000000c49444154789c63f8cfc0000003010100c9fe92ef"
    "0000000049454e44ae426082"
)

    第一行 89504e470d0a1a0a 是所有 PNG 都相同的文件头，最后一块的名字是 IEND（结束）。别小看这 69 个字节：文件头对、各块的校验也对，浏览器能正常把它渲染出来（用 img 标签加载验证过，显示一个红点），测上传完全够用。把「现场构造」养成习惯，工程里就不用提交二进制图片文件，仓库里也不会多出一张说不清用途的图。

    6.1.3 上传的用例¶

    接口约定：jpg 或 png、不超过 200 KB。第 5 章的边界值方法直接套用：类型给一个错的；大小卡在 200 KB 正好和超过 1 字节；再加一条成功路径，上传后用 /api/me 的 hasAvatar 和下载接口回读确认，不只断「上传成功」，还要断数据真的存进去了。tests/api/test_scene_upload.py：

    """文件上传的用例：头像只收 jpg、png，不超过 200 KB。"""
import allure
import pytest

from common.api_client import ok

# 一张 1×1 像素的红色 PNG 图片，一共 69 个字节。四行依次是：文件头、尺寸信息、像素数据、结束标记
PNG = bytes.fromhex(
    "89504e470d0a1a0a"
    "0000000d4948445200000001000000010802000000907753de"
    "0000000c49444154789c63f8cfc0000003010100c9fe92ef"
    "0000000049454e44ae426082"
)
LIMIT = 200 * 1024       # 上限 200 KB，也就是 204800 字节


def png_of_size(size):
    """造一个指定大小的「PNG」：开头 8 个字节是 PNG 的文件头，后面用 0 补齐。只在内存里，不落盘。"""
    return PNG[:8] + b"0" * (size - 8)


@allure.feature("账号")
@allure.title("上传 png 头像成功，hasAvatar 变成 true，下载回来和上传的一样")
def test_upload_avatar(api):
    data = ok(api.upload_avatar(PNG))
    assert data == {"size": 69, "type": "image/png"}
    assert ok(api.me())["hasAvatar"] is True
    resp = api.get_avatar()
    assert resp.status_code == 200
    assert resp.headers["Content-Type"] == "image/png"
    assert resp.content == PNG


@allure.feature("账号")
@allure.title("上传 txt 文件被拒绝，提示只支持 jpg 或 png")
def test_upload_avatar_wrong_type(api):
    body = api.upload_avatar(b"hello", filename="note.txt", content_type="text/plain").json()
    assert body["code"] == 4001
    assert body["msg"] == "头像只支持 jpg 或 png 格式"


SIZE_CASES = [
    ("正好200KB", LIMIT, 0),
    ("超过1个字节", LIMIT + 1, 4002),
]


@allure.feature("账号")
@allure.title("头像大小的边界：{title}")
@pytest.mark.parametrize("title, size, code", SIZE_CASES, ids=[c[0] for c in SIZE_CASES])
def test_upload_avatar_size_limit(api, title, size, code):
    body = api.upload_avatar(png_of_size(size)).json()
    assert body["code"] == code


@allure.feature("账号")
@allure.title("没带文件时返回 422，指出缺的是 file 字段")
def test_upload_avatar_missing_file(api):
    resp = api.request("POST", "/api/users/avatar")
    assert resp.status_code == 422
    assert resp.json()["data"] == [{"field": "file", "reason": "Field required"}]

    （upload_avatar、get_avatar 两个方法加在 common/api_client.py 的 ShopApi 里，一行一个请求，和 pay_order 他们排在一起。）

    两个造数据的细节：

    • 超大文件在内存里拼，不落盘。 png_of_size(size) 造出指定大小的字节串：开头 8 个字节是 PNG 文件头，后面补 0。测试只关心「多大」，不关心「是什么图案」，真去生成一张 200 KB 的图片又慢又没有意义；
    • 内容是假的不影响。 服务端按声明的类型判断、不检查图片内容，所以补 0 的「PNG」照样能传成功。这不是漏洞，是很多系统的现实做法（逐字节验图要花计算），第 6.9 节的练习会让你把这条行为钉成用例。

    6.2 文件下载与导出¶

    6.2.1 二进制响应断什么¶

    下载和上传相反：响应体不再是 JSON，而是文件字节。断言的套路是四查：状态码、Content-Type、Content-Disposition、内容本身。练习网站的订单导出接口 GET /api/orders/export 把当前账号的订单导出成 CSV，先手工看一次（scratch/export_demo.py，脚本里先下一单再导出）：

    (.venv) > python scratch\export_demo.py
刚下的订单： SO20261022000001
状态码： 200
Content-Type： text/csv; charset=utf-8
Content-Disposition： attachment; filename=orders.csv
开头 6 个字节： b'\xef\xbb\xbf\xe8\xae\xa2'
----- 按 utf-8-sig 解码 -----
订单号,商品,金额(元),状态,下单时间
SO20261022000001,中性笔 ×2,5.0,待支付,2026-10-22 16:21:24

    逐个说：

    • Content-Disposition: attachment：attachment 的意思是「让浏览器下载」，filename 是建议的文件名。浏览器看到这个头就自己弹出下载，页面代码一个字都不用管保存的事（orders.html 里就一行 location.href = "/api/orders/export?token=" + getCookie("token")）。断言它，等于断言「这是一个下载接口」；
    • 开头 3 个字节 ef bb bf：UTF-8 的 BOM（字节顺序标记）。Excel 打开 CSV 时靠它认出文件是 UTF-8，没有它，中文列名在 Excel 里就是乱码。服务端特意用 utf-8-sig 编码（sig 就是带 BOM 的意思），测试要验证这一点——你测的不只是「程序能不能解析」，还有「用 Excel 的人能不能用这个文件」；
    • 解码用 utf-8-sig：Python 里 decode("utf-8-sig") 会把开头的 BOM 去掉。用 decode("utf-8") 也能解，但第一列的列名会带着看不见的 BOM 字符，字符串比较永远不相等。实测对比（scratch/bom_demo.py）：
    utf-8     第一列的列名：'﻿订单号'，等于'订单号'吗：False
utf-8-sig 第一列的列名：'订单号'，等于'订单号'吗：True

    6.2.2 导出的用例¶

    内容校验的思路：先下一单（unpaid_order 夹具），导出，用 csv.DictReader 按列名解析，断言刚下的订单号在文件里、各列的值都对。tests/api/test_scene_download.py：

    """文件下载的用例：订单导出成 CSV。"""
import csv
import io

import allure
import pytest


@allure.feature("订单")
@allure.title("导出订单：返回带 BOM 的 CSV 附件，里面有刚下的那一单")
def test_export_orders(api, product, unpaid_order):
    resp = api.export_orders()
    # 1. 状态码和响应头：确认拿到的是一个要下载的 CSV 文件
    assert resp.status_code == 200

    6.3 开放接口与签名¶

    6.3.1 为什么接口要签名¶

    练习网站还有一个不用登录的接口：GET /api/stats/orders，订单统计，文档里写着「开放给合作方的接口」。这类接口叫开放接口（Open API）：公司把部分数据开放给外部合作方调用，合作方拿 appKey（应用标识）和 secret（密钥）来证明身份。没有登录态，就得有别的防伪手段，签名是常见的一种：

    • 证明请求来自持有密钥的人。 把密钥和时间戳拼接后做 md5，得到签名。服务端存有同样的密钥，按同样的规则算一遍，对得上才放行。密钥本身不出现在请求里，看到请求内容的人也伪造不出来；
    • 防止旧请求被重放。 时间戳超出允许范围（前后 300 秒）就拒绝。有人录下一条合法请求，过几分钟原样再发一遍也进不来。

    签名规则是接口文档必须写清楚的部分，本教程演示环境的规则是：

    参数 值 说明
    x_app_key shop-open 合作方身份
    x_timestamp 当前时间戳（秒） 与服务器相差不超过 300 秒
    x_sign md5(密钥 + 时间戳) 演示密钥是 shop-secret-2026

    四种失败各有一个业务码：4011 appKey 不对、4012 时间戳格式不对、4013 时间戳超出范围、4014 签名不正确，HTTP 状态码都是 401。

    6.4 token 过期与自动续期¶

    前面所有用例都是「登录一次，token 一直用到底」。真实系统里 token 通常有有效期：短的十几分钟，长的几个小时。原因很简单，token 一旦被别人拿到，就能冒充你调接口，有效期越短，被偷后能造成的损失越小。

    可有效期太短，用户每隔一会儿就要重新输一次密码，体验很差。常见的折中做法是登录时发两个凭证：

    • token（也叫访问令牌）：调业务接口时带上，有效期短；
    • refreshToken（刷新令牌）：只用来换新的 token，有效期长，平时不往业务接口上带。

    token 过期后，客户端拿 refreshToken 去换一对新的，用户不用重新登录。练习网站的登录接口一直都返回了 refreshToken，只是前面的章节用不到。

    对测试来说，这一节要解决两件事：验证续期这套机制本身对不对，以及让长时间运行的自动化用例不会因为 token 过期而成片失败。

    6.4.3 把续期收进客户端¶

    新建 common/auto_refresh_client.py：

    """带 token 自动续期的接口客户端。

业务请求收到 401、业务码 40102（登录过期）时，自动用 refreshToken 换一对新 token，
再把刚才那个请求重发一次，调用方不用关心续期这件事；refreshToken 也失效时抛出
SessionExpired，让用例失败并提示需要重新登录。

用法（和 ShopApi 一样）：
    api = AutoRefreshApi(base_url)
    api.login("alice", "alice123")
    api.me()          # 就算 token 刚好过期，这里也会自动续期后正常返回
"""
import threading

import requests

from common.api_client import ShopApi


class SessionExpired(Exception):
    """刷新 token 也失效了，只能重新用账号密码登录。"""


class AutoRefreshApi(ShopApi):
    """在 ShopApi 的基础上，给每个请求加上「过期自动续期并重发」。

    续期时要注意并发：refreshToken 是一次性的，两个请求同时发现过期、同时去刷新，
    后到的那个会拿到 40103。这里用一把锁保证同一时刻只有一个线程在刷新，
    其他线程等它刷完，直接用新 token 重发。
    """

    def __init__(self, base_url: str, timeout: float = 10):
        super().__init__(base_url, timeout)
        self.refresh_token = None
        self._refresh_lock = threading.Lock()

    def login(self, username, password):
        resp = super().login(username, password)
        if resp.status_code == 200 and resp.json()["code"] == 0:
            self.refresh_token = resp.json()["data"]["refreshToken"]
        return resp

    def request(self, method: str, path: str, **kwargs) -> requests.Response:
        resp = super().request(method, path, **kwargs)
        if not self._is_expired(resp):
            return resp
        with self._refresh_lock:
            used = resp.request.headers.get("token")
            if self.token == used:            # 别的线程还没刷新过，由这个线程来刷
                self._refresh()
        return super().request(method, path, **kwargs)   # 用新 token 重发一次

    @staticmethod
    def _is_expired(resp: requests.Response) -> bool:
        if resp.status_code != 401:
            return False
        try:
            return resp.json()["code"] == 40102
        except ValueError:
            return False

    def _refresh(self):
        resp = self.session.post(
            f"{self.base_url}/api/token/refresh",
            json={"refreshToken": self.refresh_token},
            timeout=self.timeout,
        )
        body = resp.json()
        if body["code"] != 0:
            raise SessionExpired(f"续期失败（{body['code']} {body['msg']}），请重新登录")
        self.session.headers["token"] = body["data"]["token"]
        self.refresh_token = body["data"]["refreshToken"]

    逐段看：

    • 继承 ShopApi（第 4 章 4.3 节）：所有接口方法（me()、create_order() ……）原样可用，只改两处：login() 多记一个 refreshToken，request() 加上续期逻辑；
    • request() 先正常发请求，只有 HTTP 401 并且业务码是 40102 才进入续期流程。别的错误原样返回，交给用例去断言；
    • _refresh() 续期失败就抛 SessionExpired。这时 refreshToken 也不能用了，继续重试没有意义，直接让用例失败，失败信息里写明原因，比一串 401 好排查得多；
    • 续期成功后只重发一次。重发还失败就原样返回，不会无限重试。

    坑

    把 40101 也当成过期去续期。 40101 说明 token 本身不对，拿 refreshToken 换一对新的，表面上又能用了，却掩盖了真正的问题，比如退出登录接口没让 token 失效。客户端只该为 40102 续期，40101 必须暴露出来。

    6.4.4 并发时只续期一次¶

    request() 里那把锁是为并发准备的。设想 5 个线程共用一个客户端，同时发现 token 过期：

    时刻 不加锁 加锁并比对 token
    1 5 个线程同时拿着同一个 refreshToken 去换 线程 A 拿到锁，换到新 token；其他 4 个排队
    2 只有第一个成功，其余 4 个拿到 40103，全部失败 线程 B 拿到锁，发现客户端的 token 已经和自己发请求时带的不一样，说明有人换过了，直接用新 token 重发
    3 — C、D、E 同 B，5 个请求全部成功

    判断「有没有人换过」靠的就是这两行：

    used = resp.request.headers.get("token")   # 这个请求发出去时带的 token
if self.token == used:                     # 客户端当前的 token 还是它，说明还没人换过
    self._refresh()

    resp.request 是 requests 留在响应对象上的「这个响应对应的请求」，从它的请求头里能取到发请求那一刻用的 token。

    不用客户端、直接用脚本也能验证服务端的一次性：三个线程同时拿同一个 refreshToken 去换（scratch/race_demo.py，网站开着 SHOP_TOKEN_TTL=2），结果只有一个成功：

    (.venv) > python scratch\race_demo.py
线程 0：code=0，成功
线程 1：code=40103，刷新 token 无效
线程 2：code=40103，刷新 token 无效

    说明

    单线程跑用例时用不到这把锁。但压测脚本、并发测试都会让多个线程共用账号，到时候就用得上。

    6.5.1 为什么会有异步接口¶

    库存报表要扫全站 25 件商品再生成文件，真实系统里的统计、导出、批量处理动辄要跑几秒到几分钟，HTTP 请求等不了这么久（网关超时一般 30 秒，浏览器更短）。所以做成异步：提交接口马上返回一个任务编号，活由后台慢慢干，客户端拿着编号轮询（polling，隔一会儿查一次）状态，跑完了再下载结果。

    6.5.2 轮询代码的正确写法¶

    轮询最容易写出没有出口的循环：while True 里只查状态、看到 completed 才 break，任务万一永远不完成（后台线程异常退出、服务重启把任务丢了），脚本就卡在那里占一个进程。正确的写法有三个要素，收在 common/api_client.py 的 wait_task 方法里（配套还有 create_stock_report、get_task、download_task 三个一行方法）：

        def wait_task(self, task_id, timeout=10, interval=0.5):
        """每隔 interval 秒查一次任务，跑完就返回任务信息；超过 timeout 秒还没跑完就报错。"""
        deadline = time.monotonic() + timeout
        while time.monotonic() < deadline:
            task = ok(self.get_task(task_id))
            if task["status"] == "completed":
                return task
            assert task["status"] == "processing", f"任务出现了意料之外的状态：{task}"
            time.sleep(interval)
        raise TimeoutError(f"任务 {task_id} 等了 {timeout} 秒还没跑完")
    要素 在代码里 为什么
    截止时间 time.monotonic() + timeout 循环条件用它卡住，超时抛 TimeoutError，报错信息带着任务号，一眼看出是等超了而不是接口坏了
    间隔 time.sleep(interval) 别查得太勤，0.5 秒一次对 3 秒的任务足够
    中间状态断言 assert task["status"] == "processing" 只认 processing 和 completed 两种状态；哪天服务端加了个 failed 状态，这条断言当场把它指出来，而不是无声地轮询到超时

    time.monotonic() 和 time.time() 的区别：monotonic 是单调时钟，只前进、不受系统对时影响，算「过了多久」用它；算「现在几点」才用 time()。

    超时的报错长这样（故意把 timeout 设成 1 秒，任务要跑 3 秒）：

    E       TimeoutError: 任务 TASK000002 等了 1 秒还没跑完

    6.6 越权测试：用 A 的身份动 B 的数据¶

    6.6.1 概念与候选清单¶

    第 5 章 5.5.2 测过数据隔离：bob 查 alice 的订单，返回 3001。那一节是订单域的一个点，这一节把这类测试正式化。水平越权指用户能访问到同等权限的其他用户的数据：A 用自己的合法 token，操作 B 的资源。安全行业给它起了个名字叫 IDOR（Insecure Direct Object Reference，不安全的直接对象引用）。和它相对的垂直越权是普通用户干管理员的事，本教程不展开。

    越权是资损和安全类缺陷的重灾区：改别人的收货地址、看他人的订单、把退款改到自己的账户，全落在「路径或参数里带编号」的接口上。测法就一句口诀：把路径里的编号换成别人的，用自己的 token，看系统拦不拦。

    练习网站收货地址一族的接口：

    方法 地址 动作
    POST /api/addresses 新增（请求里没有编号，天然没有越权问题）
    GET /api/addresses 我的地址列表（服务端只返回自己的）
    GET /api/addresses/{id} 地址详情
    PUT /api/addresses/{id} 修改
    DELETE /api/addresses/{id} 删除

    带 {id} 的三个就是越权候选。先手工探一遍（scratch/idor_demo.py）：bob 建一个地址，alice 拿自己的 token 去查、改、删这个编号：

@pytest.mark.parametrize("action, method, path, body", ID_APIS, ids=[c[0] for c in ID_APIS])
def test_cannot_touch_others_address(api, bob, bob_address, action, method, path, body):
    resp = api.request(method, path.format(id=bob_address["id"]), json=body)
    assert resp.json()["code"] == 5001, f"{action}别人的地址成功了，存在越权：{resp.json()}"
    # 只看返回码还不够，再回到 bob 那边确认地址原封不动
    assert ok(bob.get_address(bob_address["id"])) == bob_address


@allure.feature("收货地址")
@allure.title("别人的地址和不存在的地址，返回一模一样")
def test_others_address_looks_like_missing(api, bob_address):
    others = api.get_address(bob_address["id"]).json()
    missing = api.get_address(999999).json()
    assert others == missing

    用例的设计有三个要点：

    • 路径里带编号的接口一个不漏。 ID_APIS 把 GET、PUT、DELETE 全列进去，参数化成三条。以后地址族再加接口（比如「设为默认地址」），往列表里加一行就行；
    • 断返回码，还要回查数据。 只断 5001 不够——万一服务端拦下了返回、却偷偷把数据改了呢。第二条断言用 bob 自己再查一次，比对整个地址原封不动；
    • 对照用例。 最后一条断言「别人的地址」和「不存在的地址」返回一模一样，这正是 5001 设计意图的完整验证。

    6.8 常见的坑¶

    现象 原因与解决
    上传报 400：Missing boundary in multipart 手工设了 Content-Type: multipart/form-data，把 requests 自动生成的边界线覆盖掉了。删掉这个头，把文件交给 files=
    上传报 4001，文件明明是 png 类型是 files= 元组第三项声明的，requests 不看内容也不猜格式。三项写全：(文件名, 内容, "image/png")
    签名死活对不上，代码看不出毛病 三个常见错：时间戳用了毫秒（13 位）；忘了 hexdigest()，把 md5 对象拼进了字符串；大小写和文档不一致。hexdigest() 返回小写，按文档原样传
    轮询脚本卡住不动 while True 没写截止时间，任务永远不完成就永远等。按 6.5.2 的三要素改：截止时间、间隔、中间状态断言
    续期用例全部 SKIPPED 练习网站没开 SHOP_TOKEN_TTL=2，探测夹具让整个文件跳过了。加 -rs 看原因，带开关重启网站再跑（6.4.5）
    多线程共用一个客户端，偶尔一批请求报 40103 续期没加锁，几个线程拿同一个一次性 refreshToken 去换，只有第一个成功。参考 6.4.4 加锁并比对 token
    做完实验，后面的用例成片失败 SHOP_TOKEN_TTL 或 SHOP_IDOR_BUG 的窗口忘了去掉：前者让共享登录态的用例全部报「登录已过期」（实测全量用例 12 条失败、2 条报错），后者让越权以外的地址用例也被改乱。Remove-Item Env:变量名 去掉，重启练习网站
    导出的 CSV 用 Excel 打开是乱码 服务端没带 BOM。用例里断言 resp.content 前三个字节是 \xef\xbb\xbf（6.2.1），把这个约定钉进用例，让开发去修
    想测「上传超大文件」，真造了个 1 GB 的文件 没必要：内存里拼字节串（png_of_size），大小精准可控，边界测到 200 KB 加 1 字节就够。真要验证服务端处理大文件的表现，再考虑真实文件
    refreshToken 随手写在代码或日志里 它等于一份长期有效的登录凭证。真实项目从环境变量或配置中心取；日志和报告里要遮蔽——第 4 章的 mask() 在本章把 refreshToken 也列进了遮蔽名单，查询参数里带的 token（6.2 节的下载链接）也一并遮蔽，Allure 附件里看到的已经是 ***

    6.9 练习¶

    1. 上传接口对类型的判断只看声明、不看内容：拿 6.1.2 的 PNG 字节串、类型声明成 image/jpeg 传上去，观察返回；再写一条用例把这个行为钉住。想想这条用例的价值：哪天开发改成逐字节验图，这条用例会第一个知道。
    2. 6.4.2 的三条用例没有覆盖两个行为：刷新换到新 token 之后，旧 token 还能不能用？退出登录之后，refreshToken 还能不能用来换新？先实测确认练习网站的行为，再各补一条用例钉住；想想这些行为安全吗，要不要在报告里提一句。
    3. 用 SHOP_TASK_LATENCY=0.5 启动网站，把 wait_task 的 interval 改成 2 秒，跑 test_stock_report，数一数它发了几次查询才等到 completed；再回答：如果任务要跑 30 秒、interval 2 秒，一共发多少次查询？timeout 该设多大？
    4. 把签名的时间戳换成一小时前的值、签名按那个时间戳认真算，调 /api/stats/orders，观察返回的业务码；再故意只换时间戳、不换签名，看业务码变成什么。用两次结果解释「签名和时间戳必须一起换」。
    5. 思考题：6.4.4 的竞态里，第二个用旧 refreshToken 的线程拿到 40103。如果那个线程是一个手机 App，它的用户会遇到什么？如果你是服务端开发，你会怎么让这种用户无感恢复？（提示：查一下「刷新令牌轮换」和宽限期这两个词。）

    6.10 自检清单¶

    • 能画出 multipart 请求体的结构，说得出 boundary 是干什么的、为什么不能手工设 Content-Type；
    • 拿到一个二进制响应，知道查哪四样：状态码、Content-Type、Content-Disposition、内容（含编码）；
    • 能说出签名防什么、时间戳防什么，知道秒和毫秒怎么区分、传错了会返回哪个业务码；
    • 能说出 40101、40102、40103 分别意味着什么、客户端各自该怎么处理，说清 refreshToken 为什么是一次性的；
    • 能解释自动续期客户端里为什么要加锁、锁里为什么要比对 token；
    • 会写带截止时间和状态断言的轮询，说得出 time.monotonic() 和 time.time() 的区别；
    • 能列出一个功能族里的越权候选接口，会设计对照组用例，知道为什么「地址不存在」的提示是故意的；
    • 面对一个没见过的接口场景，能按 6.7 的五步走完从手工调试到用例落地的全过程。
