    第 4 章 接口自动化进阶¶

    本章目标

    • 把重复的代码收进接口客户端，用例里只写业务；
    • 用配置文件管理地址和账号，同一套用例能跑多个环境；
    • 写出覆盖完整业务流程的用例，学会管理测试数据；
    • 用 JSON Schema 校验返回结构；
    • 加上日志，生成 Allure 图文报告；
    • 了解 Mock 和数据库断言。

    这一章结束时，你的接口自动化就是一个像样的小框架了。

    4.1 第 3 章的代码有什么问题¶

    回头看第 3 章写的用例，能挑出不少毛病：

    • BASE = "http://127.0.0.1:8000" 在好几个文件里各写了一遍，换个环境要改好几处；
    • 每个请求都要写 headers={"token": token}、timeout=10；
    • 接口地址散落在各条用例里，开发改一个地址，你要满工程找；
    • 账号密码写死在代码里；
    • 请求发了什么、回了什么，失败时只能靠猜。

    这些问题用例少的时候不明显，几百条用例时就是灾难。解决办法是分层。

    4.2 分层¶

    用例层   tests/                    只写业务步骤和断言：登录、下单、支付，检查结果
  │
业务层   ShopApi                   一个方法对应一个接口：api.login()、api.pay_order()
  │
基础层   ApiClient                 发请求的公共逻辑：拼地址、带 token、超时、日志、报告附件
  │
配置层   config/*.yaml + config.py 地址、账号、超时，按环境切换

    每一层只管自己的事：

    • 接口地址变了，只改业务层的一个方法；
    • 想给所有请求加日志，只改基础层；
    • 换测试环境，只换配置文件；
    • 用例层读起来像测试步骤，不懂代码的人也能看懂在测什么。

    4.3 接口客户端¶

    新建 common 文件夹，在里面新建一个空文件 __init__.py（有了它，Python 才把这个文件夹当成可以导入的包），再新建 common/api_client.py：

    """接口客户端。

每个请求都要做的事收在这里：拼完整地址、带上登录 token、设置超时、记日志、
把请求和响应挂进 Allure 报告。用例里只写业务，比如 api.login(...)、api.create_order(...)。
"""
import json
import logging
import time

import requests

try:
    import allure
except ImportError:  # 没装 allure-pytest 也能用，只是报告里没有附件
    allure = None

log = logging.getLogger("api")
SECRET_KEYS = {"password", "token"}


def mask(data):
    """把口令、token 换成 ***，日志和报告里就不会泄露。"""
    if isinstance(data, dict):
        return {k: "***" if k.lower() in SECRET_KEYS else mask(v) for k, v in data.items()}
    if isinstance(data, list):
        return [mask(v) for v in data]
    return data


class ApiClient:
    """通用的 HTTP 客户端，和具体业务无关，换个项目也能直接用。"""

    def __init__(self, base_url: str, timeout: float = 10):
        self.base_url = base_url.rstrip("/")
        self.timeout = timeout
        self.session = requests.Session()  # 复用连接，也方便统一设置请求头

    def request(self, method: str, path: str, **kwargs) -> requests.Response:
        kwargs.setdefault("timeout", self.timeout)
        url = self.base_url + path
        start = time.perf_counter()
        resp = self.session.request(method, url, **kwargs)
        cost_ms = (time.perf_counter() - start) * 1000
        log.info("%s %s -> HTTP %s，耗时 %.0f 毫秒", method, path, resp.status_code, cost_ms)
        self._attach(method, url, kwargs, resp, cost_ms)
        return resp

    @staticmethod
    def _attach(method, url, kwargs, resp, cost_ms):
        if allure is None:
            return
        try:
            body = mask(resp.json())
        except ValueError:
            body = resp.text[:2000]
        detail = {
            "请求": {"方法": method, "地址": url, "查询参数": kwargs.get("params"), "请求体": mask(kwargs.get("json"))},
            "响应": {"状态码": resp.status_code, "耗时毫秒": round(cost_ms), "响应体": body},
        }
        allure.attach(
            json.dumps(detail, ensure_ascii=False, indent=2),
            name=f"{method} {url}",
            attachment_type=allure.attachment_type.JSON,
        )


class ShopApi(ApiClient):
    """迷你商城的接口，一个方法对应一个接口。"""

    def __init__(self, base_url: str, timeout: float = 10):
        super().__init__(base_url, timeout)
        self.username = None

    @property
    def token(self):
        return self.session.headers.get("token")

    def login(self, username, password):
        resp = self.request("POST", "/api/login", json={"username": username, "password": password})
        if resp.status_code == 200 and resp.json()["code"] == 0:
            self.session.headers["token"] = resp.json()["data"]["token"]  # 之后的请求自动带上
            self.username = username
        return resp

    def logout(self):
        return self.request("POST", "/api/logout")

    def me(self):
        return self.request("GET", "/api/me")

    def search_products(self, keyword="", page=1, size=10):
        return self.request("GET", "/api/products", params={"keyword": keyword, "page": page, "size": size})

    def get_product(self, product_id):
        return self.request("GET", f"/api/products/{product_id}")

    def create_order(self, items):
        return self.request("POST", "/api/orders", json={"items": items})

    def list_orders(self, status=None):
        return self.request("GET", "/api/orders", params={"status": status} if status else None)

    def get_order(self, order_no):
        return self.request("GET", f"/api/orders/{order_no}")

    def pay_order(self, order_no):
        return self.request("POST", f"/api/orders/{order_no}/pay")

    def cancel_order(self, order_no):
        return self.request("POST", f"/api/orders/{order_no}/cancel")


def ok(resp: requests.Response):
    """断言接口调用成功（HTTP 200 且业务码为 0），返回 data 部分。"""
    assert resp.status_code == 200, f"HTTP 状态码是 {resp.status_code}，响应：{resp.text[:300]}"
    body = resp.json()
    assert body["code"] == 0, f"业务失败：code={body['code']}，msg={body['msg']}"
    return body["data"]

    几个设计要点：

    要点 说明
    requests.Session() 会话对象会复用网络连接，比每次 requests.get 快；登录后把 token 放进 session.headers，之后所有请求自动带上
    ApiClient 和 ShopApi 分开 ApiClient 和业务无关，换个项目直接拿走；ShopApi 继承它，只写这个系统的接口
    方法返回原始的 Response 用例想断什么都可以：正常用例用 ok() 取数据，异常用例自己断状态码和业务码
    ok() 帮手函数 「HTTP 200 且业务码为 0」这个判断几乎每条用例都要，收成一个函数，失败时还会说清楚是哪一层失败
    留着 request() 可以直接调 「请求体缺字段」「参数类型不对」这种异常用例，业务方法发不出来，用 api.request(...) 直接发原始请求
    mask() 遮掉敏感信息 日志和报告会被很多人看到，口令和 token 不能明文出现

    改造前后对比一下同一条用例：

    # 改造前（第 3 章）
def test_pay_order(base_url, token, unpaid_order):
    headers = {"token": token}
    before = requests.get(f"{base_url}/api/me", headers=headers, timeout=10).json()["data"]["balance"]
    resp = requests.post(f"{base_url}/api/orders/{unpaid_order['orderNo']}/pay", headers=headers, timeout=10)
    assert resp.json()["code"] == 0
    after = requests.get(f"{base_url}/api/me", headers=headers, timeout=10).json()["data"]["balance"]
    assert after == pytest.approx(before - unpaid_order["amount"])


# 改造后
def test_pay_order(api, unpaid_order):
    balance_before = ok(api.me())["balance"]
    data = ok(api.pay_order(unpaid_order["orderNo"]))
    assert data["status"] == "PAID"
    assert data["balance"] == pytest.approx(balance_before - unpaid_order["amount"])

    4.4 配置文件与多环境¶

    真实工作中至少有两三套环境：开发环境、测试环境、预发布环境。同一套用例要能在不同环境跑，地址和账号就不能写在代码里。

    4.4.1 配置文件¶

    新建 config/local.yaml，放本机练习网站的配置：

    # 本机练习网站（迷你商城）的配置
base_url: http://127.0.0.1:8000
timeout: 10              # 接口超时时间，单位秒

accounts:
  main:  {username: alice, password: alice123}   # 用例默认用的账号
  login: {username: bob, password: bob123}       # 登录类用例专用，会被反复登录
  pool:  {prefix: user, password: test123}       # 账号池 user001～user100，并行执行和压测用

    {username: alice, password: alice123} 是 YAML 里字典的单行写法，和分行写是一样的。

    4.4.2 读配置¶

    新建 common/config.py：

    """读取测试配置。

配置文件放在 config/<环境名>.yaml，环境名取环境变量 TEST_ENV，没设置就用 local。
文件里可以写 ${变量名}，读取时换成同名环境变量的值，口令这类敏感信息就不用写进文件。
"""
import os
import re
from functools import cache
from pathlib import Path

import yaml

ROOT = Path(__file__).resolve().parent.parent
_VAR = re.compile(r"\$\{(\w+)\}")


def _fill_env(text: str) -> str:
    def replace(match):
        name = match.group(1)
        if name not in os.environ:
            raise RuntimeError(f"配置里用到了环境变量 {name}，但它没有设置")
        return os.environ[name]

    return _VAR.sub(replace, text)


@cache
def load_config(env: str | None = None) -> dict:
    env = env or os.getenv("TEST_ENV", "local")
    path = ROOT / "config" / f"{env}.yaml"
    if not path.exists():
        raise FileNotFoundError(f"找不到配置文件 {path}，检查 TEST_ENV={env} 写对没有")
    cfg = yaml.safe_load(_fill_env(path.read_text(encoding="utf-8")))
    cfg["env"] = env
    return cfg

    @cache 让同样的参数只真正读一次文件，之后直接返回上次的结果。

    4.4.3 切换环境¶

    假设还有一套测试环境，新建 config/staging.yaml，口令写成 ${变量名}：

    base_url: https://shop-staging.example.com
timeout: 15

accounts:
  main:  {username: autotest01, password: "${MAIN_PASSWORD}"}
  login: {username: autotest02, password: "${LOGIN_PASSWORD}"}
  pool:  {prefix: autotest-pool-, password: "${POOL_PASSWORD}"}

    运行前用环境变量选环境、给口令（PowerShell 的写法，只对当前窗口有效）。文件里用到了三个口令变量，三个都要设：

    (.venv) > $env:TEST_ENV = "staging"
(.venv) > $env:MAIN_PASSWORD = "真实口令1"
(.venv) > $env:LOGIN_PASSWORD = "真实口令2"
(.venv) > $env:POOL_PASSWORD = "真实口令3"
(.venv) > pytest

    Mac / Linux 写成 export TEST_ENV=staging。只设了 TEST_ENV、一个口令都没设时，会直接报出第一个缺的变量，不会带着错误的口令去跑：

    RuntimeError: 配置里用到了环境变量 MAIN_PASSWORD，但它没有设置

    环境名写错也会说清楚：

    FileNotFoundError: 找不到配置文件 D:\work\autotest-demo\config\prod.yaml，检查 TEST_ENV=prod 写对没有

    练习网站没有 staging 环境，这一节看懂就行。如果你在命令行里试过上面的命令，一定要把这些变量去掉，否则之后在这个窗口里跑的用例都会去连那个不存在的地址：

    (.venv) > Remove-Item Env:TEST_ENV, Env:MAIN_PASSWORD, Env:LOGIN_PASSWORD, Env:POOL_PASSWORD

    也可以直接关掉这个窗口重开一个。

    口令永远不要写进代码和配置文件。 代码会上传到代码仓库，所有能看到仓库的人都能看到口令。第 19 章讲 Git 时会把 config/staging.yaml 加进忽略清单，参考代码里只放一份不带真实信息的样板 config/staging.yaml.example。

    4.5 重写夹具¶

    把 tests/conftest.py 整个换成下面的内容：

    """全局夹具（fixture）：配置、账号、接口客户端、测试数据。tests 下所有用例都能直接用。"""
import pytest

from common.api_client import ShopApi, ok
from common.config import load_config


@pytest.fixture(scope="session")
def config():
    return load_config()


@pytest.fixture(scope="session")
def base_url(config):

@pytest.fixture(scope="session")
def account(config):
    """本轮测试用的账号。（第 19 章并行执行时会改这里）"""

@pytest.fixture(scope="session")
def api(config, account):
    """已登录的接口客户端。整轮测试只登录一次，所有用例共用。"""
    client = ShopApi(config["base_url"], timeout=config["timeout"])
    ok(client.login(account["username"], account["password"]))
    return client


@pytest.fixture
def guest(config):
    """没登录的接口客户端，每条用例一个新的。"""
    return ShopApi(config["base_url"], timeout=config["timeout"])


@pytest.fixture
def product(api):
    """一个便宜、库存充足的商品，下单类用例都用它。"""
    items = ok(api.search_products(keyword="中性笔"))["items"]
    assert items, "练习网站里应该有「中性笔」这个商品"
    return items[0]


@pytest.fixture
def unpaid_order(api, product):
    """准备一张待支付订单；用例结束后它要是还没支付，就取消掉，把库存还回去。"""
    order = ok(api.create_order([{"productId": product["id"], "quantity": 1}]))
    yield order
    if ok(api.get_order(order["orderNo"]))["status"] == "UNPAID":
        ok(api.cancel_order(order["orderNo"]))

    和第 3 章比，有三处改进：

    • product 按名称搜出商品，不再写死 13 号。换个环境商品编号不同，用例照样能跑；
    • unpaid_order 的清理会先看订单状态，只有还没支付才取消，并且用 ok() 检查取消成功了；
    • 账号从配置里取，换环境不用改代码。

    然后在 pytest.ini 里加一行 pythonpath：

    [pytest]
testpaths = tests
# 把工程根目录加进导入路径，用例里才能 from common.xxx import ...
pythonpath = .
addopts = -ra
# 用例标记要先在这里登记，用法第 7 章讲
markers =
    smoke: 冒烟用例，每次改动后最先跑的那一小批
    concurrency: 并发类用例
disable_test_id_escaping_and_forfeit_all_rights_to_community_support = true

    不加这一行，运行 pytest 会报：

    ImportError while loading conftest 'D:\work\autotest-demo\tests\conftest.py'.
E   ModuleNotFoundError: No module named 'common'

    原因是 pytest 默认只把用例所在的文件夹加进导入路径，找不到工程根目录下的 common。（用 python -m pytest 运行不报错，因为这种方式会把当前文件夹也加进去，但别依赖这个区别。）

    第 3 章写的 tests/api/test_login_fail.py 和 tests/api/test_order.py 要删掉：新的 conftest.py 里已经没有 token 夹具了，留着 test_order.py 会报 fixture 'token' not found；test_login_fail.py 的内容下面会用新写法并进 test_login.py，留着就重复了。订单相关的用例会重写到新文件 test_order_flow.py 里。

    4.6 重写用例¶

    4.6.1 登录¶

    tests/api/test_login.py：

    """登录接口的用例。"""
from pathlib import Path

import allure
import pytest
import yaml

from common.api_client import ShopApi, ok

CASES = yaml.safe_load((Path(__file__).parents[2] / "data" / "login_cases.yaml").read_text(encoding="utf-8"))


@allure.feature("账号")
@allure.title("正确的用户名和密码可以登录")
@pytest.mark.smoke
def test_login_success(guest, config):
    acc = config["accounts"]["login"]
    data = ok(guest.login(acc["username"], acc["password"]))
    assert data["username"] == acc["username"]
    assert len(data["token"]) == 32


@allure.feature("账号")
@pytest.mark.parametrize("case", CASES, ids=[c["title"] for c in CASES])
def test_login_fail(guest, case):
    allure.dynamic.title(f"登录失败：{case['title']}")
    resp = guest.login(case["username"], case["password"])
    assert resp.status_code == 200
    body = resp.json()
    assert body["code"] == case["code"]
    assert body["msg"] == case["msg"]
    assert body["data"] is None


@allure.feature("账号")
@allure.title("请求体缺少密码字段时返回参数错误")
def test_login_missing_field(guest):
    resp = guest.request("POST", "/api/login", json={"username": "bob"})
    assert resp.status_code == 422
    assert resp.json()["data"] == [{"field": "password", "reason": "Field required"}]


@allure.feature("账号")
@allure.title("不带 token 访问需要登录的接口返回 401")
def test_requires_token(guest):
    resp = guest.me()
    assert resp.status_code == 401
    assert resp.json()["code"] == 40101    # 业务码区分：40101 是没登录，40102 是登录过期


@allure.feature("账号")
@allure.title("退出登录后原来的 token 失效")
def test_logout_invalidates_token(config):
    acc = config["accounts"]["login"]
    client = ShopApi(config["base_url"])
    ok(client.login(acc["username"], acc["password"]))
    ok(client.logout())
    assert client.me().status_code == 401

    @allure 开头的几行是给测试报告用的，4.11 节讲；@pytest.mark.smoke 是给用例打标记，第 7 章讲。先照抄。

    注意 test_logout_invalidates_token 没用共享的 api 夹具，而是自己新建了一个客户端：它会让 token 失效，要是用了共享的那个，后面所有用例都会变成「未登录」。会破坏共享状态的用例，自己准备一份专用的数据。

    4.7 接口串联：完整的购买流程¶

    单个接口测完了，还要测业务流程：前一个接口的输出是后一个接口的输入，这叫接口串联（也叫接口关联）。tests/api/test_order_flow.py 里的第一条用例：

    @allure.feature("订单")
@allure.title("完整购买流程：下单、支付，余额和库存都对得上")
@pytest.mark.smoke
def test_purchase_flow(api, product):
    with allure.step("记下余额和库存"):
        balance_before = ok(api.me())["balance"]
        stock_before = ok(api.get_product(product["id"]))["stock"]
    with allure.step("下单 3 件"):
        order = ok(api.create_order([{"productId": product["id"], "quantity": 3}]))
        assert order["status"] == "UNPAID"
        assert order["amount"] == pytest.approx(product["price"] * 3)
        assert ok(api.get_product(product["id"]))["stock"] == stock_before - 3
    with allure.step("支付"):
        paid = ok(api.pay_order(order["orderNo"]))
        assert paid["status"] == "PAID"
    with allure.step("核对订单状态和余额"):
        detail = ok(api.get_order(order["orderNo"]))
        assert detail["status"] == "PAID"
        assert detail["paidAt"] is not None
        assert ok(api.me())["balance"] == pytest.approx(balance_before - order["amount"])

    要点：

    • 从响应里取值往下传：product 夹具搜出来的商品编号传给下单，下单返回的订单号、金额传给支付和后面的核对；
    • 每一步都断言，出了问题能马上知道断在哪一步，而不是最后才发现余额不对；
    • 检查业务结果：除了每个接口返回成功，还要核对「库存少了 3」「余额少了订单金额」这些业务上必须成立的规则；
    • with allure.step("...") 把用例分成几个步骤，报告里会一步步展开显示。

    同一个文件里的其他用例覆盖了各种异常情况，这里列出标题，完整代码见参考代码：

    用例 检查什么
    下单数量超过库存时返回库存不足，库存不变 「限量版手办」只有 3 个，买库存加 1 个，返回 2002，库存没被扣
    下单参数非法时返回 422 商品列表为空、数量为 0、数量超过 999
    支付成功后订单变为已支付，余额扣减订单金额 正常支付
    同一订单重复支付会被拒绝，只扣一次钱 第二次支付返回 3003，余额只少了一次
    余额不足时支付失败，订单还是待支付 买够超过余额的显示器，支付返回 3002，余额没变
    取消订单后库存归还，订单不能再支付 取消后库存恢复，再支付返回 3003
    看不到别人的订单 用 bob 查 alice 的订单，返回 3001

    4.8 测试数据管理¶

    接口自动化做不好，一大半原因出在测试数据上：今天能跑明天不能跑，单独跑能过一起跑就挂，换个环境全红。几条原则：

    1. 自己造，自己清。 用例需要的数据用夹具现造，用完清理（yield 后面的代码，或者 try/finally）。比如「余额不足」那条用例下了一个金额很大的订单，不管断言过没过，finally 里都会把它取消，把占用的库存还回去：
    order = ok(api.create_order([{"productId": monitor["id"], "quantity": quantity}]))
try:
    body = api.pay_order(order["orderNo"]).json()
    assert body["code"] == 3002
    ...
finally:
    ok(api.cancel_order(order["orderNo"]))   # 不管断言过没过，都把占用的库存还回去
    1. 断言变化量，不断言绝对值。 余额会被别的用例改动，所以不要断言「余额等于 99997.5」，要断言「余额比支付前少了订单金额」。
    2. 不依赖执行顺序。 任何一条用例都能单独运行，也能和别的用例以任意顺序一起运行。
    3. 按特征找数据，别写死编号。 用名称搜出商品，比写死 13 号商品更能适应不同环境。
    4. 稀缺的数据别消耗掉。 「限量版手办」只有 3 个库存，测库存不足时下单数量是「当前库存加 1」，下单必然失败，库存不会被消耗，跑多少次都行。
    5. 会破坏共享状态的操作，用专用数据。 退出登录会让 token 失效，那条用例就自己登录一个专用账号。
    6. 共享环境里不要清库、不要改别人的数据。 测试环境往往是多人共用的，用专门的测试账号，只动自己造的数据。

    4.9 结构校验：JSON Schema¶

    前端和其他系统依赖接口返回的结构：字段名、字段类型、哪些必有。开发改接口时不小心把 price 从数字改成了字符串，功能用例未必能发现，页面却可能显示出错。JSON Schema 是一种描述 JSON 结构的标准写法，可以一次把结构检查到位。

    新建 data/product_schema.json，描述商品详情的结构：

    {
  "type": "object",
  "required": ["id", "sku", "name", "price", "stock"],
  "additionalProperties": false,
  "properties": {
    "id": {"type": "integer", "minimum": 1},
    "sku": {"type": "string", "pattern": "^SKU\\d{4}$"},
    "name": {"type": "string", "minLength": 1},
    "price": {"type": "number", "exclusiveMinimum": 0},
    "stock": {"type": "integer", "minimum": 0}
  }
}

    意思是：这是一个对象，五个字段都必须有，不允许出现别的字段；id 是大于等于 1 的整数，sku 是 SKU 加 4 位数字，price 是大于 0 的数字，依此类推。

    在 tests/api/test_products.py 里读入这个文件，用例里一行就能校验：

    import json
from pathlib import Path

from jsonschema import validate

from common.api_client import ok

PRODUCT_SCHEMA = json.loads((Path(__file__).parents[2] / "data" / "product_schema.json").read_text(encoding="utf-8"))


def test_product_detail_schema(guest):
    data = ok(guest.get_product(1))
    validate(instance=data, schema=PRODUCT_SCHEMA)  # 字段缺了、多了、类型不对都会报错

    结构不对时的报错很直观：

    '199.00' is not of type 'number'                                  # price 变成了字符串
'stock' is a required property                                    # 少了 stock 字段
Additional properties are not allowed ('color' was unexpected)    # 多了一个没约定的字段

    是否允许多出字段（additionalProperties）看团队约定：设成 false 很严格，接口加字段也会让用例失败，好处是任何结构变化都逃不过；很多团队只要求必有字段齐全、类型正确，不限制新增字段。

    4.10 日志¶

    ApiClient.request 里每发一个请求都会记一行日志。在 pytest.ini 里加上日志的配置：

log_level = INFO

    4.11 Allure 测试报告¶

    命令行里的输出适合自己看，给别人看需要一份图文报告。Allure 是用得最多的测试报告工具，能展示每条用例的步骤、请求和响应、截图、耗时、通过率。

    4.11.1 安装¶

    Allure 分两部分：

    • allure-pytest：pytest 插件，运行用例时把结果记成一堆数据文件。第 1 章已经装好了；

    • Allure 命令行：把这些数据文件生成网页报告。Allure 3 是用 Node.js 写的，需要先装 Node.js。

    • 到 https://nodejs.org/ 下载 LTS（长期支持） 版本安装，装完新开一个命令行窗口检查（在 VS Code 里用终端的，要把 VS Code 整个关掉重开，见第 1 章 1.2 节）：

    > node --version
v24.15.0
    1. 安装 Allure 命令行：
    > npm install -g allure
> allure --version
3.21.0

    下载慢可以先执行 npm config set registry https://registry.npmmirror.com 换成国内镜像。

    说明

    网上很多旧教程让你装 allure-commandline，那是需要 Java 的 Allure 2，命令和这里不一样。本教程用的是 Allure 3，包名就叫 allure。

    4.11.2 报告配置¶

    在工程根目录新建 allurerc.yaml：

    # Allure 3 报告配置（allure generate 会自动读取工程根目录下的这个文件）
name: 迷你商城自动化测试报告
output: reports/allure-report
plugins:
  awesome:
    options:
      reportLanguage: zh   # 报告界面用中文
      singleFile: true     # 生成单个 HTML 文件，双击就能打开，方便发给别人
      layout: split        # 左边用例树、右边详情的分栏布局

    4.11.3 生成报告¶

    (.venv) > pytest --alluredir=reports/allure-results --clean-alluredir
(.venv) > allure generate reports/allure-results
    • --alluredir 指定结果数据存哪；--clean-alluredir 先清掉上一次的数据，否则新旧结果会混在一起；
    • allure generate 读取 allurerc.yaml，在 reports/allure-report/ 下生成 index.html。它成功时什么都不打印，没报错就是成功了，去目录里找文件就行；
    • 双击 index.html 就能打开。不想生成单文件的话，把配置里的 singleFile 改成 false，再用 allure open reports/allure-report 打开（多文件的报告直接双击打不开）。

    4.11.4 报告里有什么¶

    • 首页：总用例数、通过和失败的数量、通过率圆环；
    • 用例树：按目录和文件分组。点开一条用例，能看到标题、耗时、失败原因、每个 allure.step 步骤；
    • 附件：ApiClient 给每个请求都挂了一个附件，点开能看到这次请求的地址、参数、请求体和响应体（token 和口令已经遮掉了）。用例失败时，不用重跑就能看到当时接口返回了什么；
    • 筛选：可以按状态、标签（比如 feature）筛选用例。

    4.11.5 常用的 Allure 写法¶

    写法 作用
    @allure.feature("订单") 功能模块，报告里可以按它筛选
    @allure.story("支付") 模块下的子功能
    @allure.title("同一订单重复支付会被拒绝") 用例在报告里显示的标题，不写就显示函数名
    @allure.title("……：{title}") 标题里引用用例的参数，参数化用例常用
    allure.dynamic.title(...) 在用例运行时再决定标题
    with allure.step("下单"): 把用例分成步骤
    allure.attach(内容, name=..., attachment_type=...) 挂附件：文字、JSON、截图都行
    @allure.severity(allure.severity_level.CRITICAL) 用例的重要程度

    4.12 Mock：依赖的系统还没好怎么办¶

    真实系统往往要调用别的系统：支付要调银行，下单要调物流，注册要发短信。这些外部系统可能还没开发完、测试环境里不稳定，或者调一次要花真钱。这时会用 Mock（模拟服务）：搭一个假的服务，按你的规定返回固定的结果，被测系统调它就像调真的一样。

    • 想测「银行返回扣款失败时订单怎么处理」，让 Mock 返回失败就行，不用真的去造一个余额不足的银行卡；
    • 常用工具有 WireMock、Apifox 和 Postman 自带的 Mock 服务，Python 里还有 responses 这类在代码里拦截请求的库；
    • UI 自动化里也有类似的手段：拦截页面发出的请求、返回假数据，第 11 章会用到。

    练习网站没有外部依赖，这里只要知道这个概念。

    4.13 数据库断言¶

    有些结果在接口返回里看不到，比如「支付后是否写了一条支付流水」，这时要直接查数据库核对。思路是：用例做完操作后，连上数据库查对应的记录并断言。以 MySQL 为例（需要 pip install pymysql，练习网站没有数据库，这段代码只演示写法）：

    import pymysql
import pytest

from common.api_client import ok


def query_one(sql, args=None):
    conn = pymysql.connect(host="数据库地址", port=3306, user="只读账号", password="口令从环境变量读",
                           database="shop", charset="utf8mb4")
    try:
        with conn.cursor(pymysql.cursors.DictCursor) as cur:
            cur.execute(sql, args)          # 参数用 %s 占位，不要自己拼字符串，防止 SQL 注入
            return cur.fetchone()
    finally:
        conn.close()


def test_pay_writes_flow(api, unpaid_order):
    ok(api.pay_order(unpaid_order["orderNo"]))
    flow = query_one("SELECT amount, status FROM pay_flow WHERE order_no = %s", (unpaid_order["orderNo"],))
    assert flow is not None, "支付后应该有一条支付流水"
    assert float(flow["amount"]) == pytest.approx(unpaid_order["amount"])

    注意：

    • 用只读账号，自动化脚本没有必要拥有改库的权限；
    • 数据写库可能有延迟（异步处理、消息队列），查不到时要稍等重试，别马上判失败；
    • 数据库的表结构属于实现细节，变得比接口快。能用接口核对的优先用接口，数据库断言留给接口确实看不到的地方。

    4.15 常见的坑¶

    现象 原因与解决
    ModuleNotFoundError: No module named 'common' pytest.ini 里没写 pythonpath = .，或者 common 文件夹里没有 __init__.py
    跑完一条用例，后面的用例全部 401 某条用例让共享的 token 失效了（比如退出登录），改成用专用账号
    用例单独跑能过，一起跑就挂 数据互相影响：断言了绝对值，或者用了别的用例留下的数据
    报告里新旧结果混在一起 生成结果时没加 --clean-alluredir
    allure 不是内部或外部命令 Node.js 或 Allure 没装好，或者装完没有新开命令行窗口
    双击报告是空白页 生成的是多文件报告，用 allure open 打开，或者在配置里开启 singleFile
    日志和报告里出现了明文口令 打印前没遮蔽，所有输出都要过一遍 mask()
